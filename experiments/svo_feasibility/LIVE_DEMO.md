## 3. 現場講法

這個展示不是要宣稱真實系統在所有資料上都能得到 1.00，而是證明我已經把「如何驗證 SVO 關係」做成可執行閉環。

這個閉環包含四件事：

1. 有原始文本資料集。
2. 有示範用 gold triples。
3. 有不同方法的三元組輸出。
4. 有 evaluator 可以計算關係正確性與來源可追溯性。

所以我不是只說「知識圖譜比較好」，而是把關係是否正確轉成可以檢查的指標：

- Precision 檢查抽出的關係有多少是真的。
- Recall 檢查標準答案中的關係有多少被抽到。
- F1 綜合 Precision 與 Recall。
- Traceability 檢查抽對的關係是否能回到支持它的來源句。

## 4. 面對專家追問時的回答

如果被問：「為什麼 verified_svo 是 1.00？」

回答：

> 因為這是最小展示資料集，用來證明 evaluator 與驗證格式成立，不是宣稱模型在真實大資料上已經滿分。這個 demo 證明的是「可以驗證」，不是「已經穩定」。驗證通過的三元組才被承認；未通過的三元組只能當候選關係。下一步是把主系統抽出的 SVO 輸出轉成同樣格式，放進這套 evaluator 跑真實實驗，逐步提高抽取品質與驗證穩定性。

如果被問：「gold triples 哪來的？」

回答：

> 目前這份 gold triples 是示範用標準答案，由研究者根據這 4 句樣本文本先制定，用來證明評估流程可以跑通。它不是正式大規模人工標註資料集。正式實驗時，才會擴大資料量，並加入人工標註或人工審核流程。

如果被問：「pure RAG 為什麼是 0？」

回答：

> 這裡的 pure RAG proxy 代表只回傳相關文字，沒有輸出明確 SVO 關係。因此它可能能回答問題，但無法用三元組層級的 Precision/Recall 直接證明關係是否正確。這正是我想凸顯的差異：RAG 偏向找文本，SVO/KG 偏向驗證關係。

如果被問：「這和主專案怎麼接？」

回答：

> 主專案目前已有 SVO 抽取、來源追溯、實體合併、事實去重與 BFS 查詢。這個子項目負責把研究驗證標準獨立出來；之後只要把主系統輸出的 SVO 轉成 sample_predictions.json 的格式，就能用同一個 evaluator 評估。
