## 2.2 各研究問題（RQ1-RQ6）核心文獻總覽

本節逐條列出六個研究問題（RQ1-RQ3 確定、RQ4a/RQ4b/RQ5/RQ6 預留）各自的核心參考文獻與其扮演的角色，細節留待 2.4 節逐階段展開，完整書目與本地檔案見 `docs/論文/附錄與參考文獻.md`。

**RQ1（KG-BFS 架構相較當代 RAG 強基準的優勢邊界）**：核心文獻為 Han et al.（2025，🟡）《RAG vs. GraphRAG》與 Xiang et al.（2025，🟢 ICLR 2026）《When to use Graphs in RAG》，兩者皆挑戰「圖結構全面優於向量檢索」的預設，主張優勢具**任務依賴性**；Fan et al.（2026，🟡）《Do We Still Need GraphRAG?》進一步指出 Agentic 迭代式搜尋能縮小與 GraphRAG 的效能差距。本論文據此設計消融實驗，界定 KG-BFS 相較強化版文字 RAG／Agentic RAG 仍然成立的具體查詢任務類型，而非重複驗證已有共識的問題。完整回顧見 2.4.3。

**RQ3（自我精煉檢索迴圈）**：核心文獻為 Self-RAG（Asai et al., 2023，🟢 ICLR 2024）、FLARE（Jiang et al., 2023，🟢 EMNLP 2023）、IRCoT（Trivedi et al., 2022，🟢 ACL 2023）三篇主動式/反思式檢索文獻，本論文延伸其評估範疇至結構化三元組 Context，機制上與三者皆有明確差異。完整回顧見 2.4.7。

**RQ4a（受控語意關係詞彙標準化）**：核心文獻為 Schema.org（Guha et al., 2016，🟢 全文已於 2026-08-20 補齊精讀）與 Wikidata（Vrandečić & Krötzsch, 2014，🟢 已精讀全文），對照開放抽取陣營的 Stanford OpenIE（Angeli et al., 2015，🟢）與 CESI（Vashishth et al., 2018，🟢）。完整回顧見 2.4.4。

## 2.3 比較表：歷史 RAG、當代 RAG 基準、GraphRAG、本論文

Lewis et al.（2020）的 RAG 是技術起點，但不應作為本論文價值主張的唯一基準線。2025-2026 年的比較文獻已顯示，GraphRAG 相對一般 RAG 的優勢具有任務依賴性，且 Agentic RAG／迭代式搜尋已能大幅縮小純文字檢索與 GraphRAG 的差距。因此，本論文的合理比較標準應是「當代強化版 RAG」：至少包含向量檢索加重排序或混合檢索、查詢分解/多輪檢索，以及 Self-RAG/Agentic RAG 類型的反思式精煉。換言之，本專案的價值不能寫成「勝過 2020 年單次 RAG」，而應寫成「在當代 RAG 已具備主動檢索與精煉能力後，知識圖譜層是否仍能在可追溯多跳推理、多知識庫路由、時序事實管理與圖結構治理上提供可測量的額外收益」。

本節依第三章系統設計與方法論的章節順序，逐一補充該階段所採方法的文獻/專案佐證，讓「這個機制為什麼這樣設計」與「第三章的哪個節點」的對應關係一目瞭然。3.1.2-3.1.4（抽取任務佇列、抽取過程、抽取後續）三節本身純屬工程機制描述，其涉及的受控詞彙/別名消解理論已分別歸入 2.4.4／2.4.5，此處不重複列節。

### 2.4.1 對應 3.1.1（暫存區分類與自動分群）

第三章 3.1 節開頭已聲明：暫存區分類與抽取斷點續傳屬建圖流程的基礎工程機制，非本論文六項研究問題（RQ1-RQ6）的驗證對象。但 3.1.1 節（暫存區分類與資料夾歸檔）與 3.1.1 §a（AI 自動分群機制）的分類分數計算、分群演算法、命名輸入篩選三個子機制，皆刻意選擇以有廣泛驗證基礎的文獻/專案為主要參考起點，而非直接沿用 v1（智慧知識庫）的既有實作——這個查證過程本身具備方法論意義，值得獨立記錄。本節依 3.1.1 的流程順序（分類 → 分群）分兩部分整理。

#### 2.4.1.1 分類分數：質心/原型式路由

3.1.1 節 `CMP` 節點的分類分數計算，採 **Prototypical Networks**（Snell, Swersky, Zemel, 2017，🟢 NeurIPS 2017）的 centroid 相似度精神——將每個類別（本論文語境下為每個 KG）表示成其支持集（成員文件）表徵向量的平均（prototype），新樣本依其表徵向量與各類別 prototype 的距離分類。這是 few-shot 分類文獻中被廣泛驗證、實作簡單且不需訓練額外參數的方法，適合本論文「KG 數量與每個 KG 的文件數皆隨使用逐步增長、無法預先準備大量標註訓練資料」的場景。

**可信任專案背書（產業驗證，🟡 部分吻合）**：以 embedding 相似度做離散類別路由，並非只有本論文與 Snell et al.（2017）如此設計——**semantic-router**（Aurelio Labs，[aurelio-labs/semantic-router](https://github.com/aurelio-labs/semantic-router)，3,738★，2026-07-23 GitHub API 查證）是持續維護的生產級語意路由函式庫，驗證了「查詢向量與類別代表向量比對以決定路由」這個大方向已是業界實際部署的設計模式。但查證其 GitHub Discussion #451 維護者說明後發現，該專案的實際機制是**即時 kNN**——查詢向量與每個 route 底下每一句範例語句個別比對取 cosine 距離，再對 top-k 結果做聚合（`aggregation`，可設 mean/sum）決定路由，並非預先算好單一 centroid 向量後只比對一次。**此處需誠實區分兩個層次**：semantic-router 佐證的是「embedding 相似度可作為離散分類的生產級信號」這個較粗的設計選擇，並不直接佐證 `CMP` 節點「預先計算單一 KG prototype 向量」這個具體機制——後者仍以 Snell et al.（2017）的原型網路精神為直接依據，兩者不可混為一談。

**與本論文的關係**：3.1.1 節 `CMP` 節點的 centroid 相似度分類，其演算法依據是 Prototypical Networks；semantic-router 僅作為「同一大類設計模式已有獨立生產實例」的旁證，用以說明本論文的技術選型並非脫離業界實踐的孤立設計，但不構成對 `CMP` 具體實作機制的直接驗證。

#### 2.4.1.2 AI 自動分群：HDBSCAN + LLM 命名

3.1.1 §a 的分群演算法採 **HDBSCAN**（McInnes, Healy, Astels, 2017，🟢 *Journal of Open Source Software*），命名輸入篩選採 **Khandelwal（2025，🟡）**《Using LLM-Based Approaches to Enhance and Automate Topic Labeling》驗證表現最佳的主導子群法（詳見第三章 3.1.1 §a 節）。

**參考專案（2026-07-23 補齊，區分「直接依賴」與「架構背書」兩個不同層次）**：

1. **直接依賴套件**：`services/cluster_service.py` 直接 `import hdbscan`，實際呼叫的就是論文作者本人維護的官方參考實作 [scikit-learn-contrib/hdbscan](https://github.com/scikit-learn-contrib/hdbscan)（3,132★，2026-07-23 GitHub API 查證）——這不是「架構模式的獨立佐證」，是本論文程式碼實際執行的套件本身，證據等級最高：不只是「這個演算法理論上可行」，而是「這個演算法的官方實作可以直接跑在本論文的程式碼裡」。

### 2.4.2 對應 3.2 §a（ConceptNode 路由層，RQ2）

**GraphRAG 核心方法**：Edge et al.（2024，🟡 arXiv 預印本，微軟研究院）提出的 GraphRAG，流程為文字切片 → LLM 抽取實體與關係 → 跨片段的同一實體/關係描述整併摘要 → 建圖 → 階層式 Leiden 社群偵測（遞迴切分至無法再分的葉節點社群）→ 逐社群生成摘要報告 → 查詢時依需求選擇 **Local Search**（以特定實體為中心的局部檢索）或 **Global Search**（跨社群摘要的 map-reduce 式問答）。此設計解決了純向量 RAG 無法回答「總結全文重點」這類全局性查詢的問題，但其架構預設是**單一大圖**，對「多個獨立知識圖譜並存」的場景著墨甚少——這正是第一章 1.1.3 節已指出的具體缺口，也是本論文 RQ2（多知識庫路由）的直接出發點。

**增量更新與可擴展性的旁支討論**：GraphRAG 官方 GitHub（microsoft/graphrag#741）本身承認新增文件需要重新跑過整個社群結構，無法增量更新。**LightRAG**（Guo et al., 2024，🟢 EMNLP 2025）改用雙層檢索（低層節點對應具體實體、高層叢集對應主題關係）取代階層社群摘要；**EraRAG**（Zhang et al., 2025，🟡）以 LSH（局部敏感雜湊）分群，只對受影響的圖區域做局部重新切分。此問題屬於**工程借鏡型**改善（見 `docs/報告/03_核心架構藍圖.md` 痛點 1 分類），業界已有成熟解法可直接參考，本論文不將其列為研究問題。

**與本論文的關係**：本論文第三章 3.2 §a 節的路由層（ConceptNode）與 Microsoft GraphRAG 的「單圖＋社群摘要」是不同的架構選擇，完整比較見 2.3 表格。RQ2 驗證的是「輕量路由層＋BFS 知識層」這個具體兩層架構在準確率、延遲、可擴展性上的效能取捨——業界對照為 **WhyHow.ai** 的 namespace 隔離機制，但未見系統性效能驗證（見 1.2 節 RQ2 範圍澄清），本論文填補的是這個驗證缺口，而非提出全新的隔離機制本身。**熱度佐證與誠實侷限（2026-07-23 補齊，完整查證見 `docs/報告/產品競品研究/00_總覽.md`）**：WhyHow.ai 目前主力產品 `whyhow-ai/knowledge-graph-studio` 929★／107 forks（MIT），較早期的純 SDK `whyhow-ai/whyhow`（namespace 隔離機制實際所在的套件）僅 128★ 且已停止更新——相較 RAGFlow（85,733★）、Neo4j LLM Knowledge Graph Builder（約 4,955★）等其他業界對照，WhyHow.ai 的規模明顯小得多，「業界對照」一詞應理解為「確有此類產品存在」而非「已獲廣泛驗證的成熟做法」，這點在寫作定稿時需要誠實反映在措辭強度上。

### 2.4.3 對應 3.2 §b（BFS 圖遍歷，RQ1）

**GraphRAG 是否真的優於一般 RAG？——一個正在進行中的學界辯論。** 近兩年（2025-2026）出現多篇論文對「圖結構是否天生有利於 RAG」提出質疑，而非預設圖結構全面優於一般向量檢索：

- **Han et al.（2025，🟡）**《RAG vs. GraphRAG: A Systematic Evaluation and Key Insights》系統性實證比較顯示，GraphRAG 相對優勢是**任務依賴**的，並非全面優於一般 RAG；該文獻同時揭露 LLM-as-Judge 評估協定存在**位置偏誤**（同樣兩個答案，放在評審 prompt 的前後順序不同，評審 LLM 的偏好會改變），直接質疑 Edge et al.（2024）原始論文所用的「comprehensiveness/diversity/empowerment」LLM 評審協定的可靠性。
- **Xiang et al.（2025，🟢 ICLR 2026）**《When to use Graphs in RAG》提出的核心發現是：「近期研究報告 GraphRAG 在許多真實任務上經常表現不如一般 RAG」，並建立 GraphRAG-Bench 基準，測試圖結構究竟在哪類任務（事實檢索／複雜推理／摘要／創意生成）才真正有幫助，而非預設圖結構全面有利。
- **Fan et al.（2026，🟡）**《Do We Still Need GraphRAG?》發現 Agentic（迭代式）搜尋能大幅縮小與 GraphRAG 的效能差距，GraphRAG 的優勢主要僅在複雜多跳推理場景才站得住腳——換言之，建圖成本只在特定查詢類型下才划算，並非普遍成立。
- 另有 **FG-RAG**（Hong et al., 2025，🟢 CIKM 2025）指出社群摘要整合的是實體的「內在」資訊而非「查詢相關」資訊，**NodeRAG**（Xu et al., 2025，🟡）指出檢索一個實體會不分青紅皂白帶入所有關聯事件（顆粒度太粗），兩者都從不同角度支持「社群摘要式檢索有結構性代價」這個判斷。

**與本論文的關係**：RQ1（KG-BFS 相較當代 RAG 強基準的優勢邊界）直接回應 Han et al.（2025）、Xiang et al.（2025）與 Fan et al.（2026）「GraphRAG 優勢具任務依賴性，且 Agentic 搜尋會縮小差距」的核心論點——本論文不泛問「圖結構是否優於向量檢索」（此問題已有上述文獻回答，結論是任務依賴的），而是在本論文的具體架構（3.2 §b 的 2-hop BFS 圖遍歷）上，系統性界定相對強化版文字 RAG／Agentic RAG 仍有優勢的查詢任務類型與邊界條件，完整架構比較見 2.3 表格。

### 2.4.4 對應 3.3（受控語意關係抽取，RQ4a）；同時是 3.1.3 `SVO_REL_TYPES` 受控詞彙機制的文獻依據

**與 3.1.3 的雙向連結（此前僅單向，2026-07-23 補上）**：3.1.3 節「為什麼選擇受控詞彙而非開放抽取」只做指標引用（「見 3.3（RQ4a）」），文獻討論集中於本節——與上方 2.4.5／3.1.2 是同一種分工模式（3.1 只描述機制怎麼跑，文獻佐證集中在對應 RQ 小節），3.1.3 並非缺乏文獻，只是刻意不重複展開。

開放資訊抽取（Open Information Extraction, OpenIE）容許任意動詞字串作為關係謂語，優點是召回率高、不受限於預先定義的關係集合，代表性基準線為 **Stanford OpenIE**（Angeli et al., 2015，🟢 ACL 2015）。但開放抽取的代價是語意不一致——**CESI**（Vashishth et al., 2018，🟢 WWW 2018）明確指出，語意相同的關係常以不同字串存入知識庫（例如「創立」「成立」「建立」被記為三個不同的關係謂語），CESI 因此提出以規範化（canonicalization）技術把這些字串收斂到同一個關係節點，這是開放抽取陣營內部嘗試解決一致性問題的代表性工作。

另一條路徑是**受控詞彙標準化**——以預先定義的本體或詞彙表限定關係類型的取值範圍。**Schema.org**（Guha et al., 2016）是網頁結構化資料領域的重要受控詞彙標準，可作為「由社群治理受控詞彙」的文獻錨點；但本論文已放棄原先評估的「結構驗證→語意驗證」循序閘門。現行設計改以 ConceptNet 33 類作為關係型別內容起點，再透過 cosine 相似度、灰色地帶 LLM 仲裁與 `EXPAND` 治理流程處理未知型別，具體方法見第三章 3.1.3 與 3.3 節。

✅ **全文查證與精讀完成（2026-08-20 補齊）**：**Guha, Brickley & Macbeth（2016，🟢 CACM 59(2) / ACM Queue 13(9)）**《Schema.org: Evolution of Structured Data on the Web》已透過 ACM Queue 開放取用版本取得完整全文並精讀（收錄於 `docs/參考文獻/03_資訊抽取與本體設計/guha-et-al-2016-schema-org-cacm.pdf`）。精讀確認四項關鍵設計決策：① 多語法支援（Microdata/RDFa/JSON-LD 並行）；② 多型性關聯（允許多 domain/range，避免傳統 OWL 冗餘超類別）；③ 實體消解負擔轉移（不強求全域唯一 URI，交由消費者端進行 reconciliation）；④ 階層化擴展機制（Core + Hosted + External Extensions）。這完全契合本論文第三章 3.3 節受控詞彙與擴展機制的設計理念，原文獻缺口已全數補齊。

**RQ4a 雙軌查證來源**：除了 Guha et al.（2016）Schema.org 外，同樣發表於 CACM 且**作者提供開放取用全文**的 **Vrandečić & Krötzsch（2014，🟢 *Communications of the ACM* 57(10)）**《Wikidata: A Free Collaborative Knowledgebase》亦作為並行佐證——此文描述了 Wikidata 屬性（property）**必須指定 datatype**（結構層限制）、且 schema 本身與資料一樣受社群治理（"Contributors edit the population number of Rome but also decide whether there is such a number in the first place"），社群另訂定語意限制條件（如「一個項目最多只能有一個出生地」）並以外部工具掃描違規資料（語意層檢查）。這證實了「受控詞彙的結構層與語意層可分別治理」是已在生產級系統規模化運作（截至該文寫作時已有 1,176 個屬性、4300 萬筆陳述句）的真實設計模式。**誠實的適配度聲明**：Wikidata 論文並未描述 Schema.org 式「結構驗證→語意驗證」**循序、單一審核閘門**的精確機制（其 datatype 限制與語意限制檢查是兩套獨立運作的機制，非新詞彙進入系統前的循序關卡），因此**不能宣稱兩者機制等價**，僅能作為「此類設計模式有生產級先例」的獨立佐證，與 Schema.org 本身的類比仍以 Guha et al.（2016）為準——完整適配度分析見 `docs/參考文獻/03_資訊抽取與本體設計/README.md`。

**與本論文的關係**：本論文選擇受控語意關係詞彙（`SVO_REL_TYPES`，現行 35 類，見第三章 3.3／3.1.3 節；此數字歷經 30→35→33→35 四次調整，完整查證歷程見下方 2026-07-24 起各段與 `docs/論文/03_變更紀錄.md`，此處 2026-08-19 訂正為與全文其餘段落一致的現行值），是刻意驗證「封閉式抽取」這個極端選項，而非業界更常見的開放式或半開放式抽取路線。這個選擇需要對比開放式抽取的文獻（Angeli et al., 2015 為基準線，CESI 為開放抽取陣營內部的一致性補強方案）以說明 trade-off：受控集合能保證語意一致性與可追溯性，但必然犧牲部分細緻語意的召回率，此 trade-off 正是 RQ4a（預留）要實證回答的問題。

**抽取流程該不該分階段處理（2026-07-26 新增討論；同日補齊全文精讀後訂正）**：3.1.3 節的 `LLM_SVO`（原始抽取＋實體型別提案）與 `SIM`／`ESCALATE3`／`EXPAND`（關係型別收斂比對）本來就分屬不同節點，本身已是分階段設計，而非塞進單一 LLM 呼叫一次做完。**AutoRE**（Xue, Zhang, Dong & Tang, 2024，🟢 ACL 2024 System Demonstrations）——全文精讀確認 §4.3 逐字寫明「the data volume for the three subtasks begin approximately 2.8%, 24.23%, and 72.97%, respectively」，摘要層級記錄的數字無誤——提出 RHF（Relation-Head-Facts）三階段拆解（關係判斷→主詞辨識→事實抽取，順序與本論文相反，本論文先抽三元組再收斂型別），佐證「關係型別判斷該與原始抽取分開處理」的方向，但其拆分動機是微調模型的訓練資料量失衡問題，是微調場景、非本論文採用的 prompting 場景，**具體機制不可直接套用**，僅能佐證「拆開處理避免困難子任務被簡單子任務淹沒」這個大方向。⚠️ **KGGen 誠實訂正（2026-07-26 全文精讀後發現原記錄有誤）**：**KGGen**（Mo, Yu, Kazdan, Cabezas, Mpala, Yu, Cundy, Kanatsoulis & Koyejo, 2025，🟢 NeurIPS 2025）§4.1 對「先抽實體、再抽關係」兩步驟的實際說明是「to ensure consistency between entities」（確保實體一致性），並未如原摘要層級記錄所稱明確以「降低認知負荷、減少錯誤傳播」為理由，此為查證過度延伸，已訂正。全文精讀後找到更貼切的段落：KGGen §4.3「Entity and Edge Resolution」——候選項目先以 S-BERT embedding＋k-means 分群，群內用 BM25＋語意相似度混合檢索近鄰，再由 LLM 判斷是否為真正重複並選出 canonical 代表名稱（原文明確類比「similar to aliases that Wikidata uses」）——這個「分群→LLM 判斷→LLM 命名」流程，比先前引用的「實體/關係兩階段抽取」更直接對應 3.1.3 §a `EXPAND` 治理機制的流程結構，且有量化驗證（Fig.7：KGGen 每個關係型別平均重用 10 次 vs. GraphRAG 的 2 次，佐證聚合式收斂機制能提升型別可重用性）。⚠️ 誠實適配度：KGGen 的分群解析是**去重合併**（同義詞收斂），本論文 `EXPAND` 是**判斷是否構成全新型別**（新增類別），問題方向不同，具體機制不可直接套用，僅佐證「分群＋LLM 判斷/命名」組合模式在 KG 抽取領域已有量化驗證的先例。

**`SIM`／`ESCALATE3` cosine+LLM 仲裁「具體組合」的理論依據（2026-07-26 新增查證，取代原「查無直接對應開源專案或論文先例」的結論）**：使用者提出「embedding 信心夠高就直接採信、信心不足才交給 LLM 仲裁，LLM 的仲裁結果再回頭校正 embedding 的準確度」的具體構想後，查證確認這正是機器學習界已有正式理論框架的 **confidence-based cascade deferral**（層級式模型交棒）研究方向。核心文獻為 **Jitkrittum, Gupta, Menon, Narasimhan, Rawat & Kumar（2023，🟢 NeurIPS 2023，Google Research）**《When Does Confidence-Based Cascade Deferral Suffice?》——以 Bayes-optimal deferral rule（其 Proposition 3.1）證明本論文設想的「目前模型信心夠高就直接判斷、否則交給下一個模型」機制，**當下游模型（本論文情境為 LLM）的錯誤機率對所有輸入大致均勻時最佳，但當下游模型是「專才」（specialist，對某些輸入類型特別準、對其他類型不特別準）時會系統性失效**（以 ImageNet 專才模型實驗量化證明）；論文提出的解法是用驗證集訓練一個輕量的 **post-hoc deferral rule**（Table 1：`Diff-01`／`Diff-Prob`／`MaxProb`，皆為小型 MLP），取代單純看模型一自身信心的門檻規則——這正是使用者所說「LLM 的決定回頭強化 embedding 準確度」的精確、有嚴謹理論基礎的具體做法：不需要 reward function 與 policy 的強化學習，而是用 LLM 過去的仲裁結果（是否推翻 embedding 初步判斷）當訓練標籤，訓練一個小型評分器校正未來的信心門檻。論文並將此框架推廣至 K>2 模型的多階段 cascade（其附錄 F），可直接對應本論文 `SIM → ESCALATE3 → EXPAND` 三階段管線。補充術語與理論定位文獻為 **Madras, Pitassi & Zemel（2018，🟢 NeurIPS 2018）**《Predict Responsibly: Learning to Defer》，提出 learning-to-defer（適應性拒絕學習）這個更早、更廣為人知的框架名稱，確認本論文機制屬於這個成熟研究方向的一個實例，非孤立自創；⚠️ 誠實適配度：其核心演算法是端對端聯合訓練（需要 ground-truth 標籤），沒有「用被轉交對象過去的判斷持續線上校正」這個回饋迴圈，此部分仍以上述 Jitkrittum et al. (2023) 的 post-hoc deferral rule 為準。**參考專案**：`stevenkolawole/Agreement-Based-Cascading`（GitHub）實作 FrugalGPT 風格的 LLM cascade 路由，佐證此類機制已應用於 LLM 系統，業界原始文獻 **FrugalGPT**（Chen, Zaharia & Zou, 2023，`docs/參考文獻/03_資訊抽取與本體設計/chen-zaharia-zou-2023-frugalgpt.pdf`）全文已於 2026-08-20 完成下載收錄。⚠️ **誠實訂正（2026-08-19，籌備新資料集抽取任務前盤點時發現）**：這是本文件目前唯一一個引用時未同步揭露 GitHub star 數的專案參考——即時 `gh api` 查證僅 **4★**，`archived: false` 但最後一次 push 為 2025-07-30，遠低於本文件其餘專案引用一貫要求的「有一定星數/瀏覽量證明可信任」門檻。**角色降級**：此專案不再列為獨立佐證，只作為「查有這樣一份公開程式碼、方向與 FrugalGPT 風格 cascade 路由相符」的存在性註記，不具備原先隱含的「已被廣泛驗證」份量；本節論點的實質支撐仍以已逐字精讀全文的 Jitkrittum et al.（2023）與 Madras et al.（2018）兩篇正式文獻為準，不受此訂正影響。**本次查證帶出一項新的誠實提醒**：LLM 作為本論文的下游仲裁模型，很可能正是 Jitkrittum et al. **`SIM` 比對目標應為型別描述句 embedding，而非型別識別碼字串本身（2026-07-27 新增查證）**：盤點時發現 `SIM` 現行設計是拿 `verb` embedding 去跟 35 個型別的**原始識別碼字串**（如 `MOTIVATED_BY_GOAL`）算 cosine，這可能有問題——AutoRE（Xue et al., 2024，已於上方引用）自己的消融實驗（其 Table 2）發現：直接使用 Wikidata 原始的、生硬不清楚的關係描述做比對，效果反而比完全不給描述還差（D-R-F-wikidesc F1=6.44 < D-R-F-nodesc F1=8.31），改寫成清楚的自然語言描述後才大幅提升（D-R-F-newdesc F1=14.04）。查證確認這是一個有正式方法論支持的既定做法：**ZS-BERT**（Chen & Li, 2021，🟢 NAACL 2021）《ZS-BERT: Towards Zero-Shot Relation Extraction with Attribute Representation Learning》——逐字精讀全文，其核心機制與本論文 `SIM` 幾乎同構：用 Sentence-BERT（Reimers & Gurevych, 2019，本論文已引用）將**關係的自然語言描述**（非關係名稱本身）編碼成 attribute vector，輸入句子也編碼成向量，用最近鄰距離比對分類（§4.1 明確寫「We feed only the relation description... in order to get the attribute vector」）；在 Wiki-ZSL／FewRel 資料集上穩定超越所有比較基線（F1 至少高出 13.54%）。⚠️ 誠實聲明：ZS-BERT 實驗發現 inner product 比 cosine similarity 略優（其 Figure 4 右圖），與本論文既有 cosine 慣例不同，但這是次要的距離函式選擇，不影響「比對目標該用描述句 embedding、非識別碼字串」這個主張本身。**範例句來源查證**：ConceptNet 官方 GitHub wiki（`commonsense/conceptnet5/wiki/Relations`，即時查詢版本）本身即提供每個核心關係的定義與範例詞對（如 `UsedFor`：「A 用於 B」，範例 bridge→cross water），可直接沿用作為 `SIM` 比對目標的描述來源，不需自行撰寫，文獻可追溯性優於 AutoRE 自創描述的做法。查證過程意外發現：此官方 wiki 已將 `Entails`／`InstanceOf` 列為棄用（詳見下一段），使用者確認後決定跟進調整，`SVO_REL_TYPES` 由 35 個訂正為 **33 個**；扣除這 2 個棄用型別後，官方 wiki 涵蓋其中 32 個型別的定義/範例，唯一未列於此 wiki 的 `SenseOf` 則直接沿用 ConceptNet 論文正文自身的說明（"linked to it with the implicit relation SenseOf" 描述 `lead/n`（金屬鉛的名詞義）是 `lead`（一般用字）的 `SenseOf`）——32（官方 wiki）+1（論文正文）＝33 個型別皆有可追溯的定義/範例來源，完整清單見 `docs/參考文獻/03_資訊抽取與本體設計/README.md`。此設計方向（`SIM` 改比對描述句 embedding）目前僅記錄查證結果，具體資料結構（例如是否需要類似 `ENTITY_TYPES` 的描述字典）留待第四章實作時一併設計。⚠️ **2026-08-19 訂正**：官方 wiki 後續新增 `HasSubevent`／`EtymologicallyDerivedFrom` 兩個關係，`SVO_REL_TYPES` 由 33 個再訂正為 35 個（見上方段落），這兩筆描述句同樣可直接從官方 wiki 取得定義/範例，涵蓋率邏輯不變，僅總數更新。

**`EXPAND` 候選池門檻與 `COMPARE` 相似度門檻的文獻查證（2026-07-26 新增）**：使用者選擇先訂具體佔位數字（比照 3.4 §b `ENTITY_DEDUP_*` 三個門檻常數的既有慣例），但要求先查文獻佐證。逐字精讀 **Vashishth, Jain & Talukdar（2018，🟢 WWW 2018）**《CESI: Canonicalizing Open Knowledge Bases using Embeddings and Side Information》全文（原僅查證到「Semantic Drift」問題定義層級，本次補齊全文，包含方法論章節）發現一項關鍵事實：CESI 用 HAC（Hierarchical Agglomerative Clustering）對開放式抽取的關係短語 embedding 分群，其論文 §6 明確寫道分群門檻「chosen based on held out validation dataset」——**沒有找到可以直接套用的具體數字**，但確認了學界對這類問題的方法論共識：分群/相似度門檻必須用驗證集校準，不是能靠理論推導或套用其他論文數字決定的。作為對照，CESI 比較的基線 AMIE（Galárraga et al. 2013）使用固定門檻（support=2、confidence=0.2），但實驗結果顯示這組固定低門檻在 22K 個關係短語的 ReVerb45K 資料集上只歸納出 51 個非單例群集，召回率遠不及 CESI 校準式做法（CESI 論文 Table 3），佐證「套用其他任務的固定門檻」確有真實風險。**查證結論**：這**驗證了本論文既有的「先訂佔位數字、明確標註未驗證、留待第五章消融實驗校準」慣例本身即為文獻認可的正確作法**——`EXPAND_POOL_MIN_SIZE＝10`（類比 3.1.1 §a 文件分群 `min_cluster_size＝3` 抓高，理由是候選池為未聚合的單一動詞 embedding，噪訊比例預期較高）與 `COMPARE_COSINE_THRESHOLD＝0.75`（類比 3.4 §b `ENTITY_DEDUP_ESCALATE_LOW_THRESHOLD＝0.75`）皆為**借用既有常數數量級的暫定值，非從文獻直接推導**，第五章消融實驗需依本論文實際資料重新校準。完整查證見 `docs/參考文獻/03_資訊抽取與本體設計/README.md`。

**`EXPAND` 治理機制：分群審核、跨 KG 登記表、人工確認畢業機制（2026-07-26 新增討論；同日補充參考先例查證）**：3.1.3 節 `EXPAND` 觸發後如何審核新關係型別提案，完整機制定案於 3.1.3 §a（候選池累積→HDBSCAN 分群→LLM 判斷群集是否構成新類別→查詢跨 KG 關係型別登記表避免重複命名→人工確認或自動核准，視滾動窗口內人機一致率是否已達畢業門檻）。分群步驟沿用本節上方已引用的 McInnes, Healy & Astels（2017，🟢 *Journal of Open Source Software*，DOI: 10.21105/joss.00205，HDBSCAN——2026-08-19 訂正：此前誤標為「🟡 arXiv／JOSS」，即時查證確認為直接發表於 JOSS 的正式論文，查無獨立 arXiv 預印本，統一為與 2.4.1.2 一致的 🟢），LLM 仲裁步驟延續本論文既有的 `ESCALATE` 設計哲學（3.4 §b／3.1.3 `ESCALATE3`／3.2 §c `QESCALATE`），皆非新查證。**「跨 KG 關係型別登記表」與「人機一致率自動化畢業」兩項設計原標註「查無直接對應文獻」，2026-07-26 查證找到功能性先例**：① **跨 KG 登記表**——既有引用文獻 Vrandečić & Krötzsch（2014）Wikidata 背後的社群治理流程裡，Property Proposal 機制明確要求「新增屬性前先搜尋既有清單確認不重複」、公開討論達共識後才建立（`Wikidata:Property_proposal`／`Wikidata:Property_creation`，2026-07-26 直接擷取確認），扮演的「中央查重詞彙表」角色與本論文設計的問題結構相同；⚠️ 誠實適配度：Wikidata 是單一共用知識庫，不是「多個獨立 KG 各自查詢同一份登記表」的架構，且這是社群方針頁面而非論文正文內容。② **人機一致率自動化畢業**——**Bloodgood & Vijay-Shanker（2009，🟢 CoNLL 2009）**提出 Stabilizing Predictions (SP) 方法，用前後兩輪模型的 Cohen's Kappa 一致率連續穩定 k 輪（longevity window）決定是否停止再要求人工標註；**Bloodgood & Grothendieck（2013，🟢 CoNLL 2013）**進一步證明 Kappa 達門檻 T 時，兩輪模型 F-measure 差距有理論上界 4(1-T)/T。⚠️ 誠實適配度：原論文比對「前後兩輪模型」而非「LLM vs. 人工」，機制目的是「停止再要求標註」而非「讓某類判斷畢業成不需逐筆人工確認」，**具體機制不可直接套用，僅佐證「一致率作為減少人工介入的量化判準」這個大方向在學界有正式理論基礎**，兩項設計本身仍是本論文自行設計，非改寫自任何既有論文或系統。完整查證見 `docs/參考文獻/03_資訊抽取與本體設計/README.md`；完整設計脈絡見 3.1.3 §a、`docs/ARCHITECTURE.md`「跨 KG 關係型別登記表」決策條目。

### 2.4.5 對應 3.4（實體指代與別名消解，RQ4b）；同時是 3.1.2「指代消解前置法」設計決策的文獻依據

RQ4a 處理的是 SVO 三元組裡「V」（關係類型）該不該受控；RQ4b 處理的是「S／O」（實體本身）的另一半問題——同一個真實世界的實體，在文字裡可能以完全不同的字面形式出現：**代名詞**（他、它、該公司）、**全稱/簡稱/別名**（Interstate Highway 35／I-35／Interstate；Richard Stone／Stone／the defendant）。第三章 3.4 節的機制分兩層，分別解決「同一份文件內」與「跨文件」兩種不同尺度的指稱不一致問題。

**與 3.1.2 的雙向連結（此前僅單向，2026-07-23 補上）**：下方「句子級抽取若不處理指代消解會漏抽」段落的 Text2KGBench／CORE-KG 兩篇文獻，不只是 3.4 §a 機制本身的理論基礎，也是 **3.1.2「設計定案」段落**選擇「指代消解前置於切塊之前」、放棄原本評估過的滑動視窗方案這個具體決策的直接文獻依據——3.1.2 本身依本章 3.1 節開頭「純粹描述建圖流程，不深入個別 RQ 文獻」的分工原則，只做指標引用（「完整機制見 3.4 §a」），文獻討論集中於此節；換句話說，3.1.2 並非「查無文獻的純工程決策」，而是「文獻討論刻意集中在別處」，兩者性質不同，不應混為一談。完整比較過程（含已放棄的滑動視窗草案）見 `docs/論文/03_變更紀錄.md`「二、已評估但未採用的設計方案」。

**句子級抽取若不處理指代消解會漏抽**：**Text2KGBench**（Mihindukulasooriya et al., 2023，🟢 ISWC 2023）是本體論式受控三元組抽取的專門 benchmark，論文自承句子級抽取會漏抽跨句指代消解關係。**CORE-KG**（Meher, Domeniconi & Correa-Cabrera, 2025，🟡 KDD '25 Workshop）提出「指代消解前置於切塊之前」的解法，其消融研究（Meher & Domeniconi, 2025，🟡）量化證實移除指代消解模組使節點重複率上升 28.25%、雜訊節點增加 4.32%（LLaMA 3.3 70B，20 份真實法院文件）——這兩篇文獻共同支撐第三章 3.4 §a「別名消解跑在代名詞消解之前」這個順序決策的大方向，但論文任務性質是開放式抽取，與本論文受控詞彙場景不同，量化數字不可直接套用。

**`PRONCHECK`／`PRONLLM` 代名詞消解的文獻與專案查證（2026-07-23 補齊，來源整理自 `docs/報告/10_代名詞雙軌檢測與正則詞庫自動進化機制設計報告.md` 2026-07-21 全面修訂，此前未拉進本章正式引用鏈）：

- **參考專案（直接依賴）**：`services/pronoun_resolution_service.py::SpacyPosTagger` 與 `services/entity_extraction_service.py::SpacyNerTagger` 皆直接 `import spacy`，實際依賴 **spaCy**（[explosion/spaCy](https://github.com/explosion/spaCy)，33,766★，2026-07-23 GitHub API 查證）——與 2.4.1.1 的 `hdbscan` 同一類「直接依賴」等級的證據，其 `PRON`／`DET` 標籤依循 **Universal Dependencies 標準**（Nivre et al., 2016, LREC 2016），其 `PRON`／`DET` 標籤依循 **Universal Dependencies 標準**（Nivre et al., 2016，🟢 LREC 2016，`docs/參考文獻/09_SVO抽取切塊策略與指代消解/nivre-et-al-2016-universal-dependencies.pdf`，全文已於 2026-08-20 完成下載與核實）。
- **查無直接先例的部分**：本機制「正則/POS 雙軌預篩、僅偵測到代名詞才觸發 LLM」的省成本設計，10 報告已誠實查證 **fastcoref**（[shon-otmazgin/fastcoref](https://github.com/shon-otmazgin/fastcoref)，192★）與 **LangChain Guardrails** 皆不構成直接先例——fastcoref 只輸出 coreference clusters、未見雙軌預篩設計；LangChain Guardrails 是泛用防護閘門概念，與本機制具體用途不同。**已移除的錯誤引用**：原稿曾宣稱 Stanford CoreNLP（Manning et al., 2014）證實此類預篩可過濾 80% 無代詞句子，查證後確認查無出處且時代語境不符（2014 年不可能討論 LLM API 成本），已整條移除，不採改寫保留——這是本論文誠實框架運作的具體案例，供口試時作為「如何自我糾錯」的實例。**結論**：`PRONCHECK`／`PRONLLM` 的雙軌偵測設計與 `PROMOTE` 同樣屬於文獻/專案佐證皆薄弱、本論文自行設計的機制，差別在於 spaCy／UD 標準確實佐證了**底層詞性標註本身**是業界標準做法，只是「拿詞性標註結果去做雙軌預篩」這個應用層設計沒有先例。

**跨文件增量聚類架構的文獻先例**：文件內別名登記表的動態標準名提升規則（`should_promote_by_length()`，PROMOTE 節點）查無直接文獻先例，經三次修訂查證後誠實標註為本論文自行設計的工程決策（完整查證史見 `docs/參考文獻/10_跨文件實體別名消解與增量聚類/README.md`）。但「跨文件持續擴增、標準名隨語料修正」這個架構方向有真實文獻先例：**Rao, McNamee & Dredze（2010，🟢 COLING 2010）**是串流式跨文件實體指代消解的先驅論文，明確對照傳統離線貪婪聚合式聚類與串流場景的增量更新需求；**Ji, Grishman & Dang（2011，🟢 TAC 2011）**的 TAC-KBP Entity Linking track overview 是官方、跨文件、隨語料持續擴增聚類機制（NIL clustering）的最高權威先例；**Saeedi, Peukert & Rahm（2020，🟢 ESWC 2020）**提出知識圖譜場景下的增量式多來源實體對齊（FAMER 框架），與本論文「跨文件別名圖譜隨時間持續擴增」的目標場景最為貼近。**誠實侷限**：這 3 篇皆只佐證「跨文件增量聚類」的**架構層面**，皆未描述本論文需要的「標準名選取規則」具體演算法——該規則已改採頻率優先，文獻依據交叉引用 2.4.4 已有的 Wikidata（社群共識最常用名稱）與 CESI（頻率加權質心），兩層佐證分工詳見 `docs/參考文獻/10_跨文件實體別名消解與增量聚類/README.md`。

**與本論文的關係**：第三章 3.4 §a（文件內前處理）／§b（跨文件別名消解）兩節的機制設計本身——登記表比對＋分級 LLM 仲裁的具體流程——為本論文自行設計，非直接沿用 CORE-KG 或 Text2KGBench 的演算法，兩篇文獻驗證的是「指代消解該前置於切塊之前」這個大方向，不背書本論文登記表比對機制本身（見第三章 3.8 節誠實框架）。

### 2.4.7 對應 3.6（自我精煉檢索迴圈，RQ3）

Lewis et al.（2020，🟢 NeurIPS 2020）提出的 RAG 架構是這條技術線的起點：以 dense retriever 檢索若干段落，seq2seq generator 在生成時對檢索結果做邊際化（marginalize），首次把「參數化記憶」與「非參數化檢索記憶」結合進同一個端到端訓練框架，直接回應第一章 1.1.1 節 LeCun（2022）指出的「持久性記憶缺失」問題。然而 RAG 的檢索是**單次、一次性**的——檢索發生在生成之前，生成過程中不會重新評估「目前的檢索結果是否足夠」，這個侷限催生了後續一系列「主動式／反思式檢索」的研究：

- **FLARE**（Jiang et al., 2023，🟢 EMNLP 2023）在生成過程中預測下一句話的內容，若預測句子中出現低置信 token，才觸發新一輪檢索，讓檢索時機由生成過程動態決定，而非固定在生成之前一次性完成。
- **Self-RAG**（Asai et al., 2023，🟢 ICLR 2024）訓練模型輸出「反思標記」（reflection tokens），讓模型自行判斷「是否需要檢索」「檢索結果是否支持回答」「回答品質如何」，把檢索決策內化為模型生成的一部分。
- **IRCoT**（Trivedi et al., 2022，🟢 ACL 2023）將檢索與思維鏈（Chain-of-Thought）推理交錯進行——每產生一步推理，就據此推理結果觸發下一輪檢索，特別針對多跳問答（multi-hop QA）任務設計。

**與本論文的關係**：這條文獻線的共同關注點是「檢索時機與方式」的動態化，本論文第三章 3.6 節的自我精煉迴圈（對應 RQ3）與此脈絡直接對話，但機制上有明確差異，不能混為一談——FLARE／Self-RAG／IRCoT 三者作用的對象都是**自由文字段落**的檢索與生成，觸發訊號來自生成模型自身的 token 置信度或反思標記；本論文的自我精煉迴圈作用於**結構化三元組 Context**，觸發訊號與圖遍歷本身的信心（如種子實體命中數、BFS 路徑長度）綁定，回補動作是「擴大 BFS 跳數」而非「重新檢索文字段落」。

**參考專案查證（2026-07-23 補齊）**：三篇皆有作者釋出的官方程式碼，可供對照演算法實作細節（而非僅依賴論文文字描述）：**Self-RAG**（[AkariAsai/self-rag](https://github.com/AkariAsai/self-rag)，2,410★）、**FLARE**（[jzbjyb/FLARE](https://github.com/jzbjyb/FLARE)，669★）、**IRCoT**（[StonyBrookNLP/ircot](https://github.com/StonyBrookNLP/ircot)，272★，2026-07-23 GitHub API 查證）。**誠實侷限**：三個官方倉庫本身**皆未實作圖結構檢索**（皆針對自由文字段落），與上一段已聲明的機制差異一致——這些倉庫的參考價值僅止於「反思式/主動式檢索觸發邏輯的具體實作範例」，不能作為本論文自我精煉迴圈（作用於三元組 Context）本身的直接程式碼佐證，此節仍應歸類為第三章 3.8 節「本論文自行設計的工程決策」，官方倉庫只是設計動機層級的參照。

### 2.4.8 對應 3.7（向量引導圖剪枝，RQ6，預留）

高連結度節點（Hub Node）在圖遍歷時容易造成路徑爆炸——BFS 從種子實體出發，一旦某一跳命中連結數極高的節點（如知識圖譜中常見的「總稱性」實體），下一跳待展開的候選集合會急遽膨脹。這個現象過去多僅見於工程實務的 naive 硬截斷處理，但近兩年已出現正式的學術命名與初步解法：

- **CatRAG**（Lau et al., 2026，🟡）《Breaking the Static Graph》明確將此問題命名為**「Static Graph Fallacy」**（靜態圖謬誤）——索引時固定的轉移機率忽略了查詢依賴的邊相關性，導致隨機遊走被引導至高連結度的「樞紐」節點，卻未能抵達與查詢真正相關的下游證據。CatRAG 建立在 HippoRAG 2 之上，提出查詢自適應的圖遍歷取代固定轉移機率。同一現象在多篇 2025-2026 論文中也被交叉引用為「Hub Bias」或「degree centrality bias」，確認這是被學界認可的現象，而非單一論文的孤立說法。
- **PathRAG**（Chen et al., 2025，🟡）提出流量式剪枝（flow-based pruning），處理冗餘的關聯路徑以改善檢索到的資訊連貫性，在 6 個資料集、5 個評估維度上優於基準方法。

✅ **G-Retriever 全文查證已完成（2026-08-18 訂正，取代下方過時記錄）**：本段原寫「尚未下載全文...暫不作為確定引用」——**He et al.（2024，🟢 NeurIPS 2024）G-Retriever** 已於 2026-07-29 逐字精讀全文含附錄，正式收錄進 `docs/參考文獻/12_三元組事實層級向量化與檢索/`，並已在第三章 3.1.4 §a（事實層級向量化）正式引用——其 §5.1-5.3 對 node／edge 各自獨立用 Sentence-BERT 算 embedding、以 Prize-Collecting Steiner Tree（PCST）取代扁平相似度排序的機制，以及 Appendix D.4 與 KAPING 的實證比較（WebQSP 準確率 70.49 vs. 60.81），是本論文評估「未來若要從扁平檢索升級為結構感知檢索」的具體文獻依據。此過時記錄的重複版本亦出現於 `docs/論文/00_README.md`，已一併訂正。

**與本論文的關係**：第三章 3.7 節（向量引導圖剪枝，對應 RQ6，預留）的理論支撐正是 CatRAG 與 PathRAG 這兩篇文獻，但需誠實聲明：本論文目前規劃的設計是「查詢向量與出邊語意向量的相似度排序」，是一個**簡化的相似度剪枝方案**，並非 PCST（Prize-Collecting Steiner Tree）這類具備最佳化理論保證的嚴謹子圖檢索算法，也不是直接複用 CatRAG 或 PathRAG 的演算法實作。若 RQ6 最終納入正式貢獻，需要在第五章明確說明本論文簡化方案與文獻中嚴謹解法的差距，不能混淆兩者的方法論嚴謹程度。

**參考專案查證（2026-08-24 更新）**：**PathRAG** 有官方程式碼（[BUPT-GAMMA/PathRAG](https://github.com/BUPT-GAMMA/PathRAG)），可對照其流量式剪枝的實際實作方式。**CatRAG** 亦已確認有作者公開的[官方程式碼](https://github.com/kwunhang/CatRAG)，因此本節不再宣稱「查無可信倉庫」。但 CatRAG 尚未整合到本專案的 Neo4j + Cypher BFS 技術棧；若 RQ6 最終納入正式貢獻，仍需自行實作並與 naive 硬截斷做消融比較，不能宣稱直接複用 CatRAG 程式碼。完整來源與查核層級見[文獻與專案查核表](文獻與專案查核表.md)。

## 2.5 評估方法論的橫向文獻回顧

GraphRAG 評估方法論本身在 2025-2026 年才開始被系統性檢視，而非早已成熟。本節內容不對應第三章單一節點，而是橫跨 RQ1、RQ3、RQ4a、RQ4b、RQ5、RQ6 共同的評估方法論基礎，故獨立成節，不併入 2.4 節的逐階段結構：

- **Han et al.（2025，同 2.4.3）**揭露的 LLM-as-Judge **位置偏誤**，是任何以 LLM 作為評審的實驗設計都必須警惕的方法論陷阱。
- **Zhou et al.（2025，🟡）**《In-depth Analysis of Graph-based RAG in a Unified Framework》指出過去的 Graph RAG 論文彼此未曾在同一基準上比較過（可重現性問題），建立統一開源基準以修正此問題。
- **GraphRAG-Bench**（Xiao et al., 2025，🟡，香港理工大學＋騰訊優圖）指出現有基準測試對長上下文、大規模異質語料的測試普遍不足，多停留在淺層多跳、簡答型、常識性問題，未能真正檢驗圖結構帶來的價值。
- **Dong et al.（2025，🟡）**《Knowledge-Graph Based RAG System Evaluation Framework》指出標準 RAGAS 類指標無法捕捉圖結構特有的性質（多跳結構、社群/叢集語意），提出結合語意社群分群的評分框架。
- **可追溯性評估**：本論文第一章 1.1.4／1.2 節採用的 AIS（Attributable to Identified Sources）框架，出自 **Rashkin et al.（2021/2023，🟢 期刊版 *Computational Linguistics* 49, 2023）**，量化生成內容是否可歸因於明確標識的來源，是第三章 RQ3／RQ4a／RQ4b 可追溯性次要指標的評估依據；**Shuster et al.（2021，🟢 EMNLP 2021 Findings）**的實證結果（檢索增強可將對話幻覺率降低 60% 以上）則是本論文「低幻覺率」產品目標的實證支撐。

✅ **全文查證與下載完成（2026-08-20 補齊）**：**Yang et al.（2018，🟢 EMNLP 2018）HotpotQA**（多跳問答標準基準資料集，`docs/參考文獻/05_評估方法論/yang-et-al-2018-hotpotqa.pdf`）與 **Es et al.（2023/2024，🟢 EACL 2024）Ragas**（RAG 自動化評估框架，`docs/參考文獻/05_評估方法論/es-et-al-2023-ragas.pdf`）皆已全數完成全文下載並收錄至 `docs/參考文獻/05_評估方法論/`，正式納入第五章實驗設計（測試資料集與評估框架選型）之確定引用。

**與本論文的關係**：本節梳理的方法論陷阱（位置偏誤、可重現性缺口、圖結構專屬性質未被標準 RAGAS 捕捉）直接構成第五章實驗設計的依據——至少需避免 Han et al. 指出的位置偏誤，且評估指標不能只套用一般 RAGAS，需針對圖結構檢索設計專屬評估項目。

**Whisper**（Radford et al., 2022/2023，🟢 ICML 2023）是本專案「音訊/影片語音轉譯」功能的核心依據；**Trafilatura**（Barbaresi, 2021，🟢 ACL-IJCNLP 2021 System Demonstrations）是本專案「網頁正文擷取」功能的核心依據。兩篇文獻的完整查證與 `parser/README.md`「學術文獻支撐」章節的對應關係見附錄與參考文獻.md。

### 2.6.2 向量化模組（對應 3.1 總覽圖 `VEC`，完整 Behavior Tree 見 `core/providers/embedding/README.md`）

向量化本身不是本論文的研究問題，完整文獻佐證與 Behavior Tree 收納於 `core/providers/embedding/README.md`，不寫入第三章正文，此處僅摘要其角色：**Sentence-BERT**（Reimers & Gurevych, 2019，🟢 EMNLP-IJCNLP 2019）證明句子向量間 cosine 相似度可作為有意義的語意距離度量，支撐本專案 chunk 向量平均值＋cosine 相似度的分類/分群/路由設計（與 2.4.1.1 的 Prototypical Networks 精神一致，兩者共同構成 `CMP` 節點的完整理論基礎）；**Dense X Retrieval**（Chen et al., 2023/2024，🟢 EMNLP 2024）與 **Rethinking Chunk Size**（Bhat et al., 2025，🟡）分別回應切塊粒度的選型依據；**MTEB**（Muennighoff et al., 2022/2023，🟢 EACL 2023）的核心發現「沒有單一模型在所有任務上都最佳」，是本專案 embedding provider 可替換設計的實證支撐；**ColBERT**（Khattab & Zaharia, 2020，🟢 SIGIR 2020）的多向量後期互動機制列為未來優化方向，非現行採用。

### 2.6.3 事實層級去重（對應 3.1.4「事實層級去重」，2026-07-26 新增）

**查證背景**：3.1.4 節「事實層級去重」——同一 `(subject, rel_type, object)` 三元組若被多個不同 chunk／文件重複抽到，合併成單一 Neo4j 邊、來源改累積記錄於 `citations_json`——是全系統中唯一完全未經文獻/參考專案查證的環節，本次盤點後補齊。完整查證見 `docs/參考文獻/11_事實層級去重與知識融合/README.md`。

**資料結構層面**：**Vrandečić & Krötzsch（2014，🟢 CACM 57(10)）**《Wikidata》"Citation Needed" 一節描述 Wikidata 的每筆陳述（statement）皆可附加一份可變長度的參考來源清單（"a reference is simply a list of property-value pairs"），截至該文寫作時 43,189,145 筆陳述中已有 23,242,779 筆附帶至少一筆參考來源——「單一陳述＋可變長度來源清單」這個資料結構與本論文 `citations_json` 的設計高度對應。⚠️ 誠實適配度：Wikidata 的參考來源是社群成員手動附加的支持性引用（回答「這個陳述憑什麼可信」），本論文的 `citations_json` 是系統自動累積的抽取來源記錄（回答「這個事實抽自哪個 chunk」，服務 AIS 可追溯性）——動機不同，但資料結構層面高度一致，可作為此結構模式已見於生產級系統的獨立佐證。

**問題成因與處理方向層面**：**Dong et al.（2014，🟢 KDD 2014）**《Knowledge Vault: A Web-Scale Approach to Probabilistic Knowledge Fusion》第 3.2／3.5 節直接處理同一類問題——同一三元組被多個不同來源各自抽取時如何處理：其融合分類器以「獨立來源數」與「平均信心分數」作為特徵計算最終信心值，且明確處理「同一網域內多篇頁面重複內容會虛灌證據數」的問題，解法是**每個網域只計一次而非每個 URL 各自計一次**。此與本論文「同一事實即使來自不同、完全不重疊的 chunk，也不該產生多條邊」的問題結構高度平行，皆屬「避免重複來源虛灌邊數/證據數」的同一類問題，只是計數單位不同（網域 vs. 三元組本身）。⚠️ 誠實適配度：KV 解決的是信心分數融合（多筆來源→一個機率值，來源本身不個別保留），本論文解決的是結構化來源保留（多筆來源→逐筆保留成 `citations_json`）——具體機制不可直接套用；且 KV 的「信心隨獨立來源數增加而上升」與本論文現行「`confidence` 取所有引用中的最大值」方向不同，此為值得留意但非本次要處理的設計差異。

**與本論文的關係**：兩篇文獻皆只提供功能性先例，「MERGE 鍵重新設計」「`citations_json` 累積來源」「confidence 取最大值」三項具體設計仍是本論文自行決定，非改寫自任一文獻。

### 2.6.4 多型態資料來源與結構保留（對應第三章 3.1.5；產品架構基礎，不另立 RQ）

本產品的輸入不應被限制為自然語言文件。JSON、JSON API、SQL 資料表、CSV／XML、既有 RDF／KG 與文件都可能是知識來源；若先把所有來源轉成一段自然語言，再交給同一套抽取流程，雖然可以共用文字檢索介面，卻可能丟失主鍵／外鍵、陣列邊界、`null`、布林／數值型別、單位、時間欄位與原始欄位路徑。這不是單純的格式轉換問題，而是來源語意與可追溯性問題。

本節採用以下文獻／標準分工：

| 來源 | 可支撐的設計原則 | 與本專案的關係 |
|---|---|---|
| **JSON-LD 1.1**（W3C Recommendation） | JSON 文件可以透過 `@context` 對應語意 IRI，讓 JSON 可保留原有使用方式，同時具備可交換的語意表示 | 支撐「Source JSON 與 Canonical Semantic Layer 分離」；本專案不宣稱直接採用 JSON-LD 序列化 |
| **R2RML**（W3C Recommendation） | 可宣告關聯式資料表、欄位、連接與目標詞彙之間的客製化映射；映射可產生虛擬 RDF 或 materialized RDF | 支撐 `SQL／資料庫 → Mapping Plan → Canonical Record` 的設計方向；不等於本專案直接使用 R2RML |
| **Direct Mapping of Relational Data to RDF**（W3C Recommendation） | 以資料庫 schema、表格與 foreign key 建立預設圖形表示，保留關聯式結構 | 支撐 Schema Profiler 必須辨識主鍵／外鍵，而非只讀取欄位文字 |
| **SHACL**（W3C Recommendation） | 以 shapes 與 constraints 描述 RDF graph 的結構，並在資料圖上產生驗證結果 | 支撐 Canonical Record 寫入 KG 前的結構驗證；本專案仍需自行決定 Neo4j／SHACL 的整合方式 |
| **PROV-O**（W3C Recommendation） | 以 Entity、Activity、Agent 與 `wasGeneratedBy` 等關係表達資料來源與生成活動 | 支撐保留 `source_id`、raw snapshot、mapping version、extractor version 與匯入活動 |
| **Data on the Web Best Practices**（W3C Recommendation） | 建議提供 structural metadata、provenance、versioning、資料 API、資料保存與互補呈現 | 支撐本產品不把 TextProjection 當作唯一真實來源，並要求保留原始資料與版本 |
| **JSON Schema Specification**（官方規格） | 描述 JSON 欄位型別、必要欄位與驗證條件 | 支撐每個 Source Schema 要保存版本化的欄位規則；它不是 KG 語意本體 |

**對本專案的設計結論**：上述標準共同支持「先保留來源結構，再建立語意映射」的大方向，但沒有任何一項標準直接給出本產品的完整多型態資料匯入演算法。因此第三章 3.1.5 的 `Source Adapter`、`Schema Profiler`、`Schema Registry`、`Mapping Plan`、`Canonical Record` 與 `TextProjection` 是本論文的產品架構設計，不應寫成直接複製某個標準或開源專案。

**雙軌表示的理由**：`Canonical Record`／KG 保留可查詢的結構與來源，`TextProjection` 只把同一筆資料轉成 LLM／文字檢索可使用的表示；兩者都要帶有 `source_record_id`、schema path 與 mapping version。這使系統可以利用自然語言模型的語意能力，又能在回答、驗證或人工治理時回到原始結構。這個雙軌設計是本專案的整合方案，不是 JSON-LD、R2RML 或 PROV-O 的直接實作。

**目前狀態**：本節完成的是產品架構與方法依據整理；目前程式尚未完成 JSON／SQL／API Source Adapter、Schema Registry 或結構化資料的端到端匯入，第四章不得宣稱這些功能已實作。正式實作後，需在第五章評估 schema mapping 成功率、人工修正成本、型別保留率、來源可追溯率與建圖品質。
