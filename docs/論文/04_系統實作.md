第三章 §3.1.5 是完整產品架構的設計預留，不是目前系統已具備的功能。本版本沒有可宣稱的 JSON／JSON API、SQL／資料庫、CSV／XML 或既有 KG／RDF `SourceAdapter`，也沒有 `RawSnapshot`、`SourceSchema`、`CanonicalRecord`、`MappingPlan` 或 `SchemaRegistry` 的正式持久化與 API。現行第四章主要記錄文件／文字輸入、解析切塊、SVO 抽取、圖譜寫入與問答流程；結構化來源若要導入，仍需依 `ARCHITECTURE.md` 的 SDD 任務完成 adapter、schema mapping、驗證、版本與追溯設計後，才能另立實作章節或產品版本說明。

## 4.1 實作範圍與開發環境

本研究以 Python 後端建立 World Knowledge Graph RAG 原型，採 FastAPI 提供 HTTP API 與 Server-Sent Events（SSE）串流問答介面，Neo4j 儲存知識圖譜，SQLite 儲存抽取任務佇列與關係型別治理的本地狀態。前端使用不依賴框架的 Vanilla JavaScript，負責知識圖譜側欄、文件暫存區與聊天串流的基本操作。

目前主要技術元件如下：

| 層次 | 實作元件 | 主要責任 |
|---|---|---|
| API | FastAPI、Pydantic | 請求驗證、文件與知識圖譜端點、SSE 問答 |
| 圖資料層 | Neo4j AsyncDriver | KG、Entity、Chunk、Fact、關係邊與向量索引 |
| 本地狀態層 | SQLite | `task_queue.db` 抽取佇列、`expand_pool`／`expand_registry`／提案狀態 |
| 解析層 | `parser/` | 文件、網頁與多媒體輸入轉為純文字，再進行句子感知切塊 |
| 向量層 | `EmbeddingProvider` | 本地 `sentence-transformers`、OpenAI 或 Ollama embedding provider |
| 生成層 | `LLMProvider` | Ollama、OpenAI、Anthropic、Gemini、Grok provider 工廠 |
| 前端 | HTML、CSS、Vanilla JS | 暫存區、KG 管理與問答串流 UI |

啟動時由 `main.py::lifespan()` 建立 Neo4j 非同步連線、初始化 provider、檢查 embedding provider/model/dimension 是否與既有 `_EmbeddingMeta` 記錄一致，並啟動抽取與治理兩個背景 Worker。embedding 設定若不一致，系統會停止啟動，避免不同向量空間被靜默混用。

## 4.2 資料模型與儲存設計

### 4.2.1 API 資料模型

`models/knowledge_graph.py` 與 `models/document.py` 使用 Pydantic 定義 API 邊界。知識圖譜模型包含 KG 識別碼、名稱、描述、資料夾位置、Neo4j 資料庫名稱與統計欄位；文件模型包含標題、內容、檔案型別與所屬 KG。`ChatRequest` 則限制問題長度、候選數、SVO BFS 跳數與對話歷史長度，讓查詢成本有明確上限。

抽取結果以 `SVOTriple` 表示，保存 `subject`、`rel_type`、原始 `verb`、`object`、主客體型別、信心分數，以及文件、SVO chunk 與句子範圍等來源欄位。這些來源欄位不是附加的除錯資訊，而是後續 `HAS_ENTITY`、`SUPPORTED_BY` 與 AIS 可追溯性評估所需的資料基礎。

### 4.2.2 Neo4j 圖資料模型

目前建圖流程使用以下核心節點與關係：

```text
(_KnowledgeGraph)
     │ kg_id
     ├── (Entity {kg_id, name, entity_type, name_embedding, aliases})
     │        ▲
     │        └── (Chunk {kg_id, source_doc_id, source_svo_chunk_index})
     │             └─[:HAS_ENTITY {surface_form}]
     │
     └── (Entity)-[:<canonical_rel_type> {citations_json, confidence}]->(Entity)
              ▲
              └── (Fact {fact_text, subject, rel_type, object, fact_embedding})
                   └─[:SUPPORTED_BY]->(Chunk)          ── 一般文件（source_article_no 為 None）
                   └─[:SUPPORTED_BY]->(LawArticle)      ── 法規領域來源（見下方節點層，2026-08-24）
```

三元組關係邊以 `(kg_id, subject, rel_type, object)` 作為事實層級的合併鍵，同一事實若由不同 chunk 或文件重複抽取，不會建立多條相同邊，而是累積 `citations_json`。另一方面，`Fact` 節點以單筆 citation 為粒度保存可向量檢索的事實文字，因此「圖結構去重」與「細粒度語意檢索」是兩個平行層次，前者不會被後者取代。

**`Document`／`LawArticle` 節點（2026-08-24 新增，對應 § 3.5「文件／法條層級的時序錨定」）**：`models/law_document.py`／`repositories/law_document_repo.py` 實作獨立於上圖的節點層，保存法規記錄原本會被匯入時丟棄的 JSON 結構化中繼資料：

```text
(Document {kg_id, source_doc_id, source, title, record_type,
           content_hash, update_date, effective_date, effective_note, source_url})
     ▲
     └── (LawArticle {kg_id, source_doc_id, article_no, article_content, chapter_title})
              -[:PART_OF]->(Document)
```

`LawDocumentRepository.merge_document()`／`merge_law_articles()` 皆以 `MERGE` 實作、冪等；`Document` 節點不存在時 `merge_law_articles()` 整批不建立，不留孤兒 `LawArticle`。✅ **`Fact.SUPPORTED_BY` 已改指向 `LawArticle`（2026-08-24）**：法規領域來源（`SVOTriple.source_article_no` 有值）的 Fact 節點，`SUPPORTED_BY` 連向 `LawArticle` 而非 `Chunk`；一般文件（`source_article_no` 為 `None`）行為完全不變。與既有 `Entity`／`Chunk`／`Fact` 圖至此已打通：`Fact -[:SUPPORTED_BY]-> LawArticle -[:PART_OF]-> Document` 可取得 `effective_date` 等中繼資料（`bfs_query()`／`vector_search_facts()` 尚未接線讀取此路徑，僅圖結構本身已連通）。真實 LLM 端到端驗證：12 個真實 Fact 節點全數正確連向對應 `LawArticle`，見 03 §3.5。匯入腳本 `import_leave_scheduling_dataset.py` 為此節點層的唯一目前呼叫端。測試：`tests/repositories/test_law_document_repo.py`。

### 4.2.3 向量索引與一致性保護

目前向量維度預設為 384，對應 `paraphrase-multilingual-MiniLM-L12-v2`。系統建立 ConceptNode、Entity、SVO Chunk、Fact 與關係型別描述句的向量索引；provider 工廠提供一致的抽象介面，使分類、分群、Fact 檢索與關係型別比對可以共用同一套 provider 生命週期。

`core/embedding_guard.py` 在啟動時記錄並比對 provider、model 與 dimension。若三者任一不一致，會拋出 `EmbeddingProviderMismatchError`。這項保護不是研究 RQ 本身，但它是所有 cosine 比對有效的必要前提：不同模型產生的向量不能直接放在同一索引中比較。

## 4.3 文件解析、切塊與暫存區分類

### 4.3.1 解析與資料夾化

`services/ingestion_service.py` 將 `DocumentParser`／`URLParser` 的輸出統一轉為純文字，再呼叫 `sentence_aware_chunking()`。每份來源文件會在暫存區建立獨立資料夾，由 `parser/chunk_writer.py` 寫入 chunk、原始文字與句子索引；同時以 `DocumentRecord` 保存來源、歸屬歷程、抽取狀態、chunk 進度與向量快取。

這種設計把「原始文件位置」與「背景處理狀態」分開：資料夾內的記錄檔是可隨文件搬移的狀態來源，`task_queue.db` 則是供 Worker 快速輪詢的效能索引。重新歸屬文件時，系統追加 assignment history，並將抽取進度重設為新的 pending 狀態，不沿用原 KG 的抽取結果。

### 4.3.2 向量分類與 AI 自動分群

`services/classify_service.py` 先對文件 chunk 向量取平均，得到文件代表向量；再對每個 KG 的成員文件代表向量取平均，形成 KG prototype，最後以 cosine similarity 計算文件與各 KG 的分類分數。prototype 與文件向量都具有快取，避免每次分類重複呼叫 embedding provider。

分類結果依分數分為自動歸檔、建議人工確認與留在暫存池三種處理路徑。現行 `CLASSIFY_AUTO_THRESHOLD` 與 `CLASSIFY_MIN_THRESHOLD` 仍是待第五章校準的工程佔位值，不能在結果章中當作已驗證參數。

當暫存池累積足夠文件時，`services/cluster_service.py` 使用 embedding、必要時的 UMAP 降維與 HDBSCAN 分群，並以主導子群篩選命名依據，再呼叫 LLM 產生候選 KG 名稱與描述。使用者仍需確認名稱與文件清單後才建立新 KG；因此 AI 分群是候選產生器，不是無人監督的最終歸檔器。

## 4.4 SVO 前處理與受控關係抽取

### 4.4.1 文件內前處理

`services/svo_preprocessing_service.py::prepare_svo_ready_chunks()` 串接以下步驟：讀取或重建句子索引、可選的實體登記表處理、代名詞雙軌偵測與 LLM 消解、逐句 embedding，以及 SVO 專用切塊與寫入。

**法規領域專屬切塊（2026-08-24 接線，對應 § 3.1.2）**：`prepare_svo_ready_chunks()` 與 `services/svo_service.py::trigger_extraction()` 皆新增 `articles` 選填參數；提供時改走 `services/svo_chunking.py::ArticleAwareChunking`（依 `payload.articles` 的 `ArticleNo` 邊界切，一條對一塊），略過上述句子清單重建／別名登記／代名詞消解／embedding 這幾個步驟。`None`（預設）維持原有 `SVOGROUP` 行為不變，只新增一條路徑。誠實侷限：此路徑目前不套用代名詞消解。

目前 `pronoun_resolution_service.py` 已提供正則與 POS 標記雙軌偵測、雙向上下文視窗與可選 LLM 消解；`entity_registry_service.py` 已提供文件內別名登記、長度優先暫定標準名與快照讀寫。這些機制已有單元測試，但正式 `trigger_extraction()` 目前仍以 `mentions=None` 呼叫，NER 上游尚未完整接入，因此文件內具名提及登記在正式流程中的生效範圍有限。此處是 RQ4b 的實作限制，不應寫成已完成的端到端實驗結果。

### 4.4.2 SVO 抽取與關係型別正規化

`services/svo_service.py::extract_svo_triples()` 將 LLM 回傳的 JSON 三元組解析為 `SVOTriple`，並對主客體型別與關係型別做正規化。受控關係型別集合由 `core/constants.py::SVO_REL_TYPES` 定義；原始動詞 `verb` 仍保留，作為來源語句與後續治理的自然語言證據。

當 LLM 回傳的關係型別不在受控集合時，系統先以 embedding 比對型別描述句，再依 `SIM`／`COMPARE`／`ESCALATE3` 流程決定沿用既有型別、交由 LLM 仲裁，或先以 `RELATED_TO` 收納。未經核准的候選動詞可進入 `expand_pool`，由治理 Worker 分群、LLM 判斷、登記表比對與人工審核逐步決定是否新增 canonical type。這套 `EXPAND` 機制已具有程式碼與測試，但門檻與治理資料量仍待第五章校準。

RQ4a 的研究設計仍是「受控關係抽取相對開放式抽取」的待驗證比較；本節描述的是目前抽取管線的工程實作，並不等同於 RQ4a 已經獲得實證結論。

## 4.5 實體對齊、事實合併與 Fact 向量化

### 4.5.1 實體對齊與別名記錄

`resolve_entity_name()` 採三階段判斷：先以字串編輯比例快速比對，再以 Entity name embedding 進行 cosine 比對，最後只在灰色地帶呼叫 LLM 仲裁。判定為同一實體後，`merge_entity()` 以 Neo4j MERGE 合併節點，並將實際出現的文字以 `surface_form` 記錄在 `(Chunk)-[:HAS_ENTITY]->(Entity)` 邊上。

跨文件標準名不是由單一文件永久決定，而是由 `HAS_ENTITY` 邊依獨立文件數聚合別名頻率，再由 `should_promote_by_frequency()` 判斷是否更新 Entity.name。`Entity.aliases` 是方便讀取的快取；權威追溯資料仍在邊上的 `surface_form` 與來源 chunk。這使「合併同一實體」與「保留實際字面」可以同時成立。

目前 RQ4b 的機制已實作並有測試，然而正式流程仍受 NER 注入、文件識別碼與門檻校準等條件限制。因此第四章只能報告實作與測試覆蓋，不能把它表述為已完成 RQ4b 消融實驗。

### 4.5.2 事實層級去重

`merge_triples_to_graph()` 對每個 `SVOTriple` 先建立或合併主客體 Entity，再以 canonical relation type 建立關係邊。若同一 `(subject, rel_type, object)` 已存在，系統保留既有邊並合併 citation；`confidence` 依目前設計取引用中的最高值。這項去重避免相同事實因被不同 chunk 抽取而造成邊數膨脹，同時保留每個來源以支援回溯。

### 4.5.3 Fact 節點與回填

若抽取時具備文件識別碼與 SVO chunk 索引，系統會把三元組文字化為 `fact_text`，呼叫 embedding provider 建立 Fact 節點，再以 `SUPPORTED_BY` 連回來源 Chunk。舊資料或抽取時沒有 Fact 節點者，可由 `backfill_fact_nodes()` 依 citation 分頁掃描並冪等補建；已存在相同六欄鍵的 Fact 不會重複建立。

文件識別碼由 `document_record_service.document_uuid()` 依固定 namespace 決定性推導，讓同一來源在不同處理階段能得到一致 UUID，也讓 `embed_svo_chunks()` 與 `merge_entity()` 使用同一組 Chunk 識別鍵。這項修正消除了兩個互不相連的 Chunk 節點群，是 Fact 向量化與來源追溯能正常接線的前提。

## 4.6 任務佇列、斷點續傳與背景 Worker

`services/task_queue_service.py` 以 SQLite 保存每個 KG、來源與 chunk index 的任務狀態。`enqueue()` 以冪等方式登記待處理 chunk，`next_pending()` 依序取出工作，`update_status()` 維護 pending、processing、pending_upload、completed 與 failed 等狀態；啟動時由 `ensure_ready()` 執行可信度檢查、卡住任務重置或依文件記錄重建索引。

抽取 Worker `run_extraction_worker()` 在背景迴圈中依序執行：取得待處理 chunk、呼叫 LLM 抽取 SVO、合併進 Neo4j、更新佇列狀態與文件進度。單一 chunk 失敗會標記 failed 並記錄錯誤，不使整個 Worker 終止。

治理 Worker `run_governance_worker()` 以較寬鬆的週期巡視各 KG，執行新關係型別治理、相關向量邊回填與 Entity name embedding 回填。抽取 Worker 與治理 Worker 都由 `main.py::lifespan()` 以 `asyncio.create_task()` 啟動，關閉時取消任務。治理流程中的人工審核提案仍由 API 端點處理；`HUMANCHECK` 的重複提案狀態管理是目前已知限制。

## 4.7 查詢與問答實作現況

### 4.7.1 BFS 與 Fact 語意檢索

`bfs_query()` 從使用者指定 KG 內的 seed Entity 做 bounded BFS，回傳跳數限制內去重後的 SVO triples。Neo4j 關係邊上的 `citations_json` 可保存多個來源，但 `SVOTriple` 回傳物件目前取最後一筆作為代表來源；更細緻的來源排序仍屬後續設計。

`vector_search_facts()` 以問題向量查詢 Fact vector index，並限制在指定 KG 內。問答流程將 BFS 結果與 Fact 結果以 `(subject, rel_type, object)` 去重後組成 prompt，讓結構路徑與語意 Fact 檢索互補。

### 4.7.2 目前問答路徑與未完成元件

目前 `routers/agent.py::chat()` 是可執行的暫時路徑：使用者必須指定單一 `kg_id`；系統先以 Entity 名稱在問題中的字面出現情形找 seed，再做 BFS，接著執行查詢關係型別連結與 Fact 語意檢索，最後以 SSE 串流 LLM 回答並送出 `sources` 事件。

這條路徑尚未等同於第三章的正式雙層 GraphRAG。`services/concept_engine.py::route_kgs()` 仍未實作，因此 ConceptNode 跨 KG 路由（RQ2）尚未接入；`chat()` 也沒有信心評分、擴大 BFS 的自我精煉迴圈（RQ3）。因此目前程式可以驗證 BFS、Fact 檢索、查詢關係連結與來源事件的接線，但不能據此宣稱 RQ1–RQ3 已完成正式比較。

**事實接地性核對 v1（2026-08-24 新增，對應 § 3.6 設計提案，詳見 `docs/報告/16_事實接地性核對機制設計報告.md`）**：`chat()` 串流結束後，`services/verification_service.py::verify_fact_grounding()` 逐句核對回答是否被 `_merge_fact_lines()`（與生成時的 prompt context 一致）支持，額外送出 `event: grounding`。這是 RQ3 自我精煉迴圈的第一塊拼圖，但範圍刻意縮小：v1 只偵測、不觸發「擴大 BFS」或「限制性重新生成」等補救動作，因此**不構成 RQ3 自我精煉迴圈本身已實作**——`chat()` 仍不具備信心評分與重新生成迴圈，此處新增的只是一個獨立的、生成後的診斷訊號。真實 Neo4j／Ollama 測試證實此訊號能偵測到既有圖遍歷信心訊號抓不到的失效模式（證據已檢索到、生成階段仍捏造內容），見報告第 8 節。

## 4.8 API 與前端整合

FastAPI router 依責任拆分為文件、暫存區、知識圖譜、擴充治理、搜尋與 agent 問答端點。受保護端點透過 `X-API-Key` 驗證；前端以 SSE 接收 token 事件與最後的 `sources` 事件，將答案與來源資訊分開呈現。

目前前端主要完成介面骨架與既有端點串接，文件 CRUD 與部分搜尋／repository 功能仍有未完成 stub。故本章所稱「系統實作完成」是指前述已落地的建圖與問答子流程，不代表所有產品功能或正式部署功能均已完成。

## 4.9 實作限制與本章小結

目前已具備可由測試核對的核心實作包括：文件解析與句子感知切塊、暫存區分類與分群、SVO 前處理與抽取、受控關係型別治理、實體合併與別名來源記錄、事實層級去重、Fact 向量化與回填、任務佇列、抽取／治理 Worker，以及單一 KG 範圍內的 BFS＋Fact 問答接線。

尚未完成、因此不能在本章當作實驗系統既成能力的元件包括：ConceptNode 正式跨 KG 路由（RQ2）、自我精煉檢索迴圈（RQ3）、以 RQ4a／RQ4b 為正式貢獻的完整端到端比較、事實時序保留與查詢過濾（RQ5），以及向量引導圖剪枝（RQ6）。第五章應依此邊界安排實驗組別；第六、七章則只能對實際跑出的組別做結果與貢獻宣稱。
