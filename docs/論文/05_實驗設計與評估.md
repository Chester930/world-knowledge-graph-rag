## 5.3 前置參數校準實驗：Chunk Size 敏感度

> 狀態：🟡 草稿（2026-07-17 新增）。此實驗**不對應任何正式 RQ**——chunk size 是工程超參數，不是研究問題本身——但它是 5.2 節所有消融組別共用的前提：3.1.1 `CMP` 分類分數、3.1.1 §a HDBSCAN 分群、3.2 §a 路由層向量粗篩、以及最終 RAG 問答品質，全部建立在「文字先被切成 chunk」這個步驟之上。目前的切塊參數（`parser/core.py` `sentence_aware_chunking(chunk_size=500, chunk_overlap=50)`）是沿用 v1 的經驗值，從未做過系統性驗證——若直接拿這個未驗證的參數去跑 RQ1-RQ6 的正式消融實驗，任何負面結果都無法排除「是不是切塊切壞了」這個混淆變因。因此本實驗**必須排在 5.2 節正式消融之前執行**，其結論（鎖定的 chunk size 數值）是後續所有實驗的固定前提，不是與 RQ1-RQ6 平行的另一組消融。

### 5.3.1 文獻依據與一個必須誠實處理的落差

- **Chen et al.（2023/2024，EMNLP 2024）Dense X Retrieval**：細粒度檢索單位（proposition 級）在檢索準確率與下游問答表現上系統性優於粗粒度段落，支持「切更細」的方向。
- **Bhat et al.（2025）**：切塊大小的最佳值**因任務類型而異**——事實型問答適合小塊（64-128 tokens），需要廣泛脈絡理解的任務適合大塊（512-1024 tokens）；且不同 embedding 模型對切塊粒度的敏感度不同。

> ⚠️ **單位落差，不可直接套用**：上述兩篇文獻回報的切塊大小皆以英文 **token**（子詞切分）為單位，但 `sentence_aware_chunking()` 目前的 `chunk_size` 參數計的是 Python **字元數**（`len(part)`），而本專案語料以中文為主。中文字元與子詞 token 的對應比例並非 1:1（且因分詞器而異），直接把「64-128 tokens」代入當作「64-128 個中文字元」是錯誤的單位轉換，會讓實驗設計本身站不住腳。本實驗的變因因此設計為**字元數的掃描區間**，並在每組設定實際跑一次 `LocalEmbeddingProvider` 底層 `sentence-transformers` 分詞器，回報測得的真實 token 數，讓「字元數 ↔ token 數」的對應關係是**實測值，而非假設值**，寫作時才能誠實地與文獻的 token 區間做對照，而不是含糊帶過單位問題。

### 5.3.2 實驗設計

**自變因**：`chunk_size`（字元數），掃描以下 5 組設定（涵蓋現行預設與文獻建議方向的粗略對應區間，兩端皆比現行預設更細/更粗）：

| 組別 | `chunk_size`（字元） | `chunk_overlap`（字元） | 備註 |
|---|---|---|---|
| S1 | 150 | 50（固定） | 對應文獻「小塊、事實型任務」方向 |
| S2 | 300 | 50（固定） | |
| S3（現行預設） | 500 | 50（固定） | v1 經驗值，作為對照基準 |
| S4 | 800 | 50（固定） | |
| S5 | 1200 | 50（固定） | 對應文獻「大塊、脈絡理解任務」方向 |

**控制變因**（單一變因原則，比照 3.6 節）：
- `chunk_overlap` 固定為現行預設值 50 字元，不在本次消融範圍內——若五組主結果顯示 chunk size 有顯著影響，overlap 的獨立消融可列為後續延伸，避免本次實驗變成二維網格搜尋、稀釋每組樣本的統計檢定力。
  - ⚠️ **名目 overlap ≠ 實際 overlap（2026-09-11 補上，Pass 2 L1 審視發現）**：`parser/core.py::sentence_aware_chunking()` 以句子為單位聚合、以字元數為界，`chunk_overlap=50` 是「回退幾個句子讓重疊字元數 ≥ 50」的目標值——當單一句子長度就超過 `chunk_size - 50` 時（中文長條文常見），回退機制無句子可退，**該切點的實際重疊靜默歸零**。因此 S1（`chunk_size=150`）這種小塊設定，實際 overlap 會系統性低於名目 50、且各組不一致，構成本掃描未受控的混淆變因。跑 S1–S5 之前需先量測各組的實際平均重疊字元數（`run_chunk_size_sweep.py` 已回報每組 chunk 數與字元分布，可一併輸出實測 overlap），若各組實際 overlap 差異顯著，需在結論中誠實標註「overlap 非嚴格固定」，或先修 `sentence_aware_chunking()` 讓名目與實際一致再跑。
- **Embedding provider／model 全程固定**為系統預設（`local`，`core/embedding_guard.py` 已在啟動時強制單一 provider，見第三章 3.1 節），不在本次實驗內切換 provider——Bhat et al.（2025）指出不同模型對切塊粒度的敏感度不同，這代表「chunk size × embedding model」存在交互作用，但窮舉多個 provider 會使實驗矩陣倍增，超出本論文核心 RQ（RQ1-RQ3）的工作量負擔；此交互作用效應**明確列為未探索的範圍限制**，記入第七章未來工作，不可略過不提。
- 其餘系統元件（雙層路由、受控關係抽取、自我精煉迴圈）維持 Full System 預設設定不變，只有輸入語料的切塊方式隨組別改變。

### 5.3.4 產出與後續依賴

本實驗的結論（勝出的 `chunk_size` 數值，附上該設定下實測的平均 token 數，明確標註與文獻區間的對應關係）將**鎖定寫入 `core/constants.py`**，作為 5.2 節 Baseline 與消融組別、以及後續 RQ1-RQ6 所有正式實驗的固定前提，不再視為待驗證變因。

> **harness（2026-09-10，SDD-52 更新）**：`run_chunk_size_sweep.py` 對每個候選 `chunk_size` 跑一次 `parser.core.sentence_aware_chunking()` 切 KG#4 語料，回報 chunk 數、字元長度分布，以及以目前 `settings.local_embedding_model`（預設 `BAAI/bge-m3`）分詞器實測的 token 數與 tok/char 比——**字元/token 校準這段離線即可跑**（不需 Neo4j／Ollama／drain）。BGE-M3 輸出 1,024 維；若切換 provider/model，需清理舊 `.npy` 與 prototype 快取並重新建立索引。§5.3.3 的三個下游評估（CMP 分類準確率、HDBSCAN 輪廓係數、RAG P@K/R@K/F1）尚未接線，`--eval` 旗標會列出前置條件（帶標籤驗證集、P0a-2 事實級標註、對 KG#4 各 size 建索引），全部卡 DRAIN-DONE。

**最低限度承諾**：若時間不足以跑滿五組完整掃描，至少需執行「S3 現行預設 vs. 依文獻方向調整的至少一個候選值（例如 S1 或 S5）」的最小對照，並在論文中誠實聲明「其餘候選值因時間限制未窮舉」——比照 3.6／1.4 節的誠實揭露慣例，不可略過此步驟就直接宣稱「chunk size 已依文獻最佳化」。

### 5.3.5 分類門檻校準（`CLASSIFY_AUTO_THRESHOLD`／`CLASSIFY_MIN_THRESHOLD`）

> 與 5.3.1-5.3.4 的關係：chunk size 決定「CMP 分數本身算得準不準」，本節校準的是「同一個 CMP 分數，切在哪個數值算自動歸檔、哪個算完全無關」的**決策門檻**——概念上是獨立的問題，但依賴同一份驗證集與 5.3.1-5.3.4 已鎖定的 chunk size，故排在 5.3 節之內、5.4 節正式資料集建置之前，作為前置校準實驗的第二部分，不另立新章節。

**現況問題**：`core/constants.py` 目前的 `CLASSIFY_AUTO_THRESHOLD = 0.30` 與 `CLASSIFY_MIN_THRESHOLD = 0.05` 是針對 v1 舊公式（`cosine × alignment × magnitude`）校準的遺留值。第三章已將分類分數公式改為 Prototypical Networks 的 centroid cosine 相似度（拿掉了經查證恆為常數、無實際作用的 alignment/magnitude 加權，見第三章 3.1.1 節），數值尺度不保證與舊公式相同——這兩個數字目前純粹是沿用舊值的佔位符，**不是通過任何驗證的結果**（程式碼中已加上對應警告註解，見 `core/constants.py`）。

**為什麼文獻無法回答這個問題**：本論文引用的 Prototypical Networks（Snell et al., 2017）與 Sentence-BERT（Reimers & Gurevych, 2019）驗證的是「用 cosine 相似度衡量語意距離」這個**計算方式**本身有效，但沒有任何文獻能告訴你「你的語料、你選定的 embedding 模型算出來的分數，切在 0.3 還是 0.4 才是對的」——**這是一個資料集依賴的數值，只能靠實際跑一次帶標籤的驗證資料才能定案，查文獻查不到答案**。這點必須在論文中誠實聲明，不能用「有文獻佐證分類機制」模糊帶過「門檻數值本身未經驗證」這件事——機制有效不代表你設的切點有效，這是兩個不同層次的問題。

**實驗設計**：
1. 沿用 5.3.3 節「分類準確率」所需的同一份驗證集（一批已知正確歸屬 KG 的文件），並擴充至少一批**刻意不屬於任何現有 KG 的負樣本**，用來檢驗 `CLASSIFY_MIN_THRESHOLD` 能否正確排除無關文件。
2. 固定 5.3.1-5.3.4 節已鎖定的 chunk size 與系統預設 embedding provider，只掃描門檻值本身：對每份驗證文件計算其與各 KG 的 CMP 分數，畫出分數分佈（正確歸屬 vs. 錯誤歸屬 vs. 完全無關三組），觀察三組分數是否有清楚可分的區間。
3. 以類似 PR 曲線的方式，掃描候選 `CLASSIFY_AUTO_THRESHOLD` 值（例如 0.10 至 0.60，間隔 0.05），計算對應的自動分類 precision（自動歸檔的文件裡真正歸對的比例）與 recall（本應自動分類、卻因門檻太高被誤放進 SUGGEST/POOL 的比例），取兩者平衡點作為正式值；`CLASSIFY_MIN_THRESHOLD` 則以「無關負樣本分數的上界」為依據校準，確保明顯無關的文件不會被誤判進 SUGGEST 清單。

**既有設計已吸收部分門檻誤差風險，這是不採用自適應機制的額外理由**：第三章 3.1.1 節的三層信心分級（AUTO／SUGGEST／POOL）本身就是針對「門檻不可能完全準確」這個事實的緩解機制——分數落在兩個門檻之間的文件不會被錯誤地自動歸檔，而是進入 SUGGEST 清單交由使用者確認再拍板。這代表門檻校準**不需要追求完美的單一切點**，只需要讓 AUTO 區間的 precision 夠高（避免誤自動歸檔）、MIN 區間夠保守（避免真正相關的文件被過早放棄留在暫存區），中間的灰色地帶本來就設計成由人工把關。也因此，門檻校準採「一次性驗證＋鎖定數值」而非「線上自適應調整」是合理選擇——現有設計已有一層人工審核吸收門檻誤差的代價，疊加一層機器學習機制去動態調整門檻，只會讓「這個門檻為什麼是這個數字」變得更難向讀者交代，卻換不回相應的必要性（同樣的理由已在 `core/providers/embedding/README.md` 討論過模型一致性與 chunk size 時說明過，此處是同一原則的第二次應用）。

**產出**：校準後的兩個門檻值連同其 precision/recall 曲線數據，一併鎖入 `core/constants.py`（取代現有帶警告註解的佔位值）與第五章實驗結果附錄，作為後續 RQ1-RQ6 消融實驗中涉及 3.1.1 分類正確性部分的固定前提。`KG_ROUTE_THRESHOLD`（3.2 §a 路由層門檻，對應 RQ2）是同一類型的舊公式遺留值，但因其直接對應正式 RQ2，校準實驗歸入 5.2 節 RQ2 消融組別內處理，不併入本節。

### 5.3.6 門檻常數敏感度與設定分層重構的行為保持驗證（對應第三章 3.8／3.9）

> 狀態：🟡 待第三章 3.9「設定分層與領域可插拔化」落地後執行；本節先固定方法。與 5.3.5 的關係：5.3.5 校準的是分類層兩個門檻，本節處理的是散落於查詢端與去重端的其餘約二十個未校準常數（`_SEED_MAX_DEGREE`、`_BFS_PER_SEED_LIMIT`、`_BFS_EXPAND_WHEN_BELOW`、`_BFS_PRIZE_TOP_K`、`_FACT_LINE_TRUNCATE_K`、`ENTITY_DEDUP_*_THRESHOLD`、`COMPARE_COSINE_THRESHOLD` 等），以及重構本身的行為保持。

**敏感度測試方法（呼應 3.8「門檻常數敏感度測試方法」）**：依 Czitrom（1999，*The American Statistician* 53(2)，見 2.6.8），「一次只動一個因子」（OFAT）只能估主效應、估不到因子交互作用，交互作用顯著時導向假的最佳點。因此分兩段：

1. **OFAT 篩選**：每次固定其餘常數、只在合理範圍內掃描一個（如 `_SEED_MAX_DEGREE ∈ {100, 200, 400}`、`_BFS_PER_SEED_LIMIT ∈ {30, 60, 100}`、`_BFS_EXPAND_WHEN_BELOW ∈ {5, 8, 12}`），對每個組態量測延遲、BFS 三元組數與答案正確性（沿用報告25/26 題組），找出對指標有實質影響的軸。此步的腳本形式見 `docs/報告/33` 引用的 `run_theta_sweep.py`。
2. **析因驗證**：對 OFAT 篩出有影響的軸，跑小型完整或部分析因設計，檢查交互作用；最終校準值以析因結果為準，不以 OFAT 結果為準。
3. **迴歸約束**：任一常數的調整不得使其他管線階段的指標退步（3.8「單一變因控制」原則在設定調整上的延伸）。

**設定分層重構的行為保持驗證（對應 3.9 / 第四章 4.10 的驗收標準）**——四項中三項已於 `tests/core/test_kg_config.py`／`tests/routers/test_agent.py` 交付（2026-09-08），列入 CI：
- ✅ **golden test**：不提供任何設定來源時，`KGConfig` 逐欄位等於重構前 `core/constants.py`／`routers/agent.py`／`services/svo_service.py` 的模組常數值（含 `domain.system_context` 逐字等於 `_TAIWAN_CONTEXT_INSTRUCTION`）——遷移每一環都必須通過，機械化證明「行為零變化」。

### 5.4.1 RQ1 的強基準前提（B1），與「勝過 pure-LLM ≠ RQ1 成立」的界線

第二章 2.3 已論證：2025-2026 年的比較文獻（Han et al. 2025、Xiang et al. 2025、Fan et al. 2026）核心發現是**GraphRAG 在許多真實任務上並不優於、甚至輸給經過調校的一般 RAG**，優勢具任務依賴性。因此 RQ1（KG-BFS 相較當代 RAG 的優勢邊界）的成立與否，取決於是否對照到一個**合理調校的向量 RAG 基準（B1）**，而非只對照 pure-LLM。

**現況落差（誠實聲明）**：報告 18、25、26 的所有真實問答測試，KG 系統的對照組都是 **pure-LLM（不檢索）**——報告 18 已附帶觀察到「RAG-MVP 意外地強」、報告 25 觀察到「pure-LLM 在 8 題中 5 題給出有信心的錯誤數字」。這些結果只能支撐「KG 系統勝過不檢索的 LLM」，**不能**支撐「KG 系統勝過當代 RAG」。

**因此**：

1. **B1 最小可行版是 RQ1 的硬前提**，非「時間允許才做」。
2. **在 B1 跑出結果之前**，第六、七章對 RQ1 的任何「優勢」陳述都必須明確限定為「相較 pure-LLM」，並標註「尚未對照當代 RAG」——不得以「勝過 pure-LLM」的既有測試結果冒充 RQ1 已成立。
3. B1 與 B2 若因時間限制只能擇一，優先 B1；並於第七章限制章明列未對照 B2 的範圍缺口。

#### B0 / B1 定義（完整設計見 `docs/報告/35_B1當代文字RAG強基準設計.md`）

B1 的結構直接對標兩篇 GraphRAG 比較論文的 plain-RAG baseline：**Han et al. (2025)**《RAG vs. GraphRAG》§3.4（dense retrieval、chunk ≈256 token、top-k=10、選配 cross-encoder reranker `bge-reranker-large`、**明確不做 query rewriting/decomposition**）與 **Zhou et al. (2025)**《Unified Framework》§7.1（「VanillaRAG」＋「ZeroShot」、BGE-M3 embedding、1,200-token chunk、top-k=4）。⚠️ 兩篇 chunk 單位為英文 token、本專案計中文字元，只借結構不借數值。方法定位另見 **Gao et al. (2023)** RAG Survey 的 Naive／Advanced／Modular 分類——**B1 ＝ Naive RAG ＋ 檢索後重排 ≈ Advanced RAG 去掉 query 轉換**（query 轉換屬 B2）。

```
B0（floor）：raw doc → 500 字元 chunk (sentence_aware_chunking) → Chunk 級 dense KNN
             (chunk_embedding_vector) → top-k → 【與 KG 路徑完全相同的生成 + grounding stack】
B1（strong）：B0 + ① 混合檢索 (dense + BM25，RRF 融合)  ② 選配 cross-encoder rerank
                  (bge-reranker-v2-m3，預設關，由校準決定)  ③ chunk_size 取 §5.3 勝出值  ④ top-k 校準
```

| 元件 | B0 | B1 | 依據 |
|---|---|---|---|
| 索引單位 | `Chunk`（現行 500 字元） | 同，chunk_size 取 §5.3 勝出值 | Bhat 2025／Chen 2023（見 §2.6.2） |
| 一階檢索 | dense KNN（與 KG 路徑同一 embedding model） | dense + BM25 混合，RRF 融合 | Karpukhin 2020（DPR，dense＋BM25 hybrid）、Cormack 2009（RRF） |
| 二階重排 | 無 | 選配 `bge-reranker-v2-m3` cross-encoder；預設關 | Nogueira & Cho 2019、Han 2025 |
| top-k | 固定（暫 5） | 校準 ∈ {3, 5, 10} | Han(10)／Zhou(4) |
| query 處理 | 原樣 | 原樣（不改寫、不分解＝B2） | Han 2025 |
| 生成端 | **與 KG 路徑逐位元相同**：同 `llm_provider`、同 `cfg.domain.system_context`、`_arrange_fact_lines` 的 retrieval-agnostic 部分、grounding 核對＋方案 B/2b 重生 | 同 B0 | §3.8 單一變因控制 |

**核心原則**：B0／B1／Full System **只差檢索前端**，生成端完全相同——否則 RQ1 分不清「贏在圖檢索」還是「贏在生成端機制」。

**與報告 08 三軌命名的對映（報告 35 §3 訂正）**：報告 08「軌道 1（粗 chunk／無 coref／dense）」＝ **B0**；「軌道 1 ＋ rerank ＋ 校準」＝ **B1**；「軌道 2（句子級＋指代消解）」＝專案自身貢獻（≈「−前處理」消融，RQ4b 相關），**不是中性 baseline**，B1 明確排除 coref。

**明確排除**：B1 不做指代消解／標準化句子（軌道 2＝專案貢獻）、不做受控關係詞彙（RQ4a）、不做 query 改寫或多輪檢索（B2）。若 §5.3 後的校準顯示 cross-encoder reranker 邊際效益低，B1 退回「dense + BM25 RRF」無新模型依賴版，並在論文說明。

**校準計畫**：§5.3 chunk-size 定案後，鎖定該值、以 OFAT（§3.8 方法）掃 `top_k ∈ {3,5,10}` × `reranker ∈ {off, bge-reranker-v2-m3}` × `hybrid ∈ {dense-only, dense+BM25 RRF}`，對 §5.4 題組量 §5.5 的 Precision@k／Recall@k ＋ 答案 F1，挑一組進 RQ1 正式對照；定版組態鎖進 §3.8 的可追溯性 manifest。

**現況資產與實作進度（2026-09-10 更新）**：`standardized_rag.py` 系列（報告 18 條件 C 的 MVP）僅為風格參考——其索引來自指代消解前的**句子級**向量，非乾淨 chunk 級 baseline。⚠️ **`Chunk` 節點的 `chunk_embedding_vector` 索引不能重用**：查證 `embed_svo_chunks()` 後確認它 embed 的是標準化 SVO chunk 文字（`"\n".join(normalized_slice)`），即軌道 2＝專案貢獻，納入會使 baseline 不中性（見報告 35 §8 訂正）。**檢索側已改為自建**（P0b 第 1 項，✅）：`build_baseline_chunk_index.py`（原文 → `sentence_aware_chunking(chunk_size)` → embedding → `.npy`，chunk_size 帶進檔名供 §5.3 掃描）＋ `services/baseline_rag_service.py::search_baseline()`（dense brute-force ＋ 選配 BM25 RRF ＋ 選配 CrossEncoder；`B0=hybrid off`、`B1=hybrid on`）＋ `build_context_lines()`；依賴 `rank-bm25`（dev），12 項單元測試、全套 775 passed。**生成側共用函式重構**（P0b 第 2 項）建議等 DRAIN-DONE／T2 後再做（T2 在 `chat()` 上跑、baseline 為特定 commit）。B1 檢索側不卡 DRAIN-DONE；跑 RQ1 對照卡 DRAIN-DONE（完整 KG#4）＋卡 §5.3。

#### B2（Agentic RAG 強基準，optional；完整設計見 `docs/報告/36_B2AgenticRAG強基準設計.md`）

B2＝在 B1 檢索前端之上包一層 **single-agent、prompt-based 的 agentic 多輪迴圈**，作為 RQ1 的上限對照組。直接動機＝ **Fan et al. (2026)**《Do We Still Need GraphRAG?》：其 RAGSearch benchmark 發現 agentic search over dense RAG 透過多輪檢索＋推理誘導出**隱式證據結構**、大幅縮小與 GraphRAG 的差距，但 GraphRAG 在複雜多跳仍佔優、離線成本攤提後更穩定。Fan 標準化 LLM backbone（含 Qwen2.5-7B，與本專案一致）＋檢索預算（≤ 5 turns、top-5）＋推理協定，並報告 accuracy 以外的離線成本／線上效率／穩定性——B2 直接照搬此評估框架。

```
B2 = Adaptive 路由（複雜度分類：規則式簡化版或小 LM，Jeong et al. 2024）
     ├─ 簡單題 → B1 單次（不進 agent 迴圈，成本對照才公平）
     └─ 複雜題 → single-agent ReAct/IRCoT 式迴圈，跑在 B1 檢索前端上：
          分解（Self-Ask 式，重用 _split_into_subquestions）→ 逐步驟用 B1 檢索取證據
          → 反思「證據夠不夠/缺什麼」（Self-RAG critique）→ 不足則精煉查詢再檢索（FLARE 觸發）
          → 重複（≤ 5 輪，Fan 2026；總檢索預算上限）→ 綜合 → 【與 B0/B1/Full System 逐位元相同的 grounding + 方案 B/2b 重生 stack】
     界限：max_rounds=5、每輪 top-k=5、generator 固定 qwen2.5:7b、無工具（只有檢索）
```

方法譜系：**ReAct**（Yao et al. 2023，🟢 ICLR 2023，📥 已下載）＝迴圈骨架（thought→action→observation）；**IRCoT**（Trivedi et al. 2022，§2.4.7；**Han et al. 2025 用它當迭代檢索 baseline**）＝檢索與 CoT 交錯做多跳；**Self-Ask**（Press et al. 2022，§2.4.7／報告 28）＝子問題分解；**FLARE**（§2.4.7）＝低信心觸發再檢索；**Self-RAG**（§2.4.7）＝證據充分性反思；**Adaptive-RAG**（Jeong et al. 2024，🟢 NAACL 2024，📥 已下載）＝複雜度路由，讓簡單題退回 B1；**Singh et al. 2025** Agentic RAG Survey（§2.3 索引）＝B2 定位為 single-agent + adaptive（不做 multi-agent）。

**單一變因**：B1 vs B2 的唯一變因＝有無 agentic 多輪迴圈；**B2 vs Full System** 的唯一變因＝agentic 多輪 chunk 檢索（隱式證據結構）vs 單次 KG-BFS（顯式圖結構）；generator／`cfg.domain`／grounding／方案 B/2b／題組／每題 ×3／§5.5 rubric 全固定。

**⚠️ Confounder 誠實聲明（呼應本章與 §3.6／§4.9）**：Full System 的 RQ3 自我精煉迴圈**尚未實作**（只有單次 grounded regeneration），因此 B2 的多輪檢索**比現行 Full System 更 agentic**。RQ1 的提問因此精確化為 Fan (2026) 的框架：「即使 Full System 沒有 agent 迴圈，顯式 KG-BFS 是否仍在可追溯性／成本／穩定性／複雜多跳上勝過完整 agentic chunk-RAG？」B2 的迴圈設計亦可回饋 §3.6 RQ3 尚未實作的「擴大 BFS 回補檢索 + 多輪迭代」分支（交叉連結，非混淆）。

**評估（擴 §5.5）**：除答案品質外，量 **① 離線建構成本**（KG 抽取 ~4 天／3303 chunk vs B2 ≈ 0）**② 線上效率**（每題 LLM 呼叫數、端到端延遲 p50/p95、context 長度）**③ 穩定性**（每題 ×3 run 的分數 mean/variance；KG-BFS 檢索為決定性、變異只來自生成端）**④ 可追溯性**（B2＝chunk 段落級、Full System＝Fact→LawArticle 條文級，質化）。

**明確排除**：無 RL 訓練／微調（Search-R1／Graph-R1〔GRPO〕是已知更強、未評估的 bar，論文聲明）；單 agent（非 multi-agent）；檢索-only agent（不加 web／計算器等工具）；B2 為 optional——時間不足時 RQ1 至少對照到 B1，第七章聲明未對照完整 Agentic RAG。

## 5.5 評估指標體系（2026-09-14 升級：新增原子事實驗證與三階段成本矩陣，原草稿保留於 5.5.4）

本研究捨棄單一答案相似度指標，建立兼顧「原子事實真實性」、「全生命週期成本」與「拓撲可追溯性」之多維度評估體系：

### 5.5.1 事實真實性與檢索指標（Atomic Verification）

| 指標名稱 | 定義與計量公式 | 對應評估目標與工具 |
|---|---|---|
| **原子事實正確率（Atomic Fact Accuracy）** | $\text{Acc}_{\text{atomic}} = \frac{\text{Supported Atomic Facts}}{\text{Total Stated Atomic Facts}}$ | 評估回答是否精確符合法條原文。由確定性接地腳本比對原始法規 `exact_span`，杜絕 LLM 寬鬆判定。 |
| **原子事實召回率（Atomic Fact Recall）** | $\text{Rec}_{\text{atomic}} = \frac{\text{Retrieved Gold Facts}}{\text{Total Gold Facts Required}}$ | 比對題庫標註之 `atomic_gold_facts` 必須命中之關鍵法規約束。 |
| **檢索精確率／召回率（Precision@K / Recall@K）** | 檢索取回之 Chunk 或 Fact 節點與 Ground-Truth 關聯節點之比值 | 評估檢索層之訊噪比，區分高噪聲 Chunk-RAG 與精確 Fact 拓撲。 |
| **全鏈路血統完整率（Lineage Integrity）** | 答案中之數值、條件、起算日是否皆能完整追溯至合法文件來源之比率 | 評估法規遵循之審計性。M4 提供 `Fact -> LawArticle -> LawFile` 條號級血統；M1/M2 僅能追溯至切塊段落。 |
| **幻覺／拒答判定一致性（Grounding / Deferral Consistency）** | 在 Type-E 惡意干擾或未包含法規下，系統之精確拒答率（Exact Refusal Rate） | 評估安全守衛與 Deferral 邊界能力。 |

| 指標類別 | 具體指標 | 說明 |
|---|---|---|
| **跨次運算變異度（Run-to-Run Variance）** | 同一問題連續執行 3 次之分數標準差 ($\sigma$) 與文本 Jaccard 相似度 | 評估系統確定性。KG-BFS 檢索路徑完全為決定性（Cypher 查詢），變異度極低；Agentic 迭代（如 B2）之多輪決策存在顯著隨機變異。 |

### 5.5.4 原始指標草稿（保留，與 5.5.1–5.5.3 互補）

5.5.1–5.5.3 是 2026-09-14 針對原子事實與三階段成本新增的精確化指標；以下是本章最初版本的指標草稿，涵蓋範圍略有重疊但用詞更寬鬆（如「答案品質」「幻覺率」用人工評分而非確定性比對），兩者互為對照，正式實驗時以 5.5.1–5.5.3 的確定性定義為準：

| 指標類別 | 具體指標 | 說明 |
|---|---|---|
| 答案品質 | Exact Match / F1（若有標準答案）、人工評分（正確性、完整性） | |
| 檢索品質 | Precision@K / Recall@K | 針對圖遍歷取回的事實與人工標註的「應該取回的事實」比對 |
| 幻覺率 | 人工標註「答案中無法從取回內容支持的陳述比例」 | 對應 RQ3，也可參考 Ragas 框架的 faithfulness 指標 |
| 線上效率 | 端到端延遲（p50/p95）、圖遍歷延遲、**每題 LLM 呼叫數、context 總長度** | 對應 RQ1（B1／B2／Full System 的成本對照，Fan et al. 2026 式）、RQ2、RQ3；若納入剪枝則另對應 RQ6 |
| 離線建構成本 | 索引/建圖的一次性時間與成本、每題攤提 | 對應 RQ1：KG 抽取（drain ~4 天／3303 chunk）vs B0/B1/B2 的 chunk embedding；Fan et al. 2026 Table 8 式對照 |

| 可解釋性／可追溯性（質化） | 案例分析：事實鏈是否可回溯到來源文件；B2＝chunk 段落級 vs Full System＝Fact→LawArticle 條文級 | 對應整體論文主張與 RQ1，質化補充量化指標 |

### 5.6.1 核對者模型敏感度與 specialist 前提驗證（對應 §3.8）

§3.8「方法論限制」段指出：本系統的生成端與其下游多個判斷關卡（接地核對、`is_claim` 分類、2b 定向修訂、關係型別 LLM 仲裁、`EXPAND` 治理仲裁）目前**由同一個 `qwen2.5:7b` 擔任**，帶來「生成者＝核對者」的循環性與 Jitkrittum et al.（2023）所述的 specialist 失效風險。本節定義對應的驗證，須在正式校準各處灰色地帶門檻數值**之前**執行：

1. **獨立核對者對照組**：在 RQ3 相關消融中，除「`qwen2.5:7b` 生成 + `qwen2.5:7b` 核對」外，加入「`qwen2.5:7b` 生成 + 一個獨立、能力更強的模型核對」對照組，量測接地核對的假陽性／假陰性率差異。若兩組差異顯著，代表現行核對存在「與生成者共謀」成分，第六章對 RQ3 幻覺抑制效果的宣稱須據此打折並明確標註。**所需的 provider 設定已實作（commit `ce84a77`）**：`settings.judge_llm_provider`／`judge_llm_model`（皆預設 `None` ＝ 沿用生成端 provider、行為零變化），設定後 `routers/agent.py::chat()` 的 3 處 `verify_fact_grounding()` 即改用該獨立 provider（生成與 `_targeted_correction` 維持用生成 provider）；跑對照組只需在該 run 的環境設定這兩個值，無需改碼。
2. **specialist 前提檢定**（2.4.4 末段掛的待辦，正式接入此處）：對 `qwen2.5:7b` 在「35 個 ConceptNet 關係型別仲裁」「`is_claim` 分類」「該不該拒答」三個任務上，各準備一批**分層**人工標註樣本，量測其準確度是否對輸入類型大致均勻。若明顯不均勻（specialist），則單純信心門檻的 deferral 規則理論上會系統性失效——此時 `SIM/ESCALATE3`、`is_claim`、grounding 各門檻的校準應改採 post-hoc deferral rule（小型評分器），或改由更強模型承擔該關卡，而非直接掃描門檻數值。**種子標註集已建立（2026-09-10，見 `docs/論文/05_附錄B_specialist前提檢定標註集.md`）**：三批各 ~18–24 筆，關係型別仲裁按型別家族分層（含刻意納入的「無合適→RELATED_TO」「⚠爭議」兩層）、`is_claim` 按句子子類分層、拒答按情境分層（完整／完全缺／近義干擾／部分）；附 P1d 的均勻性檢定方法（卡方適合度＋分層兩兩比例差異＋候選型別順序隨機化）。P1d 若發現某分層檢定力不足需依附錄 §B.4 擴充。
3. **位置偏誤（Han et al. 2025）**：任何以 LLM 做 A/B 評審的實驗（如 RQ1 KG-BFS vs. B1），兩個答案在評審 prompt 中的前後順序須隨機化並回報順序效應，避免重蹈 Edge et al.（2024）評審協定的位置偏誤。
