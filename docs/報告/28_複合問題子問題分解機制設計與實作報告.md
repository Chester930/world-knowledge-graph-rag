報告26 §4 排序第 2 的殘留瓶頸：

> `qwen2.5:7b` 會混淆、漏項。檢索是對的（事實都在），生成端的問題。

報告27（L0+L1，圖遍歷剪枝）§6.1 早期驗證意外發現：Q3 這次跑出**乾淨、四個事實

## 2. 前置查證：重現率與失效機制（2026-09-04）

用報告26 的原題（N0080013 大量解僱優先僱用，4 個子事實：連續三個月／發給三個月
為限／開始僱用起三十日內報備／滿三個月起三十日內申請）連跑 **4 次**（報告27 §6.1
的原驗證 1 次 + 本報告補測 3 次）：

| 次 | 結果 |
|---|---|
| 報告27 §6.1 原驗證 | ✅ 四個事實清楚分述 |
| 補測 Run 1 | ✅ 四個事實清楚分述（編號格式） |
| 補測 Run 2 | ❌ **重現**——見下方 |
| 補測 Run 3 | ✅ 四個事實清楚分述（編號格式） |

**重現率 1/4（25%）**，比報告26原本「每次都糊」低很多（L1 降噪確實有連帶效果），
但沒有歸零。

**Run 2 的失效機制比報告26原本的描述更精確**——不是「完全分不清誰是誰」，是
**答案內部自相矛盾**：

> 3. 事業單位應於開始僱用原經其大量解僱勞工之日起三十日內...報備。
> 4. 事業單位應於**連續僱用同一勞工滿三個月之日起三十日內**檢附下列文件向當地
>    公立就業服務機構申請僱用獎助措施。
>
> （...收尾...）事實清單中並未明確記載事業單位在**連续僱用满三个月之日起**的
> 具体申请期限，**因此無法確認**這部分的時間。

模型在第 4 點**正確引用**了「連續僱用滿三個月之日起三十日內申請」，但收尾摘要
卻又說這項資訊「並未明確記載」「無法確認」——**同一個事實，前面用對了、後面
自己推翻**。這與報告20 已確立的 `qwen2.5:7b` 批次推論非決定性（Horace He 2025）
一致：同輸入跨次呼叫結果不同，不是每次都會踩到這個失效模式。

## 3. 文獻對照

## 4. 設計與實作

### M0（prompt 補強，最小侵入）

`_build_prompt()`／`_build_constrained_prompt()` 的生成指示各加一句：

> 若你在回答的任何一部分已經引用某條事實作答，後面的摘要或結論不可以再說這項
> 資訊「未記載」或「無法確認」——同一份事實清單內，已經用過的事實視為確定
> 可用，前後結論必須一致。

直接對應 Run 2 觀察到的失效模式（引用後又推翻）。純文字指示，不改動事實清單
組裝邏輯（未做扁平列表 → 編號結構的格式改造——評估後判定侵入面過大：`_split_
fact_lines()`／`_is_contentful_line()`／dedup／`_score_lines_by_embedding()`／
RRF／既有測試皆依賴目前的 `"- "` 前綴格式，且 M1 分解上線後每個子問題已經是
獨立、聚焦的生成，格式改造的邊際效益降低，故不做）。

### M1（規則式問題分解，核心修法）

`routers/agent.py`：

- **`_split_into_subquestions(question)`**：按句末問號（`？`／`?`）切分複合問題。
  ≥2 個非空子句才視為複合問題，否則原樣回傳 `[question]`（單一問題行為完全
  不變）。`_MAX_SUBQUESTIONS=6` 防極端案例（貼上整段條文）炸開過多次生成。
  **零額外 LLM 呼叫**——中文問句以「？」結尾本身就是現成的子問題邊界，不需要
  文獻裡的 LLM 分解步驟。
- **`_generate_decomposed_answer(sub_questions, triples, fact_results, ...)`**：
  每個子問題各自呼叫一次 `_build_prompt()` + `llm_provider.stream()`，同一份
  已檢索事實清單、**不重新檢索**、彼此在生成當下互相看不到對方的輸出——這是
  避免「回答子問題 A 時受子問題 B 已寫內容影響、互相汙染」的機制核心。依原
  問題的子問題順序組裝（`"{i}. {sub_q}\n{answer}"`），不做額外的整合摘要呼叫。
- **`chat()` 接線**：`payload.use_svo` 且分解出 ≥2 個子問題且有檢索到事實
  （`triples or fact_results`）時走 `_generate_decomposed_answer()`；否則走
  原本的單次生成路徑（`use_svo=False`、無檢索結果、或非複合問題時行為不變）。
  下游 `verify_fact_grounding()`／限制性重新生成沿用既有機制，對組裝後的完整
  文字整體核對一次，不逐子答案核對（介面不變）。

**成本**：N 個子問題 = N 次完整生成呼叫，取代原本 1 次。報告26 Q3 通常 2–4 個
子問題，生成端延遲會相應增加，換取正確性——與報告27 L0+L1 降低的檢索延遲是
獨立的成本維度，不互相抵銷。

## 5. 驗證

**測試**：新增 9 個（`_split_into_subquestions` 5 個：多問號切分／單問號不變／
無問號不變／上限截斷／半形問號也切；`_generate_decomposed_answer` 1 個：各子
問題各一次呼叫、不互相夾帶問句文字；`chat()` 接線 3 個：複合問題觸發分解／
單一問題維持單次生成／**分解後接地核對失敗時重生也保留分解結構**）。全套
**666 passed**（`pytest -q`，132s）。

## 5.1 開發中真實測出的 bug：重生路徑漏接分解

初版實作只把分解接進「草稿生成」，未接進「限制性重新生成」（`chat()` 判定
草稿有未接地陳述時觸發，見 `_build_constrained_prompt()`）。**第一次真實 LLM
複測**（見下方）就抓到：分解出的草稿一旦觸發重生，`chat()` 會退回用
`_build_constrained_prompt(payload.question, ...)` 對**整個複合問題單次**
重新生成——分解機制在最需要它的路徑（已知有問題、要修正）上完全失效，
真實輸出格式錯亂（多個子答案內容混在一起、夾雜奇怪的自我核對註記如
「已經引用第6條」）。修正：新增 `_generate_decomposed_constrained_answer()`，
讓重生路徑跟草稿路徑用同一套分解結構逐子問題重生（`services/agent.py`
`chat()` 內 `ungrounded_claims` 分支據 `len(sub_questions) > 1` 二選一）。

## 6. 真實 LLM 驗證（2026-09-05，主 drain 暫停期間跑）

用報告26/27 §6.1 同一題（N0080013，3 個句末問號、對應 4 個子事實）連跑：

| 階段 | 次數 | 重現「引用又否認」自相矛盾 |
|---|---|---|
| 修法前（前置查證，§2） | 4 次（報告27原驗證1 + 補測3） | 1/4（25%） |
| **M0+M1 上線後**（含重生路徑修正） | 3 次 | **0/3** |

3 次全部輸出正確、格式為分解後的編號子答案（`"1. <子問句>\n<答案>"`），
無自相矛盾、無漏項、無跨子問題內容混淆。樣本數仍小（3 次），不宣稱「完全
根除」——`qwen2.5:7b` 的批次推論非決定性（報告20）意味著理論上仍可能在
某次呼叫重現，但決定性地降低了重現率，且失效模式（若重現）預期會侷限在
單一子問題內、不再是整個複合答案跨子事實混淆。

**副作用觀察**：修法後的答案明顯更長（每個子問題各自完整作答、常引用
「詳細來源如下」等自證句），生成端延遲因而上升（N 次獨立生成 vs. 原本 1 次）——
與報告27 L0+L1 降低的檢索延遲是獨立的成本維度，本報告不重新量測整體延遲，
留待日後跟報告27 §6 的驗證題組合併做一次全面延遲基準測試。
