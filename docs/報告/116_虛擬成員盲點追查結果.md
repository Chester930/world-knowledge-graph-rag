## 3. 暫存目錄重現

依 S2 在系統暫存目錄建立並執行腳本；腳本只使用暫存 staging/KG 目錄、fake driver、mock provider、mock queue，沒有啟動 Neo4j、Ollama 或 server。第一次執行因暫存腳本未把 repo 根加入 `sys.path` 而得到 `ModuleNotFoundError: No module named 'parser'`；僅修正暫存腳本後重跑，repo 沒有變更。最終腳本全文見附錄 A。

兩份文件都以 virtual manifest 指派，僅對第一份呼叫 `trigger_extraction(..., kg_folder=kg_folder)`。觀察結果如下：

| 觀察 | 結果 |
|---|---|
| KG 根內容 | `_members.json`、`virtual_one`；第二份沒有輸出子目錄 |
| 第一份輸出 | 輸出子目錄存在，但沒有 `_record.json` |
| `build_graph(force_rebuild=False)` | fake `trigger_extraction` 0 次，driver query 0 次 |
| `build_graph(force_rebuild=True, doc_ids=None)` | fake `trigger_extraction` 0 次；driver 收到 `MATCH (n {kg_id: $kg_id}) DETACH DELETE n` |
| `rebuild_from_records` | queue DB rows = 0 |
| `_kg_source_charset(kg_folder)` | 空集合，size = 0 |
| `_kg_source_charset(staging)` | 非空，size = 29 |

因此 Q3 的「清空後無法復原」程式路徑與 Q4、Q6 的虛擬成員盲點均可在離線暫存環境重現；未使用真實 LLM／embedding，provider 以刻意拋錯函式封鎖。

## 5. 修正方向選項（僅列選項，不實作、不排優先序）

1. 讓 `build_graph()` 以 manifest 的 `source_path`／文件 resolver 產生 target，並把正確 KG context 傳給抽取；對 force rebuild 增加虛擬成員完整性與清空前置檢查。
2. 讓 `rebuild_from_records()` 由 manifest 解析來源文件與 record，而不是只掃 KG 實體子目錄。
3. 讓 `_kg_source_charset()` 依 manifest source paths 蒐集 `original.md`，並統一三個呼叫點的 KG/source context。
4. 更新三個匯入腳本，明確區分 staging source、virtual assignment 與 KG output，將正確 `kg_folder`／resolver context 傳入抽取；保留實體複製腳本的獨立語意。
5. 更新比較、readiness、baseline 與 sweep 工具的 scope resolver，使 manifest ID 能解析到真實 source；對缺少原文或抽取輸出的情形明確報告，而不是靜默跳過。
