## 2. L2 已確定的設計決定與原因

1. **位置**：`services/semantic_marks.py`。理由：專案的純運算規則模組放 `services/`；`services/__init__.py` 是空檔，匯入它不會帶入其他重量模組；`check_node_cards.py` 執行結果「掃描 3 張節點卡，0 則警告」（新增前後相同）。
2. **無 I/O**：型別查表（核心 52／擴充 939）由**呼叫端傳入** `core_lookup`／`ext_lookup`（鍵須用本模組的 `normalize_type_key` 正規化，與 `services/extraction/prompt.py::_normalize_type_key` 相同規則但**自行實作、不匯入**，所以不碰 `prompt.py`）。L3 腳本載入 `data/schema_org_entity_types.json` 與 `core.constants.ENTITY_TYPES` 後建查表，仿 `scripts/analysis/phase0_marking_baseline.py`。
3. **值域**：`RESOLVED／NOT_APPLICABLE／UNKNOWN／PENDING／INDETERMINATE` ＝ 已解決／不適用／未知／尚未處理／無法由現有資料判定，常數 `PROVISIONAL = True`；只當函式回傳值，不寫回資料。
4. **`concept_scheme`**：`"A"`（預設，「概念」→未知）、`"B"`（→已解決）、`"strict"`（→無法判定）；其他值拋 `ValueError`。「概念」單獨（所有 token 都是「概念」）才適用；與標準型別並列者視為已解決；與非標準原字串並列者視為「尚未處理」（沿用 Phase 0 `classify_entity_type`）。
5. **關係型別**：`mark_relation_type(rel_type)` **簽章只有一個參數**，結構上不可能用 `verb_embedding` 推論來源（有測試）；非 `RELATED_TO`＝已解決，`RELATED_TO`／空／None＝無法判定。**與 Phase 0 的一個潛在差異**：Phase 0 把「空字串 rel_type」算作已解決（`t != "RELATED_TO"`），本函式把空白算無法判定；KG#4 的 `rel_type_null` 為 0，空字串數**未查**——L3 對照若差一點點，先查這個再說，**不要調規則湊數字**。
6. **`source_article_no`**：用 `has_article_no()`＝「是字串且 strip 後非空」做**明確比較**，不依賴 `None`／`""` 的真假值；文件層 `document_has_any_article_no` 決定「適用」；`mark_article_no(value, document_applicable)` 回已解決／未知／不適用。哨兵字串（如 `"N/A"`）只被當一般字串（有測試證明不被特別處理，也不被產生）。**與 Phase 0 的潛在差異**：Phase 0 用 `a not in (None, "")`，純空白字串在 Phase 0 算「已知」、這裡算「無」；KG#4 實測 `article_no` 欄位若無純空白值則一致（L3 會揭露）。
7. **空欄位**：`mark_fact_fields(subject, obj, verb)` 沿用報告209 嚴格規則：空受詞且空 verb＝未知；其餘至少一空＝尚未處理；完整＝已解決；`None` 與純空白都算空。
