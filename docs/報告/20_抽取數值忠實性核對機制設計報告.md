# 20：抽取數值忠實性核對機制設計報告

> 狀態：🟡 設計完成，待實作。2026-08-31，接續報告19實作後的真實重跑驗證（§10）意外發現，撰寫。

## 1. 問題陳述：同一份輸入文字，不同次真實LLM呼叫得到不同結果

報告19 §10 的最小規模真實重跑驗證發現：對 KG `a53203ab` 的 `D0080015_警察人員特別休假辦法` chunk 4（第4條，原文明確寫「給予三至七日之特別休假」）呼叫 `extract_svo_triples_with_completeness_check()`：

- **第一次呼叫**（`debug_chunk4.py`）：正確抽出「三至七日之特別休假」。
- **第二次呼叫**（透過 `_process_one()` 真實production路徑）：**錯誤**抽出「一至三日之特別休假」——這是同一份文件**第2條**（相鄰但不同等級）的數字，被錯誤挪用到第4條的三元組上。

兩次呼叫的輸入（`chunk["text"]`）、prompt、`temperature=0.0` 設定完全相同。這不是規則7-9或完整性核對機制的問題（兩次呼叫都只觸發1次抽取，涵蓋比對正確判定無遺漏），而是**同一輸入、不同次真實LLM呼叫產生不同（且其中一次錯誤）結果**——已排除是本專案程式碼的bug。

## 2. 根因（2026-08-31 即時查證，非猜測）

**temperature=0 不保證決定性輸出**：Horace He（Thinking Machines Lab，2025-09-10 部落格文章《Defeating Nondeterminism in LLM Inference》）指出，即使把 temperature 降到 0，LLM 推論伺服器在實務上仍非決定性——根因不是取樣隨機性，而是**批次大小依賴（batch-size dependence）**：伺服器當下的負載（決定查詢被分到哪個動態批次）會改變底層 GPU 核心的並行化策略與浮點運算累加順序，浮點運算不具結合律，不同累加順序產生不同結果，使用者對此完全不可控。文中量化：徹底解決（batch-invariant kernels）需付出 **62-113% 的吞吐量開銷**（依優化程度不同）。

**對本專案的適配度**：本專案已將 `core/providers/llm/ollama.py` 的 `temperature` 設為 `0.0`（`generate`／`generate_json` 皆是），但這**不足以消除不確定性**，報告19 §10 的真實案例正是具體證據。⚠️ 本文為部落格文章，非同行評審論文，不適用 🟢/🟡 信任分級；但作者為知名 ML 系統工程師（PyTorch 核心貢獻者），文中提供可重現的 GitHub 實作與量化實驗數據，非空泛主張。

**結構性結論**：徹底解決（batch-invariant kernels）需要客製化推論核心，代價高昂，**不適合本專案這種單機本地 Ollama 環境**的規模與投入。應改為「不追求消除不確定性，改追求偵測不確定性造成的具體錯誤」這個更務實的方向。

## 3. 設計：抽取數值忠實性核對（第三個「輸出↔依據互相核對」鏡像應用）

**核心構想**：本專案已有兩個同一architecture家族的機制：
- 報告16 事實接地性核對——生成的內容有沒有**多說**（捏造），方向是精確度
- 報告19 抽取完整性自我核對——抽取的內容有沒有**少說**（遺漏），方向是召回率

本報告是第三個鏡像應用，方向是**忠實性**——抽取的數值有沒有**抄錯地方**（從同一份文件裡其他相似段落挪用了錯誤的數字）。

**設計**：抽取完成後，對每筆三元組的 `subject`／`object`，用正則表達式偵測是否含有數量/期限/比例用字（中文數字或阿拉伯數字＋「日」「月」「年」「次」「百分之」「％」等單位），偵測到時檢查該片段文字是否**逐字**出現在**這個 chunk 的原文**（`chunk["text"]`）裡；沒有出現，代表這個數值不是這段文字本身的內容（極可能是從同文件其他相似段落錯誤挪用），直接**丟棄**這筆三元組，不寫進圖譜——比照 3.1.3 REJECT（不合法 rel_type 退回兜底，不阻斷整體）、以及本設計自身鏡像的 report16/19 的既有降級哲學：寧可漏抓一筆有疑慮的三元組，也不留下錯誤數字污染圖譜。

**為什麼是逐字比對，不是語意/embedding比對**：這裡刻意選擇最簡單的機制——數值/期限用字本身就是需要精確比對的內容（差一個字「三」變「一」意義就完全不同），embedding 相似度比對反而會讓「三至七日」與「一至三日」因為結構相似被誤判為語意相近而放行，起不到防護作用。純字串比對雖然簡陋，但正好是這個失效模式需要的精確度。

**文獻定位**：
- Horace He（2025，部落格，非論文）——見§2，根因與成本量化依據。
- See, Liu & Manning（2017，🟢 ACL 2017）《Get To The Point: Summarization with Pointer-Generator Networks》——文中提出的 pointer-generator 機制讓模型可以直接從原文「複製」關鍵詞彙，而非完全仰賴生成，是「直接複製自原文的內容比生成內容更可信」這個設計原則的既有學術先例；⚠️ 誠實聲明：這篇論文的應用場景是摘要生成（訓練時的架構設計），不是本報告設計的「事後核對抽取結果是否逐字出現於原文」，機制層級不同，僅能佐證「複製自原文＝更可信」這個大方向的設計哲學，具體演算法不可直接套用。

## 4. 對應程式碼草案（未實作）

```python
import re

# 中文數字（含全形阿拉伯數字混用）＋常見單位的量詞片語粗略偵測，
# 不要求完全精確（寧可多檢查幾個非量詞片語，也不要漏掉真正的量詞片語）。
_QUANTITY_PATTERN = re.compile(
    r"[〇零一二三四五六七八九十百千萬0-9]+"
    r"(?:至[〇零一二三四五六七八九十百千萬0-9]+)?"
    r"(?:日|月|年|次|小時|分鐘|百分之|％|%|元|倍)"
)


def _contains_ungrounded_quantity(text: str, source_text: str) -> bool:
    """偵測 `text`（三元組 subject 或 object）裡是否含有數量/期限用字，
    且該片段未逐字出現在 `source_text`（chunk 原文）裡——真的偵測到才
    回傳 True，供呼叫端決定是否丟棄這筆三元組（見報告20 §3）。
    """
    for match in _QUANTITY_PATTERN.finditer(text):
        if match.group() not in source_text:
            return True
    return False


def _filter_ungrounded_quantity_triples(
    triples: list[SVOTriple], source_text: str,
) -> list[SVOTriple]:
    """丟棄 subject／object 含未逐字出現於原文的數量/期限用字的三元組——
    對應報告19 §10 發現的真實失效案例（跨條文數字挪用）。"""
    return [
        t for t in triples
        if not _contains_ungrounded_quantity(t.subject, source_text)
        and not _contains_ungrounded_quantity(t.object, source_text)
    ]
```

**整合點**：在 `extract_svo_triples_with_completeness_check()` 回傳前（合併去重之後）套用 `_filter_ungrounded_quantity_triples(merged, text)`，`text` 即該函式已有的第一個參數（chunk全文），不需要新增呼叫端參數。

## 5. 成本分析

純字串比對＋正則表達式，無額外 LLM 或 embedding 呼叫，成本可忽略不計（毫秒級）。

## 6. 誠實侷限

- 正則表達式偵測數量片語不可能完全精確——可能漏抓某些不規則寫法的數量用語（偽陰性，不擋下該擋的），也可能誤判非數量的巧合數字片語為數量用語（偽陽性，丟棄了其實正確的三元組）。
- 只能抓「數值本身沒出現在原文」這一種失效模式，抓不到「數值出現在原文、但被錯誤配對到錯的subject/object」這種更隱蔽的錯誤（例如把本條的天數配到別條的罪名上，若剛好兩個片段都各自在原文出現過）。
- 不解決根本的LLM輸出不確定性問題，只防堵這個具體失效模式的下游後果——與 §2 的結論一致，是刻意的取捨。
