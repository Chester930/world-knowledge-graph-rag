## 2. 逐題結果

### 題1｜警察人員特別休假辦法：核發依據、天數、是否與年資有關

- **[A] 新KG**：正確列出「获得特别贡献或特殊功绩受颁勳章者给予**三至七日**之特别休假」與「其他情形给予**一至三日**之特別休假」兩個檔次，誠實標示「資料未明確記載，無法確認…是否與服務年資有關」。
- **[B] 舊KG**：**只列出「一至三日」情形，完全遺漏「三至七日」較高檔次**，最終結論「最高可以给予**三日**特别休假」——與辦法原文（最高七日）不符。
- **[D] 純LLM**：全面捏造，引用不存在的《警察人員特別休假條例》、虛構《勞動基準法》第31-33條與「服勤滿一年5日、滿20年14日」等不存在的規則。

**判定：[A] 明顯優於 [B]**——這正是報告19完整性核對（漏抽取原文中的次要條款）與報告20數值忠實性核對（防止數量憑空捏造/遺漏）要解決的失效模式，新KG正確保留了較高檔次資訊，舊KG漏掉後導致「最高天數」這個關鍵結論性錯誤。[D] 明顯最差，全篇幻覺。

### 題2｜勞工請假規則第7條：事假天數與工資

- **[A]**：「一年內合計不得超過十四日」「請事假期間不給工資」，答對核心數字。
- **[B]**：同樣答對「14天」「不給工資」，且額外補充「應於事前親自以口頭或書面敘明請假理由及日數」。
- **[D]**：迴避具體天數，承認「勞動基準法對此並沒有明確規定」（此題劃錯法規，事假規定在《勞工請假規則》非《勞基法》本文）。

**判定：[A]／[B] 打平**，兩者都答對核心數字。此條文的規則7修正效果在報告18已用專門測試驗證過，本題未再現額外差異，屬預期內結果。

### 題3｜勞工請假規則第7條：家庭照顧彈性

- **[A]**：只答出「可以依第七條規定請事假」，**未提及原文「並得擇定以小時為請假單位」這項關鍵彈性**。
- **[B]**：正確答出「事假期間可選擇**以小時為單位**」。

**初步判定（已修正，見下方2026-09-01追查）：[B] 優於 [A]**。

**⚠️ 追查更正（2026-09-01）**：原始判定誤把此差異歸因於「新KG抽取遺漏」。事後直接重跑一次同樣的檢索管線（`_find_seed_entities` → `bfs_query` → `resolve_query_relation_type`／`_filter_triples_by_relation_type` → `vector_search_facts` → `_filter_triples_by_source_doc_ids` → `_merge_fact_lines`）並逐步攔截中間結果，發現：

1. **抽取正確**：新KG的Neo4j圖裡確實存在 `事假 -[RELATED_TO]-> 小時為請假單位`（verb: 得以，來源N0030006第7條chunk 7）——完整性/數值忠實性核對機制運作正常，並未遺漏。
2. **檢索正確**：這筆三元組通過了關係型別篩選（`resolved_rel_type=None`，不篩選）與文件範圍篩選（`relevant_doc_ids`涵蓋N0030006），最終確實出現在送給LLM的28行事實清單中的第「- 事假（概念）得以小時為請假單位（概念）」一行。
3. **生成階段遺漏**：LLM在收到這28行事實清單（含正確答案）的情況下，仍然生成「資料未明確記載，無法確認是否給了其他額外的彈性」——**事實有檢索到，但沒被生成階段引用**。

**修正後判定**：本題並非抽取或檢索管線的缺陷，而是生成階段對較長事實清單（本題28行）的遵循率問題，性質上與 `/agent/chat` docstring 中提及、待 3.2 §a（RQ2）正式雙層RAG流程（含「自我精煉迴圈」）解決的既有誠實侷限相同——目前的生成呼叫是一次性的，沒有機制強制LLM逐條核對事實清單裡每一項與問題的相關性。完整性/數值忠實性核對機制在**抽取端**的效果，本題不構成反例。

## 4. 誠實侷限

- 樣本數small（5題），統計把握力有限，結論屬方向性觀察而非嚴謹顯著性檢定。
- 測試時新KG僅抽取到約18%（600/3303），受限於「新舊KG皆須100%完成」的篩選條件，只涵蓋了8份小型文件（各6-9個chunk），未涵蓋大型文件（如N0030001_勞動基準法，數十個chunk）——大型文件的抽取品質差異尚待新KG完整跑完後另行驗證。
- 舊KG本身不是純粹的「修正前」快照，而是三項修正陸續上線期間累積的混合快照（見背景說明），题2打平的結果可能反映的是「舊KG累積時規則7已經上線」而非規則7無效——報告18已用更早期的KG（`99a25aca`，規則7修正前）做過乾淨的pre/post比較，此處不重複驗證。

### 5.1 修正後的真實線上驗證（2026-09-01，同日）——效果有限，如實記錄

部署後直接重跑題1、題3兩次（`/agent/chat` 真實呼叫，非離線排序測試），結果：

| | 題1（警察特休天數） | 題3（事假小時彈性） |
|---|---|---|
| Run 1 | 涵蓋三至七日／一至三日兩檔次，但未給出明確「最高天數」結論 | **完全沒提到目標事實**，答「資料未明確記載」——比修正前更差 |
| Run 2 | 明確答出「最高可以給七日」，較Run 1更完整 | 提到第7條另一項細節（全勤獎金不受影響），**仍未提到「以小時為單位」這個目標事實** |

**誠實結論**：2次真實重跑中，題3的原始目標事實（「以小時為請假單位」）**一次都沒有成功被引用**——bigram排序把它從第16名推到第11名，但28行清單裡的第11名顯然仍不夠靠前，LLM在冗長清單中持續選擇了其他同樣提到「事假」「第七條」的細節（全勤獎金那句），而非目標事實。**低成本方案（排序＋prompt指示）方向正確，但沒有實質解決題3這個具體失效案例**；也再次確認了報告20已root-caused的LLM推論非決定性——兩次BFS三元組數不同（54 vs 之前測試的37/40），連檢索階段的種子命中都不穩定，題1的表現波動（Run1模糊、Run2清楚答出七日）同樣印證這點。

**修正後建議**：低成本方案已是誠實侷限下能做的第一步，但**不建議就此視為已解決**。下一步應評估：(a) 升級為embedding相似度排序（比bigram更準確的相關性訊號，成本是每次問答多一輪批次encode）；(b) 縮短事實清單長度（例如BFS結果先依語意分數篩選到前N筆，而非把所有50+筆全塞給LLM，降低訊噪比）；(c) 3.2 §a（RQ2）正式雙層RAG流程的自我精煉迴圈，屬於更根本、成本也更高的方案。三者可先從(b)（限制事實清單長度）開始評估，成本與(a)相近但實作更簡單。

**✅ 文獻查證（2026-09-01，同日）**：查證後發現 Liu et al. (2023, TACL 2024) *Lost in the Middle: How Language Models Use Long Contexts*（見 [docs/參考文獻/19_生成端長清單事實遺漏與位置偏誤](../參考文獻/19_生成端長清單事實遺漏與位置偏誤/README.md)）與本次真實觀察高度吻合——LLM對長輸入內容的效能呈U形曲線，相關資訊在**開頭或結尾**效能最好，在**中段**顯著下降。目標事實被bigram排序推到第11名（28筆中，中段偏前）恰好落在效能低谷區間，這解釋了為何「排序方向正確但沒解決問題」。

進一步找到 Jin et al. (2025, ICLR) *Long-Context LLMs Meet RAG: Overcoming Challenges for Long Inputs in RAG* ——不只重現Lost-in-the-Middle現象，還給出正式的zigzag重排公式（與LangChain `LongContextReorder` 開源實作邏輯一致），並提供關鍵的**邊界條件實證**：retrieval reordering**在檢索集合較小時效果不明顯**，只有集合較大時才顯著改善。這代表原先「(a) 升級相關性訊號＋(b) LiTM重排＋(c) 截斷到前K筆」**不是可以無腦疊加的三件事**——若能安全截斷到小K值（如3-7筆），清單已無夠大的中段可造成低谷效應，重排的邊際效益低；只有在因涵蓋率考量、清單無法大幅截斷時，重排才有實質必要。

**修正後建議（依文獻邊界條件重新排序）**：優先評估能否安全截斷事實清單到小K值（同時觀察對召回率的影響）；若截斷會犧牲太多涵蓋率、清單仍需維持較大長度，才疊加(a)升級相關性訊號（embedding取代bigram）與(b)移植LiTM zigzag重排。三者不是無條件全上，而是依「能不能安全截斷」這個判斷分岔。
