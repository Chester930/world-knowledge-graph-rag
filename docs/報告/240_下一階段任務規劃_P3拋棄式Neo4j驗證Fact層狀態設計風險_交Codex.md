## 4. T0 規格（安全閘門）

腳本放 `scripts/analysis/`（純標準庫＋專案既有 `neo4j` 驅動），**純運算（參數檢查、命令組裝）與 docker／DB 存取分離並附單元測試**：
1. **連線閘門**：任何會連 Neo4j 的函式，**在連線前**檢查 URI——port 必須是 `27687`、host 必須是 `localhost`／`127.0.0.1`；**port 為 `17990` 或與 `kg2-neo4j` 相關者一律拒絕並丟錯**；`kg_id` 不得為 `236903cf-055a-40a8-8923-b9d06601f3b7`。**這些閘門要有單元測試**（含故意傳入 17990 必須失敗）。
2. **臨時容器密碼**：由腳本在**記憶體內隨機產生**，只透過環境變數傳給 `docker run` 與驅動，**不得印出、不得寫入任何檔案、報告、JSON、命令列歷史**；不得讀取專案 `.env` 的 `NEO4J_PASSWORD`。
3. **容器參數固定**：名稱 `kg2-throwaway-neo4j`；映像 `neo4j:5.26-enterprise`（不得 `pull`）；`-p 27474:7474 -p 27687:7687`；`--memory 3g`；`NEO4J_server_memory_heap_max__size=1G`、`NEO4J_server_memory_pagecache_size=512M`；**不得**使用 `--privileged`、`-v`／`--mount`、`--network host`、`--restart`；若同名容器已存在，**先停止並詢問使用者，不得強制刪除**。
4. **docker 指令白名單**：只允許 `docker run`（上列參數）、`docker ps`、`docker inspect --format`（**僅取 State／StartedAt，不得輸出環境變數**）、`docker stop kg2-throwaway-neo4j`、`docker rm kg2-throwaway-neo4j`。**嚴禁** `docker rm -f` 其他容器、`docker system prune`、`docker volume`／`docker network` 變更、對 `kg2-neo4j` 的任何指令（含 `exec`／`logs`／`inspect` 完整輸出）。
5. **前後快照**：開始前與結束後記錄 `kg2-neo4j` 的 `State.StartedAt` 與 `State.Status`（僅此兩欄），證明它沒被重啟或停止。
6. 提供 `--teardown`，並確保任何失敗路徑也會嘗試拆除臨時容器（`finally`）。

## 5. T1 規格（五個驗證情境；**用 production 既有函式在臨時容器上取得「現行行為」，不得修改 production**）

資料以**合成（虛構）**事實建立，向量用**小維度（例如 8 維）決定性假向量**（可自訂一個假的 `EmbeddingProvider`，只放在驗證腳本內）；盡量透過 production 既有路徑建立（如 `merge_triples_to_graph`、`create_fact_vector_index`），以確保測的是真實行為。**所有「設計提案」的行為（狀態過濾、標記撤銷等）一律只寫在驗證腳本內的 Cypher 或函式，不得改 production。**

| ID | 情境 | 要驗證 | 通過判定 |
| --- | --- | --- | --- |
| **C1** | **去重風險**：同一（主詞,關係型別,受詞）有兩個 Fact——舊版（`lifecycle_state=已被取代`、向量與查詢更近）與新版（`有效`） | ①呼叫既有 `vector_search_facts`：**記錄它是否留下分數最高者（預期＝舊版，證實風險）**；②在腳本內實作「先依狀態過濾、再去重」的提案版本，驗證**留下新版** | 兩項結果皆如實記錄；若現行行為**不是**預期，如實回報並解釋，不要硬湊 |
| **C2** | **撤銷**：既有 `revoke_chunk_facts` 對某 chunk 的 Fact 的行為 | ①記錄其是否**實體刪除 Fact**（預期是）；②腳本內實作提案版本：已採信的 Fact 追加事件並標 `已駁回`、**保留節點**，驗證檢索排除 | 如實記錄 |
| **C3** | **BFS 只看邊**：`bfs_query` 在有「已被取代」Fact 時的輸出 | 記錄 BFS 是否仍回傳該邊（預期是，因它不讀 Fact 狀態）；腳本內以 Cypher 聚合驗證「邊狀態＝其 Fact 狀態聚合」（報告234 §6 的暫定規則）可行；量測在約 1,000 個合成 Fact 上的查詢耗時（僅供量級） | 如實記錄 |
| **C4** | **舊資料缺席狀態**：無 `lifecycle_state` 屬性的 Fact | 驗證 D3 預設可檢索集合在 Cypher 層的表達（`IS NULL OR IN [候選,有效,爭議]`），且過濾發生在去重之前；缺席者仍可檢索 | 如實記錄 |
| **C5** | **事件清單與狀態漂移**：`lifecycle_events_json`（只追加）＋ `lifecycle_state`（快取） | 用 Cypher 追加事件、用 `services.relation_lifecycle.replay` 重播，驗證兩者一致；故意製造不一致（手動改 `lifecycle_state`）並驗證稽核檢查能偵測到 | 如實記錄 |

每個情境輸出：現行行為、提案行為、是否符合報告233／234 的推論、**未預期發現**。**不得宣稱「驗證了整個狀態機落地」**——這只驗證上述五個讀寫風險點。
