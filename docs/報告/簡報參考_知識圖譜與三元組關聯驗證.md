# 簡報參考：知識圖譜與三元組關聯驗證

> 使用順序提醒：報告時先完成「為什麼要用知識圖譜」與「如何驗證三元組關聯」兩個回答，再開始介紹本專案。這樣聽眾會先理解問題意義，再理解專案為什麼這樣設計。

## 題目一：為什麼要用知識圖譜

### 先說清楚隱含問題

這一題真正要回答的不是「知識圖譜很好」，而是：

```text
既然 2026 年的 RAG 已經有混合檢索、重排序、查詢改寫、Agentic RAG、Structured Planning RAG，
為什麼還需要知識圖譜？為什麼不用 RAG 就好？
```

所以報告時不要一開始就介紹知識圖譜。比較好的順序是：

```text
先承認 RAG 的優點
-> 說明 2026 版 RAG 仍然存在的結構限制
-> 比較知識圖譜的優缺點
-> 引出 GraphRAG：整合 RAG 與 KG 的優點
-> 點出 2024 GraphRAG 的重大缺陷
-> 收束到本專案要處理的核心：三元組關聯品質
```

### 1. 2026 版 RAG 的優點

RAG 的核心價值，是讓 LLM 不只依賴訓練時記住的知識，而是在回答前先從外部資料庫取回相關內容。到 2026 年，RAG 已經不只是「向量搜尋 + LLM」的簡單流程，而是發展出多種強化版本：

- **Hybrid RAG**：結合向量搜尋、BM25 關鍵字搜尋與 metadata filter。
- **Reranking RAG**：先大量召回，再用 reranker 選出更相關的片段。
- **Query Rewriting / Decomposition**：把使用者問題改寫或拆成子問題。
- **Agentic RAG**：讓 agent 多輪規劃、搜尋、反思與補查。
- **Structured Planning RAG**：先建立查詢計畫，再逐步檢索證據，降低多跳問題中的 retrieval drift。

這些技術讓 RAG 仍然非常有價值：

- 建置速度快，不一定要先建完整知識圖譜。
- 對開放式問答、摘要、一般文件查詢很彈性。
- 適合資料常更新、格式不固定、短期導入的場景。
- 可以直接利用原文片段，避免過度結構化造成資訊損失。

簡報講法：

> 所以我的主張不是「RAG 不好」。相反地，2026 年的 RAG 已經很成熟，尤其在快速導入、語意搜尋與一般問答上仍然是主流方法。真正的問題是：當任務需要明確關係與多步推理時，RAG 是否仍然足夠？

### 2. 2026 版 RAG 仍然不擅長的地方

即使是強化版 RAG，它的基本檢索單位多半仍是文字 chunk。這會帶來幾個限制：

| 問題 | RAG 的困難 |
|------|------------|
| 關係不明確 | RAG 找到相似片段，但不一定知道哪兩個實體有什麼關係。 |
| 多跳推理不穩 | 問題需要 A -> B -> C 時，系統必須剛好找回所有支撐片段，且 LLM 要自行串起來。 |
| Retrieval drift | 多輪檢索時，後續查詢可能逐漸偏離原本推理路徑。 |
| 噪音累積 | 召回越多 chunk，LLM 要在更多無結構文字中挑答案，反而可能降低正確率。 |
| 可追溯性不足 | 可以引用文件片段，但較難明確標示「答案是沿著哪幾條關係推得」。 |
| 長期知識管理不足 | 實體別名、同義關係、重複事實、時間變化，若只存在 chunk 中較難統一管理。 |

簡報講法：

> RAG 的強項是找資料；但知識管理不只要找資料，還要知道資料裡的實體、關係、路徑與來源。這就是知識圖譜要補的位置。

### 3. 知識圖譜的優點與代價

知識圖譜把知識表示成：

```text
實體 A --關係--> 實體 B
```

例如：

```text
Neo4j --儲存--> 知識圖譜
知識圖譜 --支援--> 多跳推理
ConceptNode --負責--> 知識庫路由
BFS 圖遍歷 --找出--> 關聯路徑
```

它的優點是：

- 把「文字相似」提升為「實體關係」。
- 可以沿著節點與邊做多跳查詢。
- 可以把推理路徑顯示出來，提升可解釋性。
- 可以把同一實體的不同名稱對齊，例如「勞基法」與「勞動基準法」。
- 可以把相同事實合併，讓多個來源支撐同一條關係。
- 可以保存來源、句子範圍、信心值與時間資訊，支援長期知識管理。

但知識圖譜也有明顯代價：

- 建圖成本高，需要抽取實體與關係。
- 抽取錯誤會污染圖譜。
- schema 設計太死會降低召回，太自由又會造成關係混亂。
- 圖太大時，遍歷會遇到高連結節點與路徑爆炸。
- 對一般摘要或開放式探索問題，不一定比 RAG 划算。

所以更合理的結論不是「RAG vs KG 二選一」，而是：

```text
RAG 適合快速找文本證據；
知識圖譜適合管理可查詢、可追溯、可推理的關係；
GraphRAG 則是把兩者結合。
```

### 4. GraphRAG：整合 RAG 與知識圖譜的優點

GraphRAG 的核心想法是：不要只把外部知識庫看成一堆文字 chunk，而是先從文本中建立實體與關係圖，再把圖結構用於檢索與生成。

它整合了兩邊的優勢：

| 能力 | RAG 提供 | 知識圖譜提供 | GraphRAG 的整合方式 |
|------|----------|--------------|----------------------|
| 快速引用原文 | 可以直接取回 chunk | 可記錄每條關係來源 | 回答同時使用文字證據與圖上關係 |
| 語意搜尋 | embedding 找相似內容 | 實體節點可加 embedding | 先語意召回，再沿圖擴展 |
| 多跳推理 | 可透過 agent 多輪查詢 | 可用 BFS/路徑查詢明確走圖 | 把推理變成可檢查的路徑 |
| 全局理解 | 摘要大量文本有成本 | 可做社群/群集摘要 | 對整個語料產生 global summary |
| 可追溯性 | 引用 chunk | 引用節點、邊、來源句 | 回答可附來源與關係鏈 |

簡報講法：

> GraphRAG 不是把 RAG 丟掉，而是把 RAG 的文本檢索能力，和知識圖譜的關係推理能力接在一起。使用者問簡單問題時可以走文本；問多跳關係時可以走圖；問全局主題時可以走社群摘要。

### 5. 2024 版 GraphRAG 的重大缺陷

2024 年 Microsoft GraphRAG 的代表性做法，是用 LLM 從文本抽取 entity/relationship，建立知識圖譜，再做 community detection，並為每個社群預先產生摘要。這個設計成功補強了傳統 RAG 對「全局問題」的不足，但也留下幾個重大缺陷，正好可以為本專案鋪墊。

#### 缺陷一：建圖成本太高，冷啟動慢

2024 GraphRAG 需要：

```text
文件切塊
-> LLM 抽取實體與關係
-> 建立圖
-> community detection
-> LLM 產生 community summaries
-> 查詢時再彙整回答
```

這代表它在查詢前就要付出大量前處理成本。對百萬 token 等級資料可以接受，但如果使用者希望「上傳後馬上可問」，全量建圖與摘要會變成明顯瓶頸。

本專案鋪墊：

> 因此本專案後續採用「向量先行、SVO 非同步建圖」的思路，讓系統先可用，再逐步補上圖譜能力。

#### 缺陷二：LLM 建圖品質不穩，錯誤會變成檢索路徑

GraphRAG 的前提是：LLM 抽出的知識圖譜足夠可靠。但 2026 年的研究已指出，這個前提在實務上不一定成立。LLM 建圖可能出現：

- spurious noise：看起來合理但原文不支撐的錯誤三元組。
- incomplete information：缺少中間橋接邊，導致多跳路徑斷裂。
- over-generalized relation：關係過度泛化。
- mis-bound relation：關係接到錯誤實體。
- semantic flip：主詞與受詞方向顛倒。
- dropped qualifier：時間、地點、條件等限定資訊被漏掉。

一旦錯誤三元組進入圖中，GraphRAG 不是單純「找錯片段」，而是可能沿著錯誤邊繼續擴展，造成 retrieval drift 或 hallucinated structural continuation。

本專案鋪墊：

> 因此本專案不能只說「我們有知識圖譜」，還必須處理三元組驗證、關係類型標準化、來源追溯與事實去重。

#### 缺陷三：2024 GraphRAG 偏向全局摘要，不等於精準三元組問答

Microsoft GraphRAG 原始論文主要強調 global sensemaking，也就是回答「整份資料的主題是什麼」、「有哪些主要觀點」這類全局問題。它對全局摘要很有價值，但本專案的目標更偏向：

- 精準查某個實體與另一個實體的關係。
- 查一條關係是從哪份文件、哪個 chunk、哪句話來的。
- 讓多跳推理路徑可以被檢查。
- 在多知識庫場景中先路由，再遍歷。

因此本專案不能只複製 2024 GraphRAG 的 community summary 架構，而需要更重視 SVO 邊的品質與來源。

#### 缺陷四：圖遍歷會遇到路徑爆炸與 Hub Node 問題

知識圖譜越大，從一個節點出發能走到的鄰居越多。像「AI」、「公司」、「年份」、「台灣」這類高連結節點，可能連到大量無關資訊。若 BFS 沒有良好剪枝，會造成：

- 候選子圖爆炸。
- 查詢延遲上升。
- 無關路徑進入 context。
- LLM 被噪音干擾。

本專案鋪墊：

> 所以本專案設計 ConceptNode 路由與 bounded BFS，不是單純把整張圖丟給 LLM，而是控制檢索範圍與路徑品質。

#### 缺陷五：評估困難，不能只看答案像不像

GraphRAG 的輸出常是摘要或開放式回答，評估不容易。只用 LLM-as-a-judge 會有偏差；只看最終答案，也看不出是檢索錯、建圖錯、路徑錯，還是生成錯。

本專案鋪墊：

> 因此後續實驗需要同時看答案正確率、可追溯性、三元組品質、關係路徑是否支撐答案，而不是只看回答流不流暢。

### 6. 回到核心：GraphRAG 的關鍵不是「有圖」，而是「邊是否可信」

GraphRAG 的核心資料結構不是漂亮的圖形介面，而是圖裡每一條可被查詢的關係。這些關係最基本的單位就是三元組：

```text
Subject --Relation--> Object
主詞 --關係--> 受詞
```

也就是本專案的 SVO：

```text
Subject + Verb/Relation + Object
```

因此第一題最後要收束到：

> 我們需要知識圖譜，不是為了多一個視覺化圖，而是為了讓 RAG 不只檢索文字，也能檢索「可驗證的關係」。而這些關係是否可靠，取決於三元組是否抽得正確、關係類型是否一致、來源是否可追溯。這就進入第二題：如何驗證三元組的關聯？

### 題目一總結

2026 年的 RAG 仍然是非常重要的基礎技術，優點是快速、彈性、能直接引用原文；但它的主要限制是以文字 chunk 為核心，對明確關係、多跳路徑、長期知識治理與關係層級可追溯仍然不足。知識圖譜補上的是結構化關係，而 GraphRAG 則試圖結合 RAG 的文本檢索與知識圖譜的關係推理。不過 2024 版 GraphRAG 仍有建圖成本高、LLM 建圖品質不穩、偏向全局摘要、圖遍歷路徑爆炸與評估困難等缺陷。因此，本專案後續要處理的核心問題，就是如何把 GraphRAG 的圖譜基礎做得更可信，而這會回到知識圖譜最基本的結構：SVO 三元組。

## 題目二：驗證三元組的關聯

### 先釐清「三元性」

報告時建議把「三元性」說成「三元組關係」，也就是：

```text
Subject --Predicate/Relation--> Object
主詞 --關係--> 受詞
```

本專案用 SVO 表示：

```text
Subject + Verb/Relation + Object
```

例如：

```text
知識圖譜 --支援--> 多跳推理
ConceptNode --負責--> 知識庫路由
BFS 圖遍歷 --找出--> 關聯路徑
```

三元組關聯驗證要回答的不是「有沒有抽到三個欄位」而已，而是要確認這個三元組是否真的能代表原文中的事實關係。

### 文獻證據：為什麼三元組需要驗證

報告時可以先拿出文獻證據，說明「三元組不是我自己發明的格式」，而是資訊抽取與知識圖譜建構裡長期使用的基礎單位；同時也證明「三元組品質需要驗證」，不是只要 LLM 抽出 JSON 就算完成。

| 文獻 | 可以拿來證明什麼 |
|------|------------------|
| Angeli et al. (2015), Stanford OpenIE | OpenIE 會從句子抽出 relation triples，例如 `(Barack Obama; was born in; Hawaii)`。這證明三元組是開放資訊抽取的標準表達方式。 |
| Text2KGBench (Mihindukulasooriya et al., 2023) | 評估 LLM 是否能依照 ontology 從文本生成知識圖譜。這證明「有本體約束的 KG 生成」需要 benchmark 與 metrics，而不是主觀判斷。 |
| CORE-KG (Meher et al., 2025) | 指出 LLM 建圖常有 hallucination、duplicate nodes、noisy graphs；加入 coreference resolution 與 domain-guided extraction 後，可降低節點重複與噪音。這支撐本專案的別名消解、來源追溯與去重需求。 |
| CoDe-KG (Anuyah et al., 2025) | 以 sentence-level KG、coreference resolution、sentence decomposition 提升關係抽取表現。這支撐本專案先做句子級前處理、SVO chunk 與原句索引。 |
| Ma et al. (2026), Robust GraphRAG | 指出不完整或錯誤的 KG 會造成 GraphRAG retrieval drift 與 hallucination。這可直接支撐「三元組錯，GraphRAG 就會沿錯誤邊檢索」的論點。 |

簡報講法：

> 文獻的共同結論是：三元組可以把文字轉成可查詢的關係，但 LLM 抽出的三元組不一定可靠。如果三元組錯了，GraphRAG 不是只是引用錯片段，而是可能沿著錯誤關係繼續推理。所以三元組驗證是 GraphRAG 能不能可信的核心。

### 1. 結構驗證：三個欄位是否完整

第一層是格式與結構檢查：

- `subject` 是否存在，而且不是空字串。
- `rel_type` 是否存在，而且屬於合法關係類型。
- `object` 是否存在，而且不是空字串。
- `confidence` 是否在合法範圍內。
- 是否保留來源資訊，例如文件 ID、chunk index、句子範圍。

這一層可以擋掉格式錯誤，例如：

```text
錯誤：GraphRAG --空白關係--> RAG
錯誤：空白主詞 --支援--> 多跳推理
錯誤：知識圖譜 --隨便產生的新關係--> 可追溯性
```

### 2. 詞彙表驗證：關係類型是否受控

如果讓 LLM 自由產生關係詞，可能會出現語意相近但字面不同的關係：

```text
A --建立--> B
A --創立--> B
A --成立--> B
```

這些可能其實是同一類關係，但在圖資料庫裡會變成不同邊，造成查詢與多跳推理不穩定。

所以本專案採用受控關係類型，也就是 `rel_type` 必須落在預先定義的合法清單中。如果 LLM 產生不合法類型，系統應該拒絕、修正或退回一般關係，例如 `RELATED_TO`。

簡報講法：

> 三元組不是抽得越自由越好。自由抽取彈性高，但容易造成關係名稱混亂；受控詞彙彈性較低，但能提高語意一致性，讓圖遍歷更可靠。

### 3. 語意驗證：關係是否真的符合句意

通過格式檢查不代表一定正確，還要確認三元組是否符合原文。

原文：

```text
Neo4j 是一種圖資料庫，常用於儲存知識圖譜。
```

合理三元組：

```text
Neo4j --IS_A--> 圖資料庫
Neo4j --STORES/SUPPORTS--> 知識圖譜
```

不合理三元組：

```text
知識圖譜 --IS_A--> Neo4j
```

這種錯誤的欄位可能都完整，但方向錯了。因此驗證時要檢查：

- 主詞與受詞方向是否正確。
- 關係類型是否貼近原文動詞或語意。
- 三元組是否過度推論，超出原文可支持的範圍。
- 是否能回到原文句子找到依據。

### 4. 來源驗證：每個三元組都要能回到原始文件

可驗證的三元組必須能回答：

```text
這條關係從哪裡來？
```

因此每條關係應該保存：

- `source_doc_id`：來源文件。
- `source_svo_chunk_index`：來源 chunk。
- `source_sentence_start` / `source_sentence_end`：來源句子範圍。
- citation 或 evidence：支撐這條關係的原文證據。

這能避免系統只留下「看起來像事實」的關係，卻無法確認依據。

簡報講法：

> 三元組驗證的關鍵是 citation。只要每條邊都能回到原始句子，我們就能檢查它到底是文件真的有寫，還是模型抽取時產生的幻覺。

### 5. 去重驗證：相同事實是否被合併

如果不同 chunk 都提到同一件事，圖中不應該產生多條重複邊：

```text
文件 1：A --支援--> B
文件 2：A --支援--> B
文件 3：A --支援--> B
```

比較好的做法是合併成一條關係邊，並把來源 citation 累積起來：

```text
A --支援--> B
來源：文件 1、文件 2、文件 3
```

這樣可以降低圖譜雜訊，也能用多個來源提高可信度。

### 6. 關聯路徑驗證：三元組是否能串成合理推理鏈

單一三元組正確，不代表整條推理鏈一定正確。GraphRAG 的重點是多個三元組能不能形成合理路徑：

```text
A --影響--> B
B --導致--> C
所以查詢 A 與 C 的關係時，可以沿著 A -> B -> C 找到線索。
```

驗證方式包含：

- 從查詢中的核心實體出發，執行 1-hop 或 2-hop BFS。
- 檢查返回路徑是否都能追溯到來源。
- 檢查路徑是否能支撐最終答案。
- 與純向量 RAG 對照，看圖路徑是否提升多跳問題的正確率。

### 7. 人工與自動化混合驗證

實務上可以分三層驗證：

```text
第一層：程式規則
檢查欄位完整、關係類型合法、來源欄位存在。

第二層：語意相似度
把 LLM 自報的 rel_type 與關係描述 embedding 比對，確認語意是否一致。

第三層：LLM 或人工仲裁
當規則與相似度無法判斷，交給 LLM 或人工確認，並把仲裁結果記錄下來，作為後續校正依據。
```

這對應本專案目前的方向：SVO 抽取後會檢查 `rel_type` 是否在合法清單內；若提供 embedding provider，會執行 SIM/COMPARE/ESCALATE 類型的事後驗證；寫入 Neo4j 時則以 `(kg_id, subject, rel_type, object)` 做事實層級合併，並保存來源資訊。

### 9. 具體例子：三元組的特性與效果

#### 例子一：方向性

原文：

```text
GraphRAG 使用知識圖譜強化 RAG 的多跳推理能力。
```

正確三元組：

```text
GraphRAG --USES--> 知識圖譜
GraphRAG --ENHANCES--> RAG 的多跳推理能力
```

錯誤三元組：

```text
知識圖譜 --USES--> GraphRAG
```

效果說明：

> 三元組有方向性。如果方向錯，圖遍歷會走到錯誤路徑，最後答案也可能錯。

#### 例子二：關係類型一致性

原文可能出現不同說法：

```text
Neo4j 儲存知識圖譜。
Neo4j 支援知識圖譜資料管理。
Neo4j 可用來保存實體關係。
```

如果不做標準化，可能變成：

```text
Neo4j --儲存--> 知識圖譜
Neo4j --支援--> 知識圖譜資料管理
Neo4j --保存--> 實體關係
```

標準化後可以收斂成：

```text
Neo4j --SUPPORTS--> 知識圖譜
Neo4j --SUPPORTS--> 實體關係管理
```

效果說明：

> 關係類型一致，查詢才穩定。否則同一種語意會分散成多種邊，造成召回不完整。

#### 例子三：來源可追溯

三元組：

```text
ConceptNode --ROUTES_TO--> 相關知識庫
```

如果保存來源：

```text
source_doc_id = report-demo
source_sentence = 3
evidence = "ConceptNode 負責將使用者問題路由到相關知識庫。"
```

效果說明：

> 來源可追溯後，回答不是只有結論，還能回到哪一句支撐這條邊。這能降低幻覺，也方便人工檢查。

#### 例子四：多跳路徑

三元組：

```text
GraphRAG --USES--> 知識圖譜
知識圖譜 --REPRESENTS--> 三元組
三元組 --SUPPORTS--> 關係驗證
```

查詢：

```text
GraphRAG 為什麼需要三元組驗證？
```

圖遍歷路徑：

```text
GraphRAG -> 知識圖譜 -> 三元組 -> 關係驗證
```

效果說明：

> 這就是 GraphRAG 與純 RAG 的差異：純 RAG 是找相關段落，GraphRAG 可以把回答依據整理成一條可檢查的關係路徑。

### 題目二總結

驗證三元組關聯，不能只看是否抽出「主詞、關係、受詞」三個欄位；必須同時驗證格式、關係詞彙、語意方向、來源證據、事實去重與多跳路徑。只有當三元組能回到原文、能被一致查詢、能支撐答案時，它才是對知識圖譜有價值的關聯。

### 專案一句話定位

World Knowledge Graph RAG 是一套以論文研究為目標的 GraphRAG 系統實作，核心目標是驗證「SVO 知識圖譜 + KG-BFS 圖遍歷 + 多知識庫路由」是否能在多跳問答、可追溯性與查詢效率上補足當代 RAG 與 2024 GraphRAG 的不足。

### 研究背景

本研究的背景可以從三個層次說明：

1. **LLM 的限制**：大型語言模型本身有靜態知識、幻覺與推理路徑不透明的問題。
2. **RAG 的補強與邊界**：RAG 能把外部文件引入回答流程，但主要仍以文字 chunk 為檢索單位，對明確關係、多跳路徑與關係層級可追溯仍有不足。
3. **GraphRAG 的機會與缺陷**：GraphRAG 嘗試結合 RAG 與知識圖譜，但 2024 代表性架構仍有建圖成本高、LLM 建圖品質不穩、偏向全局摘要、Hub Node 路徑爆炸與評估困難等問題。

簡報講法：

> 因此我的研究不是單純做一個聊天系統，而是要驗證：當我們把文件轉成可追溯的三元組知識圖譜後，是否能讓 RAG 在多跳推理與可解釋性上更可靠。

### 研究缺口

依緒論脈絡，本專案主要承接以下缺口：

| 缺口 | 說明 | 對應專案方向 |
|------|------|--------------|
| 多跳推理不穩 | 當答案需要串接多個片段，純文字 RAG 容易漏掉中間證據或發生 retrieval drift。 | KG-BFS 圖遍歷 |
| 多知識庫可擴展性不足 | 多個 KG 並存時，若每次都查全部資料，延遲與成本會上升。 | ConceptNode 輕量路由 |
| 幻覺與來源不明 | LLM 回答可能流暢但缺乏明確依據。 | 自我精煉與來源回補 |
| 關係語意不一致 | 開放式抽取容易把相同語意寫成不同關係。 | 受控關係詞彙與 SVO 驗證 |
| 實體重複與指代問題 | 同一實體可能被不同名稱表示，造成節點分裂。 | 實體別名與指代消解 |
| Hub Node 路徑爆炸 | 高連結節點會讓 BFS 找到太多無關路徑。 | 向量引導剪枝 |

### 研究目標

本研究的目標不是泛稱「GraphRAG 比 RAG 好」，而是要界定它在特定任務上的成立條件：

```text
目標一：驗證 KG-BFS 在多跳推理任務上是否優於當代強化版 RAG。
目標二：驗證多知識庫場景下，輕量路由是否能降低延遲並維持準確率。
目標三：驗證自我精煉與來源回補是否能降低幻覺並提升可追溯性。
目標四：延伸評估三元組關係標準化、實體別名消解、時序更新與 Hub Node 剪枝。
```

簡報講法：

> 這個研究的重點不是宣稱 GraphRAG 全面勝過 RAG，而是找出它在哪些問題類型上真的有用、代價是什麼、哪些元件會影響結果。

## 建議簡報順序

### Slide 1：題目與動機

標題：為什麼需要知識圖譜 RAG

講法：

> 這一題真正要回答的是：既然 2026 年的 RAG 已經有混合檢索、重排序、Agentic RAG 與 Structured Planning，為什麼還需要知識圖譜？我的回答是：RAG 很適合找文本證據，但知識圖譜補的是明確關係、多跳路徑與可追溯結構。

### Slide 2：RAG 的優點與限制

重點：

- 優點：快速、彈性、可直接引用原文。
- 2026 強化：hybrid search、reranking、query decomposition、Agentic RAG、Structured Planning。
- 限制：檢索單位仍多是文字 chunk。
- 多跳問題容易出現 retrieval drift、噪音累積與路徑不透明。

### Slide 3：知識圖譜的價值與代價

重點：

- 實體變成節點。
- 關係變成邊。
- 答案可以沿圖查詢。
- 推理路徑可以被檢查。
- 來源可以追溯。
- 代價是建圖成本高、抽取錯誤會污染圖譜、schema 需要治理。

### Slide 4：GraphRAG 的整合

重點：

- RAG 提供文本證據。
- KG 提供關係結構。
- GraphRAG 把文字檢索、圖遍歷、社群摘要與 LLM 生成接在一起。
- 簡單問題可走文本，多跳關係可走圖，全局問題可走摘要。

### Slide 5：2024 GraphRAG 的缺陷

重點：

- 建圖與 community summary 成本高，冷啟動慢。
- LLM 建圖品質不穩，錯誤三元組會造成 retrieval drift。
- 原始架構偏向 global sensemaking，不等於精準三元組問答。
- 圖遍歷遇到 Hub Node 會有路徑爆炸。
- 評估困難，不能只看最後答案流暢度。

### Slide 6：什麼是三元組

重點：

```text
Subject --Relation--> Object
```

例子：

```text
Neo4j --儲存--> 知識圖譜
BFS --找出--> 關聯路徑
知識圖譜 --支援--> 多跳推理
```

### Slide 7：三元組驗證的文獻依據

重點：

- OpenIE 證明三元組是資訊抽取的標準形式。
- Text2KGBench 證明 ontology-driven KG generation 需要 benchmark。
- CORE-KG / CoDe-KG 證明 coreference、sentence decomposition、去重會影響 KG 品質。
- Robust GraphRAG 證明錯誤 KG 會造成 retrieval drift 與 hallucination。

### Slide 8：三元組如何驗證

重點：

- 結構完整。
- 關係類型合法。
- 語意方向正確。
- 可回到原文來源。
- 相同事實可合併去重。
- 多個三元組能形成合理路徑。

### Slide 9：簡化成果比較

重點：

- 準備 5 到 8 句 micro-benchmark。
- 人工標出 gold triples。
- 比較純 RAG、未驗證 SVO、驗證後 SVO。
- 指標：Precision、Recall、F1、Traceability。

### Slide 10：具體例子

重點：

- 方向性：`GraphRAG --USES--> 知識圖譜` 不能反過來。
- 關係一致性：`儲存/支援/保存` 需要收斂成可查詢的關係類型。
- 來源追溯：每條邊要能回到原文句子。
- 多跳路徑：`GraphRAG -> 知識圖譜 -> 三元組 -> 關係驗證`。

## 口頭報告用短版稿

我會先回答為什麼要用知識圖譜。這一題隱含的問題其實是：既然 2026 年的 RAG 已經有混合檢索、重排序、查詢拆解、Agentic RAG 與 Structured Planning，為什麼不用 RAG 就好？我的回答不是否定 RAG。RAG 的優點是快速、彈性、可以直接引用原文；但它的主要檢索單位仍然多是文字片段。當問題需要知道「誰和誰有什麼關係」，或需要跨文件串接多個事實時，RAG 可能會遇到 retrieval drift、噪音累積與推理路徑不透明的問題。

知識圖譜補上的，是把文字中的知識整理成實體與關係，也就是節點與邊。這讓系統不只找相似文字，也能沿著明確關係查詢。GraphRAG 的意義就是整合兩邊：保留 RAG 的文本證據能力，同時利用知識圖譜做關係檢索與多跳推理。不過 2024 版 GraphRAG 也有重大缺陷，例如建圖成本高、LLM 抽圖品質不穩、偏向全局摘要、不一定適合精準三元組問答，以及圖遍歷可能遇到 Hub Node 路徑爆炸。因此後續專案要鋪陳的重點，就是如何讓圖裡的關係更可信。

接著是三元組關聯如何驗證。三元組指的是 Subject、Relation、Object，例如「Neo4j 儲存 知識圖譜」。這不是我自己定義的格式，OpenIE 早就把 relation triple 作為資訊抽取的基本形式；Text2KGBench 也把從文本依 ontology 產生 KG 當成需要 benchmark 的任務。近年的 CORE-KG、CoDe-KG 與 Robust GraphRAG 更進一步指出，如果沒有處理指代、句子拆解、去重與錯誤三元組，知識圖譜會變得破碎、有噪音，甚至讓 GraphRAG 沿著錯誤邊檢索。

所以驗證三元組不能只看有沒有抽出三個欄位，還要看主詞和受詞方向是否正確、關係類型是否合法、語意是否符合原文、是否能追溯到來源句子，以及相同事實是否能合併去重。為了快速證明這點，我會準備一個簡化 micro-benchmark：用 5 到 8 句文本人工標出 gold triples，比較純 RAG、未驗證 SVO、驗證後 SVO，在 Precision、Recall、F1 與 Traceability 上的差異。這個小成果不代表完整實驗，但可以先展示三元組驗證確實會影響圖譜品質。

在這兩個前提下，我的專案 World Knowledge Graph RAG 就是這篇論文的實作載體。它不是只做一個聊天 demo，而是用來回答幾個研究問題：第一，KG-BFS 在多跳推理上是否真的比當代強化版 RAG 有優勢；第二，多知識庫場景下，ConceptNode 路由是否能降低查詢延遲並維持準確率；第三，自我精煉與原文回補是否能降低幻覺並提升可追溯性。延伸來看，三元組關係標準化、實體別名消解、時序事實管理與 Hub Node 剪枝，則是後續要驗證的圖譜品質與效率問題。專案目前是 v2 重構階段，後端、前端與資料層骨架已建立，重點是把研究問題落到可實驗、可比較、可追溯的系統架構上。

## 簡報可引用資料來源

- [Edge et al. (2024/2025), *From Local to Global: A Graph RAG Approach to Query-Focused Summarization*](https://doi.org/10.48550/arXiv.2404.16130)：Microsoft GraphRAG 原始代表性論文，說明 RAG 對全局問題的不足，以及以 entity graph、community detection、community summaries 處理 global sensemaking 的方法。
- [Peng et al. (2026), *Graph Retrieval-Augmented Generation: A Survey*](https://doi.org/10.1145/3777378)：整理 GraphRAG 與 text-based RAG 的差異，並指出 GraphRAG 在候選子圖爆炸、圖檢索相似度、評估與大規模圖延遲上的挑戰。
- [Huang et al. (2026), *Retrieval-Augmented Generation for Multi-Hop Question Answering Based on Structured Planning*](https://doi.org/10.1145/3789506)：說明多跳 RAG 中 iterative retrieval 可能出現 retrieval drift 與噪音累積，並以 structured planning 降低問題。
- [Ma et al. (2026), *Toward Robust GraphRAG: Mitigating Retrieval Drift and Hallucination from Imperfect Knowledge Graphs*](https://arxiv.org/abs/2603.14828)：指出 LLM 建圖可能有 spurious noise 與 incomplete information，會導致 GraphRAG 沿錯誤或不足的圖結構繼續檢索。
- [Angeli et al. (2015), *Leveraging Linguistic Structure For Open Domain Information Extraction*](https://aclanthology.org/P15-1034/)：Stanford OpenIE 代表性論文，支撐從句子抽取 relation triples 的基礎做法。
- [Mihindukulasooriya et al. (2023), *Text2KGBench: A Benchmark for Ontology-Driven Knowledge Graph Generation from Text*](https://arxiv.org/abs/2308.02357)：支撐 ontology-guided KG generation 需要以 benchmark 與 metrics 評估。
- [Meher et al. (2025), *CORE-KG: An LLM-Driven Knowledge Graph Construction Framework for Human Smuggling Networks*](https://arxiv.org/abs/2506.21607)：指出 LLM 建圖中的 hallucination、duplicate nodes 與 noisy graph 問題，並以 coreference resolution 與 domain-guided extraction 降低噪音。
- [Anuyah et al. (2025), *Automated Knowledge Graph Construction using Large Language Models and Sentence Complexity Modelling*](https://aclanthology.org/2025.emnlp-main.783/)：支撐句子級 KG、coreference resolution 與 sentence decomposition 對關係抽取品質的影響。
