# 簡報參考：知識圖譜與三元組關聯驗證

> 使用順序提醒：報告時先完成「為什麼要用知識圖譜」與「如何驗證三元組關聯」兩個回答，再開始介紹本專案。這樣聽眾會先理解問題意義，再理解專案為什麼這樣設計。

## 題目一：為什麼要用知識圖譜

### 先說清楚隱含問題

這一題真正要回答的不是「知識圖譜比較好」，而是：

```text
既然 2026 年的 RAG 已經很成熟，為什麼還需要知識圖譜？
RAG 和知識圖譜到底是在解決同一個問題，還是不同層次的問題？
```

目前建議的回答主軸：

```text
RAG：查詢時過濾文字證據。
KG：事前提煉關係知識。
GraphRAG：在提煉後的關係上檢索，再回原文驗證。
```

所以報告時不要一開始就說「知識圖譜很強」。比較好的順序是：

```text
先用 NotebookLM 作為共同經驗入口
-> 抽象出 RAG 的核心流程
-> 說明 2026 RAG 的改良其實在修補哪些 failure modes
-> 說明知識圖譜的核心流程
-> 說明 2026 版知識圖譜如何改良傳統建圖問題
-> 比較 RAG 與知識圖譜的差異
-> 說明 GraphRAG 如何結合兩者
-> 說明 GraphRAG 的不足
-> 證明 SVO 關聯性為什麼重要
-> 說明本專案將如何改良
```

報告時的定位句：

> 我的主張不是 RAG 不好，也不是 KG 取代 RAG。RAG 解決的是「我要參考哪些內容」；知識圖譜解決的是「內容中的關係如何被提煉、整理與重複使用」。兩者不衝突，KG 反而可以改變 RAG 的檢索單位，讓系統從原始文字檢索提升到事實與關係檢索。

### 1. 先用 NotebookLM 理解 RAG，但不宣稱其內部實作

NotebookLM 可以作為共同經驗入口，因為多數聽眾知道它的使用方式：使用者放入來源資料，系統根據來源回答並提供引用。

但報告時要先講清楚限制：

> 我用 NotebookLM 不是要介紹產品功能，也不是宣稱 Google 內部一定用了哪一種 chunking、embedding、reranker 或 routing。Google 沒有公開完整 pipeline，所以我只把 NotebookLM 當成 source-grounded RAG 的共同經驗入口。

可以抽象成：

```text
資料來源
  ↓
檢索相關證據
  ↓
語言模型根據證據生成回答
  ↓
回答並附來源引用
```

### 2. RAG 的核心流程

RAG 的核心原理，是把 LLM 的參數記憶接上一個外部、可更新、可檢索的非參數記憶。它不是讓模型只憑訓練時記住的知識回答，而是在生成答案之前，先從外部資料庫找出可能支撐答案的 evidence。

完整流程可以用中文講成：

```text
原始資料
  ↓
資料解析與切分
  ↓
建立可搜尋索引
  ↓
使用者提問
  ↓
檢索相關證據
  ↓
整理成模型可讀的上下文
  ↓
語言模型根據證據生成回答
  ↓
回答並附上來源引用
```

簡報講法：

> RAG 不是讓模型直接回答，而是先幫模型查資料。查到資料後，再把資料交給模型整理成答案。它的核心不是生成本身，而是「檢索控制」：資料怎麼切、索引怎麼建、問題怎麼轉成檢索、證據怎麼排序、上下文怎麼組合，這些都會影響最後答案。

### 3. 2026 版 RAG 的改良原理與不足

2026 年的 RAG 已經不是簡單的「向量搜尋 + LLM」。它的改良大多是在修補檢索流程中的不同失敗點。

#### 3.1 語意搜尋漏掉精確詞

問題：

> 單純向量搜尋擅長找意思接近的內容，但有時會漏掉精確詞、專有名詞、型號、法條、公司名稱、人名或特定術語。

改善原理：

> 現代 RAG 常把語意搜尋和關鍵字搜尋混合使用。語意搜尋負責找意思相近的內容，關鍵字搜尋負責找字面精確匹配的內容，metadata 則限制搜尋範圍，例如年份、文件類型、部門、作者、權限或知識庫 ID。

例子：

```text
問題：勞動基準法第 24 條加班費怎麼算？

語意搜尋：找「加班」「薪資」「工資加給」相關段落。
關鍵字搜尋：精確命中「第 24 條」。
metadata filter：限制在「法規」「勞動基準法」「現行版本」。
```

仍然不足：

> 這只能提高找到相關文字的機率，但不保證系統知道「第 24 條」和「加班費」之間是規定、例外、修正、廢止還是適用條件。也就是說，RAG 可以縮小搜尋範圍，但沒有自然形成可查詢的關係結構。

#### 3.2 初始搜尋結果排序不準

問題：

> 檢索器通常會先找出一批候選片段，但第一批結果不一定排序正確。最能支撐答案的證據可能排在第 20 名，而不是前 5 名。

改善原理：

```text
第一階段：先多找，召回一批候選片段。
第二階段：再細選，用更精細的模型重新排序。
```

仍然不足：

> 重排序評估的是片段和問題的相關性，但相關不等於正確支撐。某段文字可能提到 A 和 B，但它是在否定兩者關係，或只是背景敘述，並不真正支持答案。

#### 3.3 問題太複雜，一次查不到

問題：

> 很多問題不是單一查詢可以回答的。它需要拆成多個子問題，每個子問題找到不同證據，最後再合成答案。

改善原理：

```text
複雜問題
  ↓
拆成多個子問題
  ↓
分別檢索
  ↓
合併證據
  ↓
生成回答
```

仍然不足：

> 拆問題可以改善檢索覆蓋率，但每一步檢索仍可能偏移。第一步如果找錯資料，後面會沿著錯誤方向繼續查，形成 retrieval drift。更重要的是，RAG 拆的是問題，不一定建出明確的關係路徑。

#### 3.4 多資料源不知道去哪查

問題：

> 現代系統可能有很多資料源：法規庫、論文庫、技術文件庫、公司內部文件、客服紀錄、產品文件。使用者問一句話時，系統要先判斷該去哪裡查。

改善原理：

> 路由式 RAG 會先判斷問題屬於哪個資料源、哪個索引或哪個檢索器，再執行檢索。這可以避免每次都查全部資料，降低延遲，也減少無關資料進入上下文。

仍然不足：

> 路由解決的是去哪個資料庫查，但不一定解決查到的資料內部關係是否正確。即使路由到正確知識庫，仍可能只拿到相關文字片段，而不是可驗證的關係結構。

#### 3.5 一次檢索不夠

問題：

> 傳統 RAG 常是在回答前檢索一次，然後就把找到的內容交給模型生成。但長答案或多步推理中，模型可能生成到一半才發現缺資料。

改善原理：

```text
傳統 RAG：先查一次 -> 回答
主動式 RAG：先查 -> 回答一部分 -> 發現不確定 -> 再查 -> 修正回答
```

仍然不足：

> 這改善了補證據能力，但也增加成本、延遲與錯誤累積風險。每次補查都可能引入新噪音。如果系統沒有結構化地管理證據，最後答案可能混入多個來源，但推理鏈仍不透明。

#### 3.6 找到的證據可能不相關

問題：

> RAG 最大問題之一是：檢索器找到的片段看起來相關，但其實不能支撐答案。模型可能仍然把它拿來生成，甚至產生看似有引用、但引用不真正支持結論的回答。

改善原理：

> 自我檢查式 RAG 會讓模型判斷是否需要檢索、檢索到的證據是否相關、生成內容是否被證據支持。這比傳統 RAG 多了一層證據使用前後的檢查。

仍然不足：

> 這種檢查通常仍是語言模型判斷，容易受 prompt、模型能力與上下文噪音影響。它可以提高可靠性，但不等於建立了可查詢、可重複驗證的關係資料結構。

#### 3.7 切塊粒度影響結果

問題：

> RAG 通常把文件切成 chunk。chunk 太大，會混入很多無關資訊；chunk 太小，又可能失去上下文。切塊方式會直接影響檢索與回答品質。

改善原理：

> 細粒度檢索的想法是：不要只用大段文字，而是把資料切成更接近單一事實的單位，例如命題、句子或原子事實。這樣檢索器找到的內容更精準，放進上下文時也比較少噪音。

仍然不足：

> 細粒度事實仍然多半是文字單位。它比 chunk 更精準，但還不一定是正式的結構化關係。它可能沒有標準 relation type，也不一定處理實體別名、方向、時間條件與去重。

### 4. 知識圖譜的核心流程

如果前面說 RAG 的核心流程是「查詢時過濾文字證據」，那知識圖譜的核心流程就是「事前提煉關係知識」。它不是等使用者提問時才讓 LLM 從一堆文字裡臨時理解關係，而是在資料進入系統時，就先把重要實體、關係、來源與重複事實整理出來。

可以用中文流程說成：

```text
原始資料
  ↓
資料解析與句子/段落切分
  ↓
抽取實體
  ↓
抽取實體之間的關係
  ↓
形成三元組
主詞 --關係--> 受詞
  ↓
實體對齊與別名合併
  ↓
相同事實去重與來源累積
  ↓
建立可查詢的節點、邊與路徑
  ↓
查詢時沿著關係找答案，再回原文補證據
```

所以兩者的差異不是「誰比較聰明」，而是處理資訊的時間點與知識單位不同：

```text
RAG：
查詢時才從大量文字中篩選相關片段。
回傳單位主要是 chunk、句子或命題文字。
讓 LLM 在上下文裡臨時理解關係。

知識圖譜：
事前抽取與整理。
回傳單位主要是實體、關係、三元組與路徑。
讓 LLM 根據已結構化的關係回答，再回原文補充細節。
```

這裡要避免把 RAG 說成「低資訊量」。比較精準的說法是：

> RAG 回傳的文字片段可能包含很多資訊，但結構鬆散；知識圖譜回傳的三元組或路徑內容較精簡，但語意結構更明確。

口語比喻：

> RAG 像是從散落的文字證據中找相關片段，再請 LLM 判斷這些片段能不能拼成答案。知識圖譜則是先把重要資訊整理成一串串關係鏈，查詢時不是只找相似文字，而是沿著實體和關係去走路徑。

### 5. 2026 版知識圖譜的改良

傳統知識圖譜的問題，是建置成本高、schema 設計重、需要大量人工維護。2026 年討論的重點，不是回到完全人工建圖，而是把 LLM、embedding、去重、來源追溯與增量治理接進知識圖譜流程，讓知識圖譜比較接近可持續運行的系統。

可以先從基本表示說起：

```text
實體 A --關係--> 實體 B
```

例如：

```text
Neo4j --儲存--> 知識圖譜
知識圖譜 --支援--> 多跳推理
ConceptNode --負責--> 知識庫路由
BFS 圖遍歷 --找出--> 關聯路徑
```

2026 版知識圖譜的改良，可以整理成七個方向。這裡要和前面 RAG 的說法對齊：每一項都不是單純名詞，而是在修補傳統 KG 的某個失敗點。

#### 5.1 LLM 輔助抽取：降低人工建圖成本

傳統問題：

> 早期知識圖譜常需要人工定義 schema、人工標註實體與關係，成本很高，也很難快速套到新領域。

改善原理：

> LLM 可以從文件中初步抽取實體、關係與三元組，讓系統先自動產生候選圖譜，再由規則、詞彙表、來源驗證或人工審核把關。這讓知識圖譜不再完全依賴人工建置。

仍然不足：

> LLM 抽取不是保證正確。它可能產生看似合理但原文不支持的關係，也可能漏掉中間關係、接錯實體或反轉方向。所以 LLM 輔助抽取只能降低建圖門檻，不能取代後續驗證。

#### 5.2 受控關係詞彙：降低關係類型混亂

傳統問題：

> 如果關係完全開放，LLM 可能把相近語意抽成很多不同詞，例如「使用」「採用」「依賴」「支援」「基於」。這些詞看起來都合理，但查詢時會變得很難統一。

改善原理：

> 受控關係詞彙會先定義一組合法 relation types，再把原文動詞對齊到標準關係類型。這讓圖譜中的邊比較一致，可以被穩定查詢與統計。

例子：

```text
原文動詞：使用、採用、利用
標準關係：USED_FOR 或 USES
```

仍然不足：

> 關係詞彙太少會壓扁語意，太多又會造成治理困難。若 LLM 把原文關係歸錯類，即使格式合法，圖譜仍然會錯。因此受控詞彙還需要語意驗證與來源驗證。

#### 5.3 實體對齊與別名合併：避免節點碎片化

傳統問題：

> 同一個實體可能在不同文件中有多種寫法，例如「勞基法」「勞動基準法」「Labor Standards Act」。如果不合併，圖譜會把同一個東西拆成多個節點，導致關係分散。

改善原理：

> 現代 KG 會做實體對齊、別名登記與去重。可以先用字串規則、編輯距離、embedding 相似度找候選，再用 LLM 或人工在灰色地帶仲裁。

仍然不足：

> 實體對齊不能只靠名字相似。兩個名稱很像不一定是同一實體，兩個名稱差很多也可能是同一實體。錯誤合併會比不合併更危險，因為它會把不同實體的關係混在一起。

#### 5.4 來源追溯：讓每條邊能回到原文

傳統問題：

> 很多圖譜只保存節點與邊，卻沒有保存這條關係來自哪份文件、哪個段落、哪句話。這會讓圖譜看起來結構化，但無法查證。

改善原理：

> 現代 KG / GraphRAG 需要在每條邊上保留來源資訊，例如文件 ID、chunk index、句子範圍、原文 citation、抽取信心值與時間資訊。這讓關係不只是圖上的一條邊，而是可以回到原文驗證的事實候選。

仍然不足：

> 有 citation 仍不等於關係成立。來源句可能只是提到兩個實體，並沒有支持該關係；也可能有否定、條件、時間限制。因此來源追溯是必要條件，但還不是充分條件。

#### 5.5 增量更新與回溯治理：避免靜態圖過時

傳統問題：

> 傳統 KG 常像一次性建好的資料庫。新文件加入、關係詞彙改變、實體別名更新時，如果每次都重建整張圖，成本太高；如果不更新，圖譜又會過時。

改善原理：

> 改良方向是增量抽取、任務佇列、斷點續傳與回溯重分類。新資料進來時只處理新增部分；關係類型或實體標準名更新時，只回頭處理受影響的候選資料。

仍然不足：

> 增量更新會帶來一致性問題。新規則套用到新資料，但舊資料是否也要回補？回補到什麼程度？什麼時候需要人工審核？這些都需要治理機制，不是單純多跑一次抽取。

#### 5.6 圖遍歷控制：避免路徑爆炸與 Hub Node

傳統問題：

> 圖譜一大，某些節點會連到非常多關係，例如「AI」「公司」「法規」「系統」。如果查詢時無限制遍歷，會帶出大量無關路徑。

改善原理：

> 現代 GraphRAG 會使用 bounded BFS、路徑長度限制、關係類型過濾、Hub Node 剪枝、查詢引導的路徑排序，避免把整張圖丟給 LLM。

仍然不足：

> 剪枝太強會漏掉真正需要的中介節點，剪枝太弱又會讓噪音進入上下文。圖遍歷控制本質上是在召回率、精確率、延遲之間取捨。

#### 5.7 向量與圖結合：補足純符號查詢太硬的問題

傳統問題：

> 純知識圖譜查詢通常需要精確知道實體名稱、關係類型或 Cypher/SPARQL 查詢方式。一般使用者的自然語言問題，未必能直接對到圖中的節點和邊。

改善原理：

> 2026 版 KG / GraphRAG 常會把向量檢索接進圖譜：節點描述、關係描述、三元組文字化、路徑摘要或 ConceptNode 都可以向量化。查詢時先用語意相似度找到候選，再沿圖做結構擴展。

仍然不足：

> 向量只能提供候選相似性，不能直接證明關係成立。因此向量適合做召回與排序，最後仍要回到三元組、來源句與關係驗證。

簡報講法：

> 現代知識圖譜不是回到傳統完全人工建圖，而是用 LLM 輔助提煉，再用受控詞彙、實體對齊、來源追溯、增量治理與圖遍歷控制把關。重點不是把文字變成漂亮的圖，而是把關係變成可查詢、可驗證、可重複使用的知識單位。

但知識圖譜也有明顯代價：

- 建圖成本高，需要抽取實體與關係。
- 抽取錯誤會污染圖譜。
- schema 設計太死會降低召回，太自由又會造成關係混亂。
- 圖太大時，遍歷會遇到高連結節點與路徑爆炸。
- 對一般摘要或開放式探索問題，不一定比 RAG 划算。

### 6. 比較：RAG 與知識圖譜的差異

RAG 和知識圖譜不是同一層的技術。RAG 的核心是「查詢時過濾文字證據」；知識圖譜的核心是「事前提煉關係知識」。

```text
RAG：從大量文字中篩選證據。
KG：從大量文字中提煉關係。
GraphRAG：在提煉後的關係上檢索，再回原文驗證。
```

| 面向 | RAG | 知識圖譜 |
|------|-----|----------|
| 處理時機 | 查詢時檢索 | 事前建圖與整理 |
| 主要單位 | chunk、句子、命題文字 | 實體、關係、三元組、路徑 |
| 強項 | 快速導入、摘要、問答、找相關段落 | 關係查詢、多跳推理、來源追溯、長期治理 |
| LLM 負擔 | 需要從文字中臨時理解關係 | 可直接使用已結構化關係 |
| 成本 | 建置較快，但查詢時可能要多輪檢索 | 建圖較慢，但關係可重複使用 |
| 風險 | 找到相關文字，但不一定支撐答案 | 抽錯關係會污染圖譜 |

簡報講法：

> 如果只是想快速了解一批資料大概在說什麼，RAG 很划算；如果重點是「誰和誰有什麼關係」「這條關係從哪裡來」「能不能串成推理路徑」，知識圖譜更有價值。所以兩者不是衝突，而是面對不同粒度的任務。

### 7. GraphRAG 如何結合 RAG 與知識圖譜

GraphRAG 的核心想法不是丟掉 RAG，而是改變 RAG 的檢索對象。

原始 RAG 多半是：

```text
query -> 找 chunk -> LLM 閱讀 chunk -> 回答
```

GraphRAG 可以變成：

```text
query -> 找 KG / ConceptNode -> 找相關 fact / triple / path
      -> 沿圖擴展
      -> 回原文補 citation
      -> LLM 回答
```

它整合了兩邊的優勢：

| 能力 | RAG 提供 | 知識圖譜提供 | GraphRAG 的整合方式 |
|------|----------|--------------|----------------------|
| 快速引用原文 | 可以直接取回 chunk | 可記錄每條關係來源 | 回答同時使用文字證據與圖上關係 |
| 語意搜尋 | embedding 找相似內容 | 實體、關係、三元組、路徑都可向量化 | 先語意召回，再沿圖擴展 |
| 多跳推理 | 可透過 agent 多輪查詢 | 可用 BFS/路徑查詢明確走圖 | 把推理變成可檢查的路徑 |
| 全局理解 | 摘要大量文本有成本 | 可做社群/群集摘要 | 對整個語料產生 global summary |
| 可追溯性 | 引用 chunk | 引用節點、邊、來源句 | 回答可附來源與關係鏈 |

簡報講法：

> GraphRAG 不是把 RAG 丟掉，而是把 RAG 的文本檢索能力，和知識圖譜的關係推理能力接在一起。使用者問簡單問題時可以走文本；問多跳關係時可以走圖；問全局主題時可以走社群摘要。

### 8. GraphRAG 的不足

2024 年 Microsoft GraphRAG 的代表性做法，是用 LLM 從文本抽取 entity/relationship，建立知識圖譜，再做 community detection，並為每個社群預先產生摘要。這個設計成功補強了傳統 RAG 對「全局問題」的不足，但也留下幾個重大缺陷，正好可以為本專案鋪墊。

#### 缺陷一：建圖成本太高，冷啟動慢

2024 GraphRAG 需要：

```text
文件切塊
-> LLM 抽取實體與關係
-> 建立圖
-> community detection
-> LLM 產生 community summaries
-> 查詢時再彙整回答
```

這代表它在查詢前就要付出大量前處理成本。對百萬 token 等級資料可以接受，但如果使用者希望「上傳後馬上可問」，全量建圖與摘要會變成明顯瓶頸。

本專案鋪墊：

> 因此本專案後續採用「向量先行、SVO 非同步建圖」的思路，讓系統先可用，再逐步補上圖譜能力。

#### 缺陷二：LLM 建圖品質不穩，錯誤會變成檢索路徑

GraphRAG 的前提是：LLM 抽出的知識圖譜足夠可靠。但 2026 年的研究已指出，這個前提在實務上不一定成立。LLM 建圖可能出現：

- spurious noise：看起來合理但原文不支撐的錯誤三元組。
- incomplete information：缺少中間橋接邊，導致多跳路徑斷裂。
- over-generalized relation：關係過度泛化。
- mis-bound relation：關係接到錯誤實體。
- semantic flip：主詞與受詞方向顛倒。
- dropped qualifier：時間、地點、條件等限定資訊被漏掉。

一旦錯誤三元組進入圖中，GraphRAG 不是單純「找錯片段」，而是可能沿著錯誤邊繼續擴展，造成 retrieval drift 或 hallucinated structural continuation。

本專案鋪墊：

> 因此本專案不能只說「我們有知識圖譜」，還必須處理三元組驗證、關係類型標準化、來源追溯與事實去重。

#### 缺陷三：2024 GraphRAG 偏向全局摘要，不等於精準三元組問答

Microsoft GraphRAG 原始論文主要強調 global sensemaking，也就是回答「整份資料的主題是什麼」、「有哪些主要觀點」這類全局問題。它對全局摘要很有價值，但本專案的目標更偏向：

- 精準查某個實體與另一個實體的關係。
- 查一條關係是從哪份文件、哪個 chunk、哪句話來的。
- 讓多跳推理路徑可以被檢查。
- 在多知識庫場景中先路由，再遍歷。

因此本專案不能只複製 2024 GraphRAG 的 community summary 架構，而需要更重視 SVO 邊的品質與來源。

#### 缺陷四：圖遍歷會遇到路徑爆炸與 Hub Node 問題

知識圖譜越大，從一個節點出發能走到的鄰居越多。像「AI」、「公司」、「年份」、「台灣」這類高連結節點，可能連到大量無關資訊。若 BFS 沒有良好剪枝，會造成：

- 候選子圖爆炸。
- 查詢延遲上升。
- 無關路徑進入 context。
- LLM 被噪音干擾。

本專案鋪墊：

> 所以本專案設計 ConceptNode 路由與 bounded BFS，不是單純把整張圖丟給 LLM，而是控制檢索範圍與路徑品質。

#### 缺陷五：評估困難，不能只看答案像不像

GraphRAG 的輸出常是摘要或開放式回答，評估不容易。只用 LLM-as-a-judge 會有偏差；只看最終答案，也看不出是檢索錯、建圖錯、路徑錯，還是生成錯。

本專案鋪墊：

> 因此後續實驗需要同時看答案正確率、可追溯性、三元組品質、關係路徑是否支撐答案，而不是只看回答流不流暢。

### 9. 本報告要證明：SVO 的關聯性是否可信

GraphRAG 的核心資料結構不是漂亮的圖形介面，而是圖裡每一條可被查詢的關係。這些關係最基本的單位就是三元組：

```text
Subject --Relation--> Object
主詞 --關係--> 受詞
```

也就是本專案的 SVO：

```text
Subject + Verb/Relation + Object
```

因此第一題最後要收束到：

> 我們需要知識圖譜，不是為了多一個視覺化圖，而是為了讓 RAG 不只檢索文字，也能檢索可驗證的關係。這些關係是否可靠，取決於三元組是否抽得正確、關係類型是否一致、來源是否可追溯。

本報告接下來要證明的不是「有抽出 SVO 就成功」，而是：

```text
SVO 是否完整？
關係類型是否受控？
主詞與受詞方向是否正確？
語意是否真的被原文支持？
來源是否能回到文件、chunk 與句子？
相同事實是否能合併？
多個三元組是否能形成合理推理鏈？
```

這就進入第二題：如何驗證三元組的關聯？

### 10. 本專案將如何改良

本專案的改良方向，不是宣稱單靠知識圖譜就能解決所有 RAG 問題，而是把 RAG 的文字證據能力與知識圖譜的關係治理能力分層整合。

目前已經先切出一個子項目完成第一版驗證閉環，不需要一次完成整套 GraphRAG。這個子項目定義為：

```text
子項目：SVO 關聯性驗證最小閉環
目標：證明抽出的三元組不是只有格式正確，而是關係真的被原文支持。
範圍：小型資料集、示範用 gold triples、三種版本比較、來源追溯與基本指標。
位置：experiments/svo_feasibility/
```

這樣範圍比較可控，也能直接對應本報告第 9 點「SVO 的關聯性是否可信」。這個資料夾不是主系統的功能測試，而是專門拿來證明給大家看：如果把文字提煉成 SVO 三元組，是否能用標準答案與來源句追溯來檢查關係正確性。

這裡要避免過度宣稱：目前 `gold_triples.json` 是示範用標準答案，也就是研究者先根據 4 句樣本文本制定「應該抽到哪些三元組」。它不是正式大規模人工標註資料集。正式論文實驗時，才會把更多文本交給人工標註或審核，形成正式 gold triples。

目前子項目已包含：

```text
dataset.json              小型文本資料集
gold_triples.json         示範用標準三元組與來源句
sample_predictions.json   pure RAG proxy、未驗證 SVO、驗證後 SVO 三種比較輸出
evaluator.py              Precision / Recall / F1 / Traceability 評估程式
test_evaluator.py         驗證評估邏輯的 pytest 測試
```

目前示範結果：

```text
SVO 關聯性可行性驗證
目標：檢查三元組是否正確，且是否能回到支持它的來源句。

system           precision  recall  f1    trace  tp  fp  fn  verdict
---------------  ---------  ------  ----  -----  --  --  --  ------------------------
pure_rag_proxy        0.00    0.00  0.00   0.00   0   0   4  NO_TRIPLES: 無法做關係層驗證
unverified_svo        0.67    0.50  0.57   0.50   2   1   2  PARTIAL: 有錯誤或來源不足
verified_svo          1.00    1.00  1.00   1.00   4   0   0  PASS: 關係正確且可追溯

結論：verified_svo 的 F1 與 Traceability 最高。
解讀：只回傳文字無法直接證明關係；未驗證 SVO 會混入錯誤；驗證後 SVO 才能把關係與來源一起檢查。
```

現場可重跑指令：

```bash
python -m experiments.svo_feasibility.evaluator
```

如果需要先證明整個專案測試狀態是乾淨的，可以先跑：

```bash
python -m pytest
```

目前完整測試結果：

```text
407 passed
```

比較適合現場的操作順序：

```text
1. 先展示已跑出的結果表。
2. 如果被要求現場證明，再執行 python -m experiments.svo_feasibility.evaluator。
3. 如果被質疑這只是獨立 demo，再執行 python -m pytest，證明它已被納入 repo 測試範圍。
```

這裡的重點不是說真實系統已經達到 1.00，而是建立一個可檢查的實驗格式：主系統未來輸出的 SVO 只要轉成同樣格式，就能被同一個 evaluator 評估。

更精準地說，這個子項目目前證明的是「SVO 關係驗證機制可行」，不是證明整套抽取系統已經在大量資料上穩定。我的立場應該是：

```text
驗證通過，才承認此抽取結果。
沒有通過驗證的三元組，只能視為候選關係，不應直接寫入可信知識圖譜。
```

因此這個 demo 的意義分成三層：

```text
第一層：可行性
證明 SVO 關係可以被檢查，不是 LLM 抽出 JSON 就算完成。

第二層：可信性
只有通過三元組比對與來源追溯的結果，才被承認為可信關係。

第三層：穩定性
目前 demo 還不能保證大量文件、複雜句型、不同領域下都穩定。
下一步任務是擴大資料集、加入更多錯誤類型、接上主系統真實輸出，
用同一套 evaluator 持續提高抽取品質與驗證穩定性。
```

```text
文字層：
保留原文 chunk、句子範圍與 citation，回答時可回原文補證據。

關係層：
抽取 SVO 三元組，將主詞、關係、受詞寫入 Neo4j。

驗證層：
檢查結構完整、關係類型合法、語意方向正確、來源可追溯。

治理層：
做實體別名合併、相同事實去重、關係類型擴充審核。

檢索層：
用 ConceptNode 路由選擇知識庫，再用 bounded BFS 控制圖遍歷範圍。
```

簡報講法：

> 本專案要改良的重點，是不要讓 GraphRAG 只停留在「LLM 抽圖後拿去檢索」。我已經先拉出一個獨立子項目：SVO 關聯性驗證最小閉環。它用小型資料集、示範用 gold triples、三種版本比較與 traceability 指標，先證明三元組的結構、語意與來源可以被檢查。這份 gold triples 目前是研究者根據樣本文本制定的標準答案，正式實驗才會擴大成人工標註資料集。這個 demo 證明的是「可以驗證」，不是「已經穩定」；驗證通過的三元組才被承認，未通過的三元組只能當候選關係。之後主系統輸出的 SVO 會接到同一套 evaluator，再逐步擴大資料與錯誤類型，提高抽取品質與驗證穩定性。

### 題目一總結

2026 年的 RAG 仍然是非常重要的基礎技術，優點是快速、彈性、能直接引用原文，並且可以透過混合檢索、重排序、查詢拆解、路由與自我檢查等方式改善檢索品質。2026 版知識圖譜則透過 LLM 輔助抽取、關係詞彙治理、實體對齊、來源追溯與增量更新，降低傳統建圖成本。兩者差異在於：RAG 偏向查詢時過濾文字證據，知識圖譜偏向事前提煉關係知識。GraphRAG 的價值就是把兩者接起來，但如果圖裡的邊不可信，GraphRAG 反而會放大錯誤。因此後續重點會回到 SVO 三元組：如何證明關係可信，並說明本專案如何用 SVO 驗證、來源追溯、去重治理與 bounded BFS 改良 GraphRAG 的可靠性。

## 題目二：驗證三元組的關聯

### 先釐清「三元性」

報告時建議把「三元性」說成「三元組關係」，也就是：

```text
Subject --Predicate/Relation--> Object
主詞 --關係--> 受詞
```

本專案用 SVO 表示：

```text
Subject + Verb/Relation + Object
```

例如：

```text
知識圖譜 --支援--> 多跳推理
ConceptNode --負責--> 知識庫路由
BFS 圖遍歷 --找出--> 關聯路徑
```

三元組關聯驗證要回答的不是「有沒有抽到三個欄位」而已，而是要確認這個三元組是否真的能代表原文中的事實關係。

### 文獻證據：為什麼三元組需要驗證

報告時可以先拿出文獻證據，說明「三元組不是我自己發明的格式」，而是資訊抽取與知識圖譜建構裡長期使用的基礎單位；同時也證明「三元組品質需要驗證」，不是只要 LLM 抽出 JSON 就算完成。

| 文獻 | 可以拿來證明什麼 |
|------|------------------|
| Angeli et al. (2015), Stanford OpenIE | OpenIE 會從句子抽出 relation triples，例如 `(Barack Obama; was born in; Hawaii)`。這證明三元組是開放資訊抽取的標準表達方式。 |
| Text2KGBench (Mihindukulasooriya et al., 2023) | 評估 LLM 是否能依照 ontology 從文本生成知識圖譜。這證明「有本體約束的 KG 生成」需要 benchmark 與 metrics，而不是主觀判斷。 |
| CORE-KG (Meher et al., 2025) | 指出 LLM 建圖常有 hallucination、duplicate nodes、noisy graphs；加入 coreference resolution 與 domain-guided extraction 後，可降低節點重複與噪音。這支撐本專案的別名消解、來源追溯與去重需求。 |
| CoDe-KG (Anuyah et al., 2025) | 以 sentence-level KG、coreference resolution、sentence decomposition 提升關係抽取表現。這支撐本專案先做句子級前處理、SVO chunk 與原句索引。 |
| Ma et al. (2026), Robust GraphRAG | 指出不完整或錯誤的 KG 會造成 GraphRAG retrieval drift 與 hallucination。這可直接支撐「三元組錯，GraphRAG 就會沿錯誤邊檢索」的論點。 |

簡報講法：

> 文獻的共同結論是：三元組可以把文字轉成可查詢的關係，但 LLM 抽出的三元組不一定可靠。如果三元組錯了，GraphRAG 不是只是引用錯片段，而是可能沿著錯誤關係繼續推理。所以三元組驗證是 GraphRAG 能不能可信的核心。

### 1. 結構驗證：三個欄位是否完整

第一層是格式與結構檢查：

- `subject` 是否存在，而且不是空字串。
- `rel_type` 是否存在，而且屬於合法關係類型。
- `object` 是否存在，而且不是空字串。
- `confidence` 是否在合法範圍內。
- 是否保留來源資訊，例如文件 ID、chunk index、句子範圍。

這一層可以擋掉格式錯誤，例如：

```text
錯誤：GraphRAG --空白關係--> RAG
錯誤：空白主詞 --支援--> 多跳推理
錯誤：知識圖譜 --隨便產生的新關係--> 可追溯性
```

### 2. 詞彙表驗證：關係類型是否受控

如果讓 LLM 自由產生關係詞，可能會出現語意相近但字面不同的關係：

```text
A --建立--> B
A --創立--> B
A --成立--> B
```

這些可能其實是同一類關係，但在圖資料庫裡會變成不同邊，造成查詢與多跳推理不穩定。

所以本專案採用受控關係類型，也就是 `rel_type` 必須落在預先定義的合法清單中。如果 LLM 產生不合法類型，系統應該拒絕、修正或退回一般關係，例如 `RELATED_TO`。

簡報講法：

> 三元組不是抽得越自由越好。自由抽取彈性高，但容易造成關係名稱混亂；受控詞彙彈性較低，但能提高語意一致性，讓圖遍歷更可靠。

### 3. 語意驗證：關係是否真的符合句意

通過格式檢查不代表一定正確，還要確認三元組是否符合原文。

原文：

```text
Neo4j 是一種圖資料庫，常用於儲存知識圖譜。
```

合理三元組：

```text
Neo4j --IS_A--> 圖資料庫
Neo4j --STORES/SUPPORTS--> 知識圖譜
```

不合理三元組：

```text
知識圖譜 --IS_A--> Neo4j
```

這種錯誤的欄位可能都完整，但方向錯了。因此驗證時要檢查：

- 主詞與受詞方向是否正確。
- 關係類型是否貼近原文動詞或語意。
- 三元組是否過度推論，超出原文可支持的範圍。
- 是否能回到原文句子找到依據。

### 4. 來源驗證：每個三元組都要能回到原始文件

可驗證的三元組必須能回答：

```text
這條關係從哪裡來？
```

因此每條關係應該保存：

- `source_doc_id`：來源文件。
- `source_svo_chunk_index`：來源 chunk。
- `source_sentence_start` / `source_sentence_end`：來源句子範圍。
- citation 或 evidence：支撐這條關係的原文證據。

這能避免系統只留下「看起來像事實」的關係，卻無法確認依據。

簡報講法：

> 三元組驗證的關鍵是 citation。只要每條邊都能回到原始句子，我們就能檢查它到底是文件真的有寫，還是模型抽取時產生的幻覺。

### 5. 去重驗證：相同事實是否被合併

如果不同 chunk 都提到同一件事，圖中不應該產生多條重複邊：

```text
文件 1：A --支援--> B
文件 2：A --支援--> B
文件 3：A --支援--> B
```

比較好的做法是合併成一條關係邊，並把來源 citation 累積起來：

```text
A --支援--> B
來源：文件 1、文件 2、文件 3
```

這樣可以降低圖譜雜訊，也能用多個來源提高可信度。

### 6. 關聯路徑驗證：三元組是否能串成合理推理鏈

單一三元組正確，不代表整條推理鏈一定正確。GraphRAG 的重點是多個三元組能不能形成合理路徑：

```text
A --影響--> B
B --導致--> C
所以查詢 A 與 C 的關係時，可以沿著 A -> B -> C 找到線索。
```

驗證方式包含：

- 從查詢中的核心實體出發，執行 1-hop 或 2-hop BFS。
- 檢查返回路徑是否都能追溯到來源。
- 檢查路徑是否能支撐最終答案。
- 與純向量 RAG 對照，看圖路徑是否提升多跳問題的正確率。

### 7. 人工與自動化混合驗證

實務上可以分三層驗證：

```text
第一層：程式規則
檢查欄位完整、關係類型合法、來源欄位存在。

第二層：語意相似度
把 LLM 自報的 rel_type 與關係描述 embedding 比對，確認語意是否一致。

第三層：LLM 或人工仲裁
當規則與相似度無法判斷，交給 LLM 或人工確認，並把仲裁結果記錄下來，作為後續校正依據。
```

這對應本專案目前的方向：SVO 抽取後會檢查 `rel_type` 是否在合法清單內；若提供 embedding provider，會執行 SIM/COMPARE/ESCALATE 類型的事後驗證；寫入 Neo4j 時則以 `(kg_id, subject, rel_type, object)` 做事實層級合併，並保存來源資訊。

### 9. 具體例子：三元組的特性與效果

#### 例子一：方向性

原文：

```text
GraphRAG 使用知識圖譜強化 RAG 的多跳推理能力。
```

正確三元組：

```text
GraphRAG --USES--> 知識圖譜
GraphRAG --ENHANCES--> RAG 的多跳推理能力
```

錯誤三元組：

```text
知識圖譜 --USES--> GraphRAG
```

效果說明：

> 三元組有方向性。如果方向錯，圖遍歷會走到錯誤路徑，最後答案也可能錯。

#### 例子二：關係類型一致性

原文可能出現不同說法：

```text
Neo4j 儲存知識圖譜。
Neo4j 支援知識圖譜資料管理。
Neo4j 可用來保存實體關係。
```

如果不做標準化，可能變成：

```text
Neo4j --儲存--> 知識圖譜
Neo4j --支援--> 知識圖譜資料管理
Neo4j --保存--> 實體關係
```

標準化後可以收斂成：

```text
Neo4j --SUPPORTS--> 知識圖譜
Neo4j --SUPPORTS--> 實體關係管理
```

效果說明：

> 關係類型一致，查詢才穩定。否則同一種語意會分散成多種邊，造成召回不完整。

#### 例子三：來源可追溯

三元組：

```text
ConceptNode --ROUTES_TO--> 相關知識庫
```

如果保存來源：

```text
source_doc_id = report-demo
source_sentence = 3
evidence = "ConceptNode 負責將使用者問題路由到相關知識庫。"
```

效果說明：

> 來源可追溯後，回答不是只有結論，還能回到哪一句支撐這條邊。這能降低幻覺，也方便人工檢查。

#### 例子四：多跳路徑

三元組：

```text
GraphRAG --USES--> 知識圖譜
知識圖譜 --REPRESENTS--> 三元組
三元組 --SUPPORTS--> 關係驗證
```

查詢：

```text
GraphRAG 為什麼需要三元組驗證？
```

圖遍歷路徑：

```text
GraphRAG -> 知識圖譜 -> 三元組 -> 關係驗證
```

效果說明：

> 這就是 GraphRAG 與純 RAG 的差異：純 RAG 是找相關段落，GraphRAG 可以把回答依據整理成一條可檢查的關係路徑。

### 題目二總結

驗證三元組關聯，不能只看是否抽出「主詞、關係、受詞」三個欄位；必須同時驗證格式、關係詞彙、語意方向、來源證據、事實去重與多跳路徑。只有當三元組能回到原文、能被一致查詢、能支撐答案時，它才是對知識圖譜有價值的關聯。

```text
-> 因為 GraphRAG 的可信度取決於圖上的邊是否正確。
```

所以開始介紹專案時，不需要立刻深入程式架構。先用緒論方式說明即可：

```text
研究背景
-> 問題缺口
-> 研究目標
-> RQ

```

### 專案一句話定位

World Knowledge Graph RAG 是一套以論文研究為目標的 GraphRAG 系統實作，核心目標是驗證「SVO 知識圖譜 + KG-BFS 圖遍歷 + 多知識庫路由」是否能在多跳問答、可追溯性與查詢效率上補足當代 RAG 與 2024 GraphRAG 的不足。

### 研究背景

本研究的背景可以從三個層次說明：

1. **LLM 的限制**：大型語言模型本身有靜態知識、幻覺與推理路徑不透明的問題。
2. **RAG 的補強與邊界**：RAG 能把外部文件引入回答流程，但主要仍以文字 chunk 為檢索單位，對明確關係、多跳路徑與關係層級可追溯仍有不足。
3. **GraphRAG 的機會與缺陷**：GraphRAG 嘗試結合 RAG 與知識圖譜，但 2024 代表性架構仍有建圖成本高、LLM 建圖品質不穩、偏向全局摘要、Hub Node 路徑爆炸與評估困難等問題。

簡報講法：

> 因此我的研究不是單純做一個聊天系統，而是要驗證：當我們把文件轉成可追溯的三元組知識圖譜後，是否能讓 RAG 在多跳推理與可解釋性上更可靠。

### 研究缺口

依緒論脈絡，本專案主要承接以下缺口：

| 缺口 | 說明 | 對應專案方向 |
|------|------|--------------|
| 多跳推理不穩 | 當答案需要串接多個片段，純文字 RAG 容易漏掉中間證據或發生 retrieval drift。 | KG-BFS 圖遍歷 |
| 多知識庫可擴展性不足 | 多個 KG 並存時，若每次都查全部資料，延遲與成本會上升。 | ConceptNode 輕量路由 |
| 幻覺與來源不明 | LLM 回答可能流暢但缺乏明確依據。 | 自我精煉與來源回補 |
| 關係語意不一致 | 開放式抽取容易把相同語意寫成不同關係。 | 受控關係詞彙與 SVO 驗證 |
| 實體重複與指代問題 | 同一實體可能被不同名稱表示，造成節點分裂。 | 實體別名與指代消解 |
| Hub Node 路徑爆炸 | 高連結節點會讓 BFS 找到太多無關路徑。 | 向量引導剪枝 |

### 研究目標

本研究的目標不是泛稱「GraphRAG 比 RAG 好」，而是要界定它在特定任務上的成立條件：

```text
目標一：驗證 KG-BFS 在多跳推理任務上是否優於當代強化版 RAG。
目標二：驗證多知識庫場景下，輕量路由是否能降低延遲並維持準確率。
目標三：驗證自我精煉與來源回補是否能降低幻覺並提升可追溯性。
目標四：延伸評估三元組關係標準化、實體別名消解、時序更新與 Hub Node 剪枝。
```

簡報講法：

> 這個研究的重點不是宣稱 GraphRAG 全面勝過 RAG，而是找出它在哪些問題類型上真的有用、代價是什麼、哪些元件會影響結果。

### Slide 1：從 NotebookLM 看 Source-Grounded RAG

重點：

- NotebookLM 只作為共同經驗入口，不作為內部實作宣稱。
- 使用者指定來源，系統根據來源回答並附引用。
- 這可抽象為 source-grounded RAG：先找證據，再生成回答。
- 報告時要明確說明：Google 未公開完整內部 pipeline，因此不宣稱它具體用了哪種 chunking、embedding、reranker 或 routing。

講法：

> 我先用 NotebookLM 當例子，不是要介紹產品功能，而是因為它是大家熟悉的 source-grounded RAG 介面。使用者放入來源，系統根據來源回答並提供引用。至於 Google 內部實作細節沒有完整公開，所以我只把它當成 RAG 共同架構的入口，不把它當成特定演算法案例。

圖示：

```text
Sources -> Retrieve evidence -> Generate answer -> Cite sources
```

### Slide 2：RAG 的正式抽象

重點：

- RAG 把 LLM 的參數記憶接上外部、可更新、可檢索的非參數記憶。
- 查詢時不是只讓模型憑內部知識回答，而是先從 corpus 找 evidence。
- Generator 根據 retrieved evidence 組織回答。
- Citation / attribution 讓回答能回指來源，但不等於所有關係都已被驗證。

圖示：

```text
Query
  ↓
Retriever
  ↓
Retrieved Evidence
  ↓
Context Construction
  ↓
Generator / LLM
  ↓
Answer + Attribution
```

講法：

> RAG 的本質不是「讓 LLM 變聰明」這麼籠統，而是讓 LLM 在生成前取得外部 evidence。這解決了模型知識難更新、單靠參數記憶容易幻覺、回答缺乏來源依據等問題。

### Slide 3：現代 RAG 在補哪些 Failure Modes

重點：

| Failure mode | 常見強化方式 |
|--------------|--------------|
| Dense retrieval 可能漏掉精確詞彙或專有名詞 | Hybrid retrieval：結合 dense vector、BM25、metadata filter |
| 初始 top-k 召回排序不一定可靠 | Reranking：先廣召回，再重排 evidence |
| Query 表達模糊或包含多個子問題 | Query rewriting / decomposition：改寫或拆解問題 |
| 多資料源、多索引、多工具不知道該查哪裡 | Router：根據 query 選擇 retriever、query engine 或資料源 |
| 一次性檢索不足，或 retrieved passages 不相關 | Active / self-reflective RAG：生成過程中判斷是否補查與檢查 evidence |

講法：

> 這些名詞不是互相取代的流派，而是在修補 RAG pipeline 不同位置的錯誤：召回漏掉、排序不準、問題拆解不足、資料源選擇錯誤，或生成時沒有檢查 evidence 是否真的支撐答案。

### Slide 4：知識圖譜的核心流程

重點：

- 原始資料先被解析與切分。
- 系統抽取實體與實體之間的關係。
- 關係形成三元組：`主詞 --關係--> 受詞`。
- 同一實體的別名要合併。
- 相同事實要去重，來源要累積。
- 查詢時沿節點、邊與路徑找答案，再回原文補證據。

講法：

> 如果 RAG 是查詢時過濾文字證據，知識圖譜就是事前提煉關係知識。它讓 LLM 不必完全從文字裡臨時理解關係，而是可以根據已整理好的實體、關係與來源回答。

### Slide 5：2026 版知識圖譜的改良

重點：

- LLM 輔助抽取實體與關係，降低初始建圖成本。
- 受控關係詞彙與型別驗證，降低關係混亂。
- 實體對齊與別名合併，避免同一實體分裂。
- 每條邊保留文件、chunk、句子與 citation。
- 增量抽取與回溯重分類，讓圖譜能隨資料演化。
- bounded BFS / Hub Node 剪枝，控制路徑噪音。

講法：

> 2026 版知識圖譜不是回到完全人工建圖，而是把 LLM 輔助抽取、schema 治理、來源追溯、實體去重與增量更新接起來，讓關係知識可以被持續維護。

### Slide 6：RAG 與知識圖譜比較

重點：

| 面向 | RAG | 知識圖譜 |
|------|-----|----------|
| 處理時機 | 查詢時檢索 | 事前建圖 |
| 主要單位 | 文字片段 | 實體、關係、路徑 |
| 強項 | 快速理解與摘要 | 關係查詢與多跳推理 |
| 成本 | 建置較快 | 建圖與維護較重 |
| 風險 | 相關文字不一定支撐答案 | 錯誤關係會污染圖譜 |

講法：

> RAG 適合快速從大量文件找證據；知識圖譜適合把重要關係整理成可查詢、可追溯、可重複使用的結構。兩者不是誰取代誰，而是任務粒度不同。

### Slide 7：GraphRAG 如何結合兩者

重點：

- RAG 提供文字證據。
- KG 提供關係結構。
- GraphRAG 可以先做語意召回，再沿圖擴展。
- 簡單問題可走文本，多跳關係可走圖，全局問題可走摘要。
- 回答時同時呈現原文證據與關係路徑。

圖示：

```text
Query -> 找 KG / ConceptNode -> 找 fact / triple / path
      -> 沿圖擴展 -> 回原文補 citation -> LLM 回答
```

### Slide 8：GraphRAG 的不足

重點：

- 建圖與 community summary 成本高，冷啟動慢。
- LLM 建圖品質不穩，錯誤三元組會造成 retrieval drift。
- 原始架構偏向 global sensemaking，不等於精準三元組問答。
- 圖遍歷遇到 Hub Node 會有路徑爆炸。
- 評估困難，不能只看最後答案流暢度。

### Slide 9：為什麼要證明 SVO 關聯性

重點：

```text
Subject --Relation--> Object
```

例子：

```text
Neo4j --儲存--> 知識圖譜
BFS --找出--> 關聯路徑
知識圖譜 --支援--> 多跳推理
```

講法：

> GraphRAG 的關鍵不是有沒有圖，而是圖裡的邊是否可信。SVO 是圖譜關係最基本的單位，所以要證明的是這條主詞、關係、受詞是否真的被原文支持。

### Slide 10：三元組如何驗證

重點：

- 方向錯：主詞與受詞反了。
- 關係類型錯：動詞或語意被歸到錯誤 relation type。
- 來源不支持：三元組看似合理，但原文沒有 entail。
- 限定條件遺失：時間、地點、條件、否定被漏掉。
- 實體綁定錯：關係接到錯誤實體或別名沒有對齊。
- 重複事實未合併：同一事實在圖中形成多條碎片邊。
- 結構完整。
- 關係類型合法。
- 語意方向正確。
- 可回到原文來源。
- 相同事實可合併去重。
- 多個三元組能形成合理路徑。

文獻對應：

- OpenIE：三元組作為資訊抽取標準形式。
- Text2KGBench：ontology-driven KG generation 需要 benchmark。
- CORE-KG / CoDe-KG：coreference、sentence decomposition、去重會影響 KG 品質。
- Robust GraphRAG：錯誤 KG 會造成 retrieval drift 與 hallucination。

### Slide 11：簡化成果與具體例子

重點：

- 準備 5 到 8 句 micro-benchmark。
- 研究者先制定示範用 gold triples。
- 比較純 RAG、未驗證 SVO、驗證後 SVO。
- 指標：Precision、Recall、F1、Traceability。
- 方向性：`GraphRAG --USES--> 知識圖譜` 不能反過來。
- 關係一致性：`儲存/支援/保存` 需要收斂成可查詢的關係類型。
- 來源追溯：每條邊要能回到原文句子。
- 多跳路徑：`GraphRAG -> 知識圖譜 -> 三元組 -> 關係驗證`。

## 口頭報告用短版稿

我會先用 NotebookLM 當入口，但不是要介紹 NotebookLM 的產品功能，而是因為它是大家熟悉的 source-grounded RAG 介面。使用者放入來源資料，系統根據來源回答並提供引用。Google 沒有公開完整內部 pipeline，所以我不宣稱它具體用了哪種 chunking、embedding、reranker 或 routing；我只用它來說明 RAG 的共同架構：先從外部 corpus 檢索 evidence，再讓 LLM 根據 evidence 生成回答。

RAG 的本質，是把 LLM 的參數記憶接上一個外部、可更新、可檢索的非參數記憶。它解決的是模型知識難更新、單靠參數記憶容易幻覺、回答缺乏來源依據等問題。現代 RAG 的很多改良，其實是在修補 pipeline 不同位置的 failure mode：hybrid retrieval 補 dense retrieval 對精確詞彙或專有名詞的盲點；reranking 補初始 top-k 排序不可靠；query rewriting 或 decomposition 補查詢表達不佳與複雜問題拆解不足；router 補多資料源或多 retriever 選擇問題；active / self-reflective RAG 則補一次性檢索不足，以及 retrieved passages 不相關卻仍被模型使用的問題。

所以我不是要否定 RAG。RAG 很適合 evidence retrieval、摘要、問答、跨文件整理與來源引用。但它主要處理的仍然是文字證據。Citation 不等於 entailment 成立；retrieved chunk 不等於 typed relation；找到相關段落，也不保證主詞、受詞、關係方向、時間條件或跨文件實體別名都正確。

這就是我引入知識圖譜的原因。知識圖譜的核心流程，是在資料進入系統時先抽取實體、抽取關係、形成三元組，再做實體對齊、事實去重與來源累積。換句話說，RAG 是查詢時過濾文字證據，知識圖譜是事前提煉關係知識。2026 版知識圖譜的改良，不是回到完全人工建圖，而是把 LLM 輔助抽取、受控關係詞彙、實體別名合併、來源追溯、增量更新與圖遍歷控制接進來，讓圖譜比較接近可持續運行的知識系統。

兩者不是衝突關係。如果只是快速了解一批資料大概在說什麼，RAG 通常比較划算；如果問題重點是「誰和誰有什麼關係」「這條關係從哪裡來」「能不能串成可檢查的推理路徑」，知識圖譜更有價值。GraphRAG 的意義，就是把 RAG 的文字證據能力與知識圖譜的關係結構能力接起來：簡單問題可以走文本，多跳關係可以走圖，全局問題可以走社群摘要。

但 GraphRAG 也有不足。2024 版 GraphRAG 代表性做法需要先抽實體關係、建圖、做 community detection，再產生 community summary，冷啟動成本高；而且 LLM 建圖品質不穩，錯誤三元組會變成錯誤檢索路徑。它也偏向 global sensemaking，不等於精準三元組問答；圖遍歷會遇到 Hub Node 與路徑爆炸；評估時也不能只看最後答案流不流暢。

所以本報告要證明的重點，是 SVO 的關聯性是否可信。三元組指的是 Subject、Relation、Object，例如「Neo4j 儲存 知識圖譜」。但三元組不是抽出三個欄位就算成功，還要檢查方向是否正確、關係類型是否合法、語意是否符合原文、是否能追溯到來源句子、相同事實是否能合併去重，以及多個三元組是否能形成合理路徑。OpenIE、Text2KGBench、CORE-KG、CoDe-KG 與 Robust GraphRAG 這些文獻，分別支撐了三元組抽取、KG generation benchmark、coreference / sentence decomposition / 去重，以及錯誤 KG 對 GraphRAG 檢索漂移與幻覺的影響。

為了快速證明這件事，我會準備一個簡化 micro-benchmark：用 5 到 8 句文本先制定示範用 gold triples，比較純 RAG、未驗證 SVO、驗證後 SVO，在 Precision、Recall、F1 與 Traceability 上的差異。這個小成果不代表正式人工標註實驗，但可以先展示三元組驗證確實會影響圖譜品質。

在這個前提下，我的專案 World Knowledge Graph RAG 就是論文的實作載體。它的改良方向是分層處理：文字層保留原文 chunk、句子範圍與 citation；關係層抽取 SVO 三元組並寫入 Neo4j；驗證層檢查結構、詞彙、語意方向與來源；治理層做實體別名合併、相同事實去重與關係類型擴充審核；檢索層用 ConceptNode 路由與 bounded BFS 控制查詢範圍。專案不是只做一個聊天 demo，而是把研究問題落到可實驗、可比較、可追溯的系統架構上。

