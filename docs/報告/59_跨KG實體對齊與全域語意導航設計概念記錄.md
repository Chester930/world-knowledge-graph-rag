## 1. 核心發現

目前系統存在兩種不同層級的實體處理機制：

1. `services/entity_registry_service.py`：文件內的別名登記表，維護單一文件中的暫定標準名、別名頻率與斷點續傳快照。
2. `services/svo_service.py`：Neo4j Entity 的 KG 內部去重，透過 exact、編輯距離、cosine 與條件式 LLM 仲裁決定 `Entity.name`。

Neo4j Entity 的目前識別鍵是：

```cypher
MERGE (e:Entity {kg_id: $kg_id, name: $entity_name})
```

候選查詢同樣以 `kg_id` 限定；即使 `Entity` 使用全域共用 label 與向量索引，查詢仍會在候選取得後以 `kg_id` 過濾。因此目前的 Entity Resolution 是「KG 內部作用域」，不是跨 KG 的全域實體對齊。

結果是：

```text
KG-A：「工資」
KG-B：「薪資所得」

兩者可以各自建立 Entity，
但目前不會自動形成跨 KG 的語意對齊關係，也沒有 SAME_AS／ALIGNED_TO 導航邊。
```

這與 SDD-51 的中央文件 SSOT／Manifest 不同：Manifest 解決的是「文件實體不重複與多 KG 邏輯歸屬」，不是「跨 KG 語意實體共指」。兩者不可混為同一個全域實體庫。

## 2. 目前實作邊界

### 2.1 已存在

- KG 內 Entity 唯一約束：`(kg_id, name)`。
- Entity 名稱的 exact／編輯距離／cosine／LLM 灰區仲裁。
- Entity 名稱向量 `name_embedding` 與 canopy 候選檢索。
- 文件內 `EntityRegistry` 的別名規則、頻率／長度提升與快照持久化。
- `Chunk-[:HAS_ENTITY]->Entity` 邊與來源文件追溯。

### 2.2 尚未存在

- 跨 KG 全域候選池或 Canonical Entity 節點。
- Entity 之間的 `SAME_AS`／`ALIGNED_TO` 關係。
- 跨 KG 對齊的 confidence、證據、判定方法與人工審核狀態。
- 查詢時沿跨 KG 對齊關係展開並回提其他 KG Chunk 的流程。
- `services/concept_engine.py::route_kgs()` 的實際路由實作。

此外，預設抽取流程目前以 `mentions=None` 呼叫前處理，因此文件內 EntityRegistry 在預設路徑仍是可用但未啟用的能力；不可將它描述成已完成的跨文件／跨 KG 對齊機制。

## 3. 設計原則

本概念不直接把所有 KG 的 Entity 合併成同一節點，採取「本地 Entity 層＋全域 Canonical 層」：

```text
(:Entity {kg_id, name})
        │
        └─[:ALIGNED_TO {
             confidence,
             method,
             evidence_json,
             status,
             created_at,
             reviewed_at
           }]
        │
(:CanonicalEntity {canonical_id, canonical_name, domain_types})
```

### 3.1 本地層

- 保留 `(kg_id, name)` 作為各 KG 的局部識別鍵。
- 不因跨 KG 相似度而改寫原有 Entity、Fact 或來源引用。
- 保留不同領域可能存在的同名但不同義實體。

### 3.2 全域層

- `CanonicalEntity` 表達跨 KG 的候選語意身份。
- `ALIGNED_TO` 是建議的內部關係名稱；只有高信心且通過驗證的對齊，才可視為語意上的 `SAME_AS`。
- 對齊結果必須保存來源、模型／規則、分數、證據與審核狀態，才能撤銷或重新評估。

### 3.3 查詢層

查詢時才進行跨 KG 導航：

```text
問題
 → 本地 Entity／Concept 候選
 → ALIGNED_TO 展開
 → 目標 KG 路由
 → Fact／SVO 路徑檢索
 → 回提來源 Chunk
 → 來源接地後生成答案
```

## 4. 後續工作計畫

### P0：建立反例與黃金測試集

至少包含：

- 跨 KG 近義：工資／薪資所得。
- 同名異義：不同法域或不同領域的同名 Entity。
- 字面相似但數值不同：四千元／八千元、五日／十日。
- 型別不一致但實體相同：同一正式機關被抽成不同型別。
- 應拒絕對齊的近義詞與上下位詞。

### P1：新增全域候選介面

保留目前 `scope="local"` 為預設，另增加明確的全域候選模式。候選流程應為：

```text
字串 canopy
 → embedding canopy
 → 型別／領域過濾
 → 高信心直接對齊
 → 灰區 LLM／人工仲裁
 → 建立待審核 ALIGNED_TO
```

不得因新增全域模式而改變既有 KG 內去重的預設行為。

### P1：建立對齊資料模型與 Neo4j 寫入

初期只新增對齊資料與關係，不搬移、不合併原有 Entity。所有自動對齊先標記為 `proposed` 或 `needs_review`；只有通過門檻與驗證的資料才升級為 `accepted`。

### P2：接入跨 KG 查詢

將對齊結果接到 `route_kgs()`，再由查詢端展開至目標 KG 的 Fact、SVO 與原始 Chunk。必須保留：

- 單一 KG fallback。
- 跨 KG 展開深度上限。
- 每個 KG 的來源標記。
- 跨 KG 污染防護與拒答機制。

## 5. 驗收標準

- 既有 KG 內 Entity 去重測試零回歸。
- 不同 KG 的相似名稱不會被直接 `MERGE` 成同一個本地 Entity。
- 全域候選可召回跨 KG 對齊候選。
- 每條對齊邊都有 confidence、method、evidence 與 status。
- accepted 對齊可以讓查詢跨 KG 找到正確來源 Chunk。
- rejected／revoked 對齊不再參與查詢導航。
- 可量測 Entity Linking precision、recall、誤合併率、跨 KG routing recall 與來源污染率。
- 原有數字、日期、否定、例外條件與法條來源不得因跨 KG 對齊而改變。
