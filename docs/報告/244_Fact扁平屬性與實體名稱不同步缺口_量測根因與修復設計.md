## 1. 白話摘要

Fact 節點（每筆來源引用一個）在建立時，會把當下的「主詞、受詞、關係型別」抄一份存成自己的屬性（稱「扁平屬性」），後面的檢索去重就用它。但實體後來若被**改名**（例如標準名提升、簡繁合併），Fact 身上那份抄本**不會跟著更新**。結果是：同一個實體對、實際上是同一件事的兩個 Fact，因為抄本名稱不同，被當成不同事實，去重失效。

**這不是狀態機帶來的新問題，現在的 KG#4 就已經有了，而且寫入流程本身會繼續製造它。** 但狀態機的「先過濾、再依鍵去重」依賴同一把鍵，所以建議先把鍵修準。

## 3. 根因（〔事實〕，讀碼）

1. **建立時一致**：`merge_triples_to_graph` 以 `subject=subject_name`、`object_=object_name`（`merge_entity` 回傳的對齊後名稱）呼叫 `_create_fact_node`（`services/svo_service.py:1295–1309`），所以 Fact 抄本在建立當下等於實體名稱。
2. **之後實體被改名，Fact 不更新**：
   - **寫入流程內**：`merge_entity` 在 `should_promote_by_frequency` 成立時，把既有實體改名為更常見的別名（`:760–776`，`SET e.name = $final_name, e.aliases = $aliases`）——**這是量測中那些別名樣本的最可能來源（〔推論〕：量測樣本符合此行為，但我沒有逐筆溯源）**。
   - **回填**：`backfill_traditionalize_entity_names`（`:2071–2197`）純改名或搬邊後刪簡體節點（報告243 H1／H2 已在真實 Neo4j 證實 Fact 抄本不更新）。
   - **改邊型別**：`backfill_related_to_edges`（`:2237–2329`）刪邊重建，Fact 的 `rel_type` 不更新，且新邊只複製 `kg_id`／`citations_json`／`confidence`（**漏複製 `verb_embedding` 與邊上的 `natural_text`**，後者為規劃對話讀碼，未實測）。
3. 全檔沒有任何程式更新 Fact 的 `subject`／`object`／`rel_type`（`SET f.` 只出現在 `fact_text`／`fact_embedding`，`:1898`、`:1978`）。
4. **同步扁平屬性還不夠**：`fact_text` 與 `fact_embedding` 也是建立時產生，報告243 V4 觀察到同步後 `fact_text` 仍是舊文字。`backfill_fact_text_embeddings`（`:1827–1911`）讀碼顯示會由扁平屬性重建 `fact_text`、不同才重算向量，故**修復順序應為「同步扁平屬性 → 重跑該回填」（〔推論〕，未實測）**。

## 4. 影響評估

| 面向 | 影響 | 程度（〔推論〕） |
| --- | --- | --- |
| 去重 | 約 208 組以上同一事實沒被合併，佔用檢索名額 | 低至中（約 1.5% 的鍵組；名額稀釋） |
| prompt 內文字 | 事實行用 `fact_text`（建立時的名稱）；顯示的是較舊別名，語意通常仍可理解 | 低 |
| 向量檢索 | `fact_embedding` 由舊 `fact_text` 算出，與目前實體名稱不一致 | 低 |
| 跨層去重（BFS 與 Fact） | BFS 用實體現名、Fact 用抄本，鍵不同 → 同一事實兩行都留 | 低至中 |
| **狀態機（未來）** | 「先過濾、再依鍵去重」的鍵若不準，舊版與新版會因抄本不同而**不被視為同一事實**，狀態過濾無法對應 | **中（是這個缺口最需要現在處理的原因）** |
| 寫入流程 | 缺口持續累積（標準名提升每次發生就多一批） | 持續 |

## 5. 修復方案（請使用者選）

| 方案 | 做法 | 優點 | 缺點／風險 | 我的評價 |
| --- | --- | --- | --- | --- |
| **A　寫入時同步（改熱路徑）** | 在 `merge_entity` 改名分支內，順手更新該實體所連 Fact 的扁平屬性（並重算 `fact_text`／向量） | 缺口不再累積 | 改正式寫入熱路徑；每次改名要更新 N 個 Fact 並重算 N 次向量（embedding 呼叫量大）；必須先充分驗證 | **不建議** |
| **B　獨立「重同步」維護函式（新增，不改既有函式）** | 新增冪等函式 `resync_fact_flat_properties(driver, kg_id, *, dry_run=True)`：①由 `HAS_SUBJECT`／`HAS_OBJECT` 回寫 `subject`／`object`；②（可選）端點間僅一條關係邊時回寫 `rel_type`；回傳變更統計；**之後**再跑既有 `backfill_fact_text_embeddings` 重建 `fact_text`／向量。預設 `dry_run`，只回報數量 | 不動既有熱路徑；冪等（報告243 V4 已證實同步能冪等）；可在每批寫入／回填後例行執行；`dry_run` 可先看影響 | 需新增模組與測試；寫 KG#4 前必須備份（§6）；回填需 embedding provider（呼叫量等於過時 Fact 數，KG#4 約 1,100–1,800 筆，量小） | **建議（首選）** |
| **C　讀取端改用實體名稱當去重鍵** | `vector_search_facts` 的 Cypher 增加 `OPTIONAL MATCH` 取 `HAS_SUBJECT`／`HAS_OBJECT` 的實體名稱，去重與回傳都用它 | **不改任何資料**；可旗標控制、可逆；同時對齊 BFS 側的鍵 | 屬檢索行為變更，需用凍結題庫評測（評分器噪音大，達標數 ±2 屬噪音）；每個 KNN 候選多兩次展開（候選數百，成本小） | 可作為 B 之外的第二道，**先評測再決定** |
| **D　穩定 ID** | 實體以穩定 ID 而非名稱識別 | 根治 | 範圍極大（圖綱要、抽取、回填全改） | 長期，不在本階段 |

**我的建議：B 為主（含既有回填的順序），C 視評測決定；不做 A。** 理由：B 不碰熱路徑、可 `dry_run`、冪等；C 不改資料但會改變檢索，需要證據。

## 6. 套用到 KG#4 之前的必要條件（〔事實〕：KG#4 是唯一副本）

1. **備份與還原演練**：目前沒有備份。需先設計並**在臨時容器演練**一次「備份→還原→總數與抽樣比對」，通過後才能對 KG#4 寫入任何東西。方式待評估（Neo4j 企業版可考慮線上備份或停機 dump；KG#4 在 `kg2-neo4j` 容器內，需再確認其資料存放位置與停機成本）。
2. **先在臨時容器驗證 B**：用與 KG#4 同型的合成資料，驗證 `dry_run` 數量與實際變更一致、冪等、不影響 Fact／邊數、重跑回填後 `fact_text`／向量一致、BFS 與 Fact 鍵對齊。
3. **每次寫入前確認併發**（無其他 session、17990 無連線、無會寫 Neo4j 的程序），並先 `dry_run`。
4. **回滾**：B 只改屬性值；備份是唯一可靠的回滾手段，故 §6-1 是硬性前提。

## 8. 限制與誠實揭露

- 量測是 KG#4 單一時點、只算「扁平名稱 ≠ 實體名稱」，**沒有逐筆溯源是哪個機制造成的**（別名提升與簡繁回填的比例未知）。
- 「約 208 組」是**下限推算**（依兩種鍵的分組數相減），不是逐組確認；對檢索品質的實際影響**未測**。
- `fact_text`／向量過時的影響與「重跑回填即可修復」皆為**推論，未實測**。
- `rel_type` 同步在端點間有多種邊時無法只憑 Fact 判定（KG#4 有 1,684 筆屬此類），方案 B 只能保守處理；目前 KG#4 沒有 `rel_type` 過時（0 筆），這部分是**預防性**。
- 本文不涉及狀態機本身的落地，只處理它依賴的鍵。
