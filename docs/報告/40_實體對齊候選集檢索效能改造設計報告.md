# 40：實體對齊候選集檢索效能改造設計報告（Pass 2 L6 R2）

> 狀態：🟡 **設計提案**（2026-09-11，Pass 2 逐層審視 L6 發現）。本報告只做設計、文獻/專案背書與驗證計畫；**實作與驗證待 DRAIN-DONE**——`_fetch_entity_candidates()` 是正在跑的抽取 Worker 每個實體 merge 都會呼叫的熱路徑，候選集改變會改變 merge 決策、產生不同的圖，不能在 drain 進行中動。對應 `docs/論文/03_系統設計與方法論.md` §3.1.4 `DEDUP4`、§3.4 §b。

## 1. 問題

### 1.1 現況

`services/svo_service.py::_fetch_entity_candidates(driver, kg_id, entity_type, name)`：

```cypher
MATCH (e:Entity {kg_id: $kg_id}) RETURN e.name AS name, e.type AS type, e.name_embedding AS name_embedding
```

**每一次實體 merge，都把該 KG 底下的全部 Entity 節點（名稱、型別、384 維 `name_embedding`）載進 Python**，再在應用層依型別集合交集過濾。`merge_triples_to_graph()` 對每個三元組呼叫兩次 `merge_entity()`（subject、object），`merge_entity()` 呼叫一次 `_fetch_entity_candidates()`——因此單一 chunk 的抽取，候選集載入次數 ≈ 2 × 三元組數；隨 KG 內實體數 `n` 線性成長，整份文件抽取 ≈ O(n²)。

`resolve_entity_name()` 拿到候選集後依序做：① GUARD4 早退（量詞/範圍/列舉樣式，回傳原名）→ ② scope-modifier 雙向過濾 → ③ 精確比對（全部候選）→ ④ 編輯距離 ≥ `ENTITY_DEDUP_EDIT_RATIO_THRESHOLD`(0.70)（`fuzzy_candidates`）→ ⑤ cosine ≥ `ENTITY_DEDUP_COSINE_THRESHOLD`(0.88)（`fuzzy_candidates`）→ ⑥ cosine 落在 `[0.75, 0.88)` 灰色地帶時 LLM 仲裁。

`vector_search_entities()`（查詢端 `_find_seed_entities()` 的語意 fallback，Pass 2 L9 V2）有**同構問題**：

```cypher
MATCH (e:Entity {kg_id: $kg_id})
WHERE e.name_embedding IS NOT NULL AND e.name IS NOT NULL
WITH e, vector.similarity.cosine(e.name_embedding, $vector) AS score
ORDER BY score DESC LIMIT $top_k
```

無向量索引、brute-force 全掃（該函式 docstring 自承「demo 規模下 brute-force 完全可接受」）。

### 1.2 影響

- **抽取吞吐**：[[project_entity_mixing_embedding_investigation]] 與 §3.1.4「`DEDUP4` 節點向量化效能改造」段皆記錄「使用者已實際觀測到隨抽取進度累積、KG 內實體數增加，抽取速度明顯下降」。2026-08-03 的 `name_embedding` 持久化只省掉「重複 `encode()`」，**沒有解決「每次 merge 全掃 n 個節點」本身**。
- **查詢延遲**：`_find_seed_entities()` 字面比對失敗退語意 fallback 時，每個查詢全掃一次 KG 實體。
- **索引現況**：`Entity.name_embedding` 屬性已持久化，但**全 codebase 無任何 `CREATE VECTOR INDEX ... FOR (e:Entity) ON e.name_embedding`**（只有 `Chunk`／`Fact`／`ConceptNode`／`RELATED_TO` 邊有向量索引）。

## 2. 為何不是「行為零變化」的純效能改造

與 §3.9「設定分層」那種「defaults == 現值、golden test 保證零變化」不同：**縮小候選集 = 改變 `resolve_entity_name()` 看得到哪些候選 = 可能改變 merge / 新建的判定 = 產生不同的圖。** 因此本改造：

1. 目標是「保留 tiers ③–⑥ 會命中的候選、只砍掉它們永遠不會看的那些」——**不是任意 blocking**（例如「首字相同」會拆壞「台積電 / TSMC」「勞工 / labour」這類真 merge）。
2. **必須有 recall 對照驗證**（見 §7）：新方案漏掉多少「舊方案會 merge」的案例，逐案分類為「漏掉真 merge（不可接受）」vs「避開了錯 merge（中性/更好）」vs「平手 tie-break 雜訊」。
3. 驗證需對 drain 正在寫的 KG#4（`236903cf-...`，kg2-neo4j）跑，故 **DRAIN-DONE 後才實作+驗證**；向量索引建立本身冪等安全（`IF NOT EXISTS`、對空/既有 label 皆無害），可先落地。

## 3. 設計：canopy 式多訊號 DB 側候選檢索

以 McCallum, Nigam & Ungar（2000）canopy clustering 的精神——**用廉價、可索引的相似訊號先圈出「可能匹配」的小集合（canopy），昂貴比對只在 canopy 內做**——把單一全掃查詢換成三個各自命中一個 match tier 的可索引子查詢，取聯集：

### 3.1 Exact canopy（tier ③）

```cypher
MATCH (e:Entity {kg_id: $kg_id, name: $name}) RETURN e.name, e.type, e.name_embedding
```

O(1)，走既有 `entity_kg_name_unique` 唯一約束附帶的索引。**零漏失。** 也涵蓋 2026-08-30 修正的「精確同名一律納入候選、不看型別」。

### 3.2 Cosine canopy（tiers ⑤⑥）

新增 per-KG 向量索引（比照 `_fact_vector_index_name()` 的 per-KG label 隔離慣例，或全域索引 + `kg_id` 屬性過濾——見 §6 取捨）：

```cypher
CREATE VECTOR INDEX entity_name_vector IF NOT EXISTS
FOR (e:Entity) ON e.name_embedding
OPTIONS { indexConfig: { `vector.dimensions`: $dim, `vector.similarity_function`: 'cosine' } }
```

查詢：

```cypher
CALL db.index.vector.queryNodes('entity_name_vector', $canopy_k, $name_vec)
YIELD node AS e, score
WHERE e.kg_id = $kg_id
RETURN e.name, e.type, e.name_embedding, score
```

`canopy_k` 取寬鬆值（初擬 50，待 §5 校準）。**漏失風險**：只有當「與 mention 的 cosine > 0.88 的既有實體」超過 `canopy_k` 個時才會漏——那代表 KG 裡有 >50 個彼此近義的實體同時和這次 mention 高度相似，實務上極罕見。`name_embedding IS NULL` 的舊節點（未跑過 `backfill_entity_name_embeddings()`）本來在 tier ⑤⑥ 就會被 fallback 即時 encode——改造後這批節點改由 §3.3 的字串 canopy 兜底（見該節）。

### 3.3 字串 canopy（tier ④ 編輯距離）

編輯距離 ≥ 0.70 的真實命中，絕大多數是**子字串關係**（「台積電」⊂「台積電公司」、「San Antonio」⊂「San Antonio, Texas」）或**高度共享前綴/後綴**。用 CJK-aware fulltext 索引圈出：

```cypher
CREATE FULLTEXT INDEX entity_name_fulltext IF NOT EXISTS
FOR (e:Entity) ON EACH [e.name]
OPTIONS { indexConfig: { `fulltext.analyzer`: 'cjk' } }
```

（`cjk` analyzer 做 bigram 切分，中文子字串可命中；若部署版本不支援，退回 `MATCH (e:Entity {kg_id}) WHERE e.name CONTAINS $name OR $name CONTAINS e.name`——仍是 O(n) 掃描，但只碰字串、不載入 384 維向量，成本約為現況的 1/10，作為過渡。）

```cypher
CALL db.index.fulltext.queryNodes('entity_name_fulltext', $ft_query)
YIELD node AS e WHERE e.kg_id = $kg_id
RETURN e.name, e.type, e.name_embedding
```

**漏失風險**：編輯距離 0.70 但無任何共享 bigram 的配對（例如純換字：「甲式」vs「乙式」`_edit_ratio` 0.5，不會過 0.70；真的過 0.70 又無共享 bigram 的中文名幾乎不存在）。英文縮寫型（「I-35」vs「Interstate Highway 35」）`_edit_ratio` 本來就 < 0.70、走的是 cosine/LLM，由 §3.2 canopy 覆蓋。

### 3.4 聯集 + 既有後處理不變

三個 canopy 的結果去重取聯集，交給**現有的** `resolve_entity_name()`——GUARD4 早退、scope-modifier 雙向過濾、tiers ③–⑥ 的門檻與順序**一行都不動**。型別集合交集過濾維持在 Python（候選集現在很小），或下推進每個子查詢的 `WHERE`（見 §6）。

## 4. Recall 分析總表

| tier | 現況來源 | 改造後來源 | 漏失情境 | 緩解 |
|---|---|---|---|---|
| ③ 精確 | 全掃 | Exact canopy（唯一約束） | 無 | — |
| ④ 編輯距離 ≥0.70 | 全掃 → Python `_edit_ratio` | 字串 canopy（fulltext bigram / CONTAINS） | 0.70 命中但零共享 bigram（中文近乎不存在） | fulltext 用 bigram；過渡期用 CONTAINS |
| ⑤ cosine ≥0.88 | 全掃 → Python cosine | Cosine canopy（向量索引 top-`canopy_k`） | >`canopy_k` 個實體同時 cosine>0.88（極罕見） | `canopy_k`=50，§5 校準 |
| ⑥ LLM 灰色 [0.75,0.88) | 全掃 → Python cosine | Cosine canopy 同上 | 同 ⑤ | 同 ⑤ |
| `name_embedding IS NULL` 舊節點 | 全掃 → fallback encode | 字串 canopy 兜底 | 舊節點且非子字串關係 | drain 後既有 backfill Worker 補齊向量即消失 |

**保守設計原則**（比照 §3.1.3 REJECT / 報告19/20 降級哲學）：`canopy_k` 寧大勿小；fulltext 不可用時退 CONTAINS 而非直接砍字串 canopy。

## 6. 實作範圍與取捨（待 DRAIN-DONE）

1. **新增** `create_entity_name_vector_index(driver, kg_id, dim)` + `create_entity_name_fulltext_index(driver)`，接進 `main.py::lifespan`（比照既有 `create_entity_index` / `create_chunk_vector_index`）。
   - **per-KG label vs 全域索引**：`Fact` 因 Neo4j「一個 `(label, property)` 只能一個向量索引」被迫 per-KG label（§3.1.4 §a）。`Entity` 已是單一 label、`_fetch_entity_candidates` 本來就帶 `kg_id` 過濾——用**全域 `entity_name_vector` 索引 + 查詢後 `WHERE e.kg_id = $kg_id`** 即可（post-filter，與 `vector_search_facts` 早期版本同模式）；除非實測多 KG 混索引下 recall 被稀釋，才改 per-KG label。
2. **改** `_fetch_entity_candidates()`：三個 canopy 子查詢 + 聯集去重。簽章不變，回傳結構不變（`[{"name", "name_embedding"}]`，型別過濾邏輯保留）。
3. **順帶改** `vector_search_entities()`（L9 V2）：改走 `entity_name_vector` 索引，去掉 brute-force `WITH ... vector.similarity.cosine`。同一個索引、同一次改造。
4. **測試**：`tests/services/test_svo_service.py` 的 `InMemoryEntityDriver` 補三種查詢形狀的 fake 支援；新增「新舊候選集對同一組 fixture 產出相同 `resolve_entity_name` 結果」的 golden test。

## 7. 驗證計畫（DRAIN-DONE 後執行）

1. **建索引**：對 KG#4 建 `entity_name_vector` + `entity_name_fulltext`；`backfill_entity_name_embeddings()` 確認 `name_embedding` 無缺漏。
2. **Recall 對照**：從 KG#4 已抽取的 chunk 隨機抽 N（≥300）個實體 mention，對每個：
   - 跑舊 `_fetch_entity_candidates`（全掃）→ `resolve_entity_name` → `old_resolved`
   - 跑新 canopy 版 → `resolve_entity_name` → `new_resolved`
   - 記錄 `old_resolved != new_resolved` 的案例，逐案人工分類：(a) 新版漏掉真 merge（**recall loss，不可接受**）／(b) 新版避開了舊版的錯 merge（precision gain）／(c) 平手 tie-break 雜訊。
3. **接受標準**：(a) 類 = 0；或每個 (a) 案例經人工確認影響可忽略。掃 `canopy_k ∈ {20,50,100}` 取最小的「(a)=0」值。
4. **效能對照**：在 KG#4 實體數（實測，約 3–5k）下，量測 `_fetch_entity_candidates` 舊/新的延遲與記憶體；預期新版候選集 O(canopy_k) 而非 O(n)。
5. **迴歸**：全套 pytest；`InMemoryEntityDriver` golden test 綠。

## 8. 文獻與專案背書（2026-09-11 即時查證）

**方法論**：

- **Papadakis, Skoutas, Thanos & Palpanas（2020）《Blocking and Filtering Techniques for Entity Resolution: A Survey》**，*ACM Computing Surveys* 53(2)（arXiv:1905.06167）——實體對齊 blocking 的權威綜述：「blocking tackles ER's inherent quadratic complexity by trading slightly lower effectiveness for significantly higher efficiency... cluster potentially matching entities in common blocks and exclusively compare entity profiles that co-occur」。本改造正是此原則的 Neo4j + 向量索引 + fulltext 實例化。⚠️ 尚未下載本地 PDF。
- **McCallum, Nigam & Ungar（2000）《Efficient Clustering of High-Dimensional Data Sets with Application to Reference Matching》**，KDD 2000——**canopy clustering** 原始文獻：用廉價相似度圈出重疊的 canopy，昂貴比對只在 canopy 內做。本改造的「三個可索引 canopy 取聯集、`resolve_entity_name` 只在聯集內做編輯距離/cosine/LLM」是其直接套用。⚠️ 尚未下載本地 PDF。
- **Fellegi & Sunter（1969）** 三區決策框架——已於 §3.1.4 §b / §3.1.3 §a-1 引用，`resolve_entity_name` 的 tiers ③–⑥ 即其實例，本改造不動判準、只換候選來源。

**開源專案（`gh api` 即時查證 2026-09-11）**：

- `moj-analytical-services/splink`（**2,394★**，活躍，2026-09-10 push）——已於 §3.1.4 §b 引用（當時記 2,310★）；其 **blocking rules** 機制正是「用 SQL 可索引的 predicate（相等、子字串、n-gram）先圈候選對，再算機率式相似度」，與本改造的三 canopy 同構。
- `dedupeio/dedupe`（**4,512★**，活躍）——**predicate blocking**（TfIdf / n-gram / 首碼等 predicate 組合），生產級 Python 實體對齊庫的候選生成層。
- `neo4j/apoc`（215★，官方擴充；主庫 bundled）——`apoc.text.levenshteinSimilarity` 等可在 Cypher 內做字串相似的過渡選項（若 fulltext CJK 不可用）。

**誠實聲明**：blocking / canopy 是資訊檢索與實體對齊的標準工程實踐，非本論文提出；本改造是「把既有全掃候選生成換成可索引 canopy、判準與門檻不變」的效能重構，佐證的是「此重構的方向與生產級先例」，不是新機制。與 §3.1.4「`DEDUP4` 節點向量化效能改造」同屬「純效能／可擴展性、不改判斷結果」的延伸——差別是後者證得了「零變化」（同 provider 同文字向量數值相同），本改造改變候選集邊界，故 §7 的 recall 對照驗證是必要條件、不是可選。
