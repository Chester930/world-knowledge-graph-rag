## 1. § 3.1.4 回填時間估算 + 查詢機制現況（摘要）

- **回填不可行（demo 前）**：現有 125 份文件、1874 個 chunk 皆是在
  `source_doc_id` 從未被賦值（3.1.4 §c 修復前）的狀態下抽取的。§b 的
  `backfill_fact_nodes()` 依賴既有 `citations_json` 裡的
  `source_svo_chunk_file` 回填 `source_doc_id`，但該欄位只在單一文件夾內
  唯一，跨 125 個資料夾會撞名，無法安全回推真正的來源文件。**唯一乾淨的
  做法是全量重新抽取，估計 24-30 小時**，明日之前不可行。折衷方案（3-5
  份短文件重新抽取，約 1-3 小時）尚待確認是否要做。
- **查詢機制現況**：BFS 圖遍歷（`bfs_query`）與 3.2 §c 查詢時關係連結
  （`resolve_query_relation_type` + `_filter_triples_by_relation_type`）
  皆已上線且運作正常；語意 Fact 檢索（`vector_search_facts`）程式碼正常，
  但因上述回填限制，目前兩個 demo KG 的 `Fact` 節點數皆為 0，**語意檢索
  在明日演示中必然回傳空結果，不是 bug，是已知限制**。
- 本節實測（§4）進一步發現：即使 BFS 本身能運作，**種子實體字面比對
  （`_find_seed_entities`，已知的「暫時方案」）在多個真實問題上導致嚴重
  雜訊**，詳見 §5。

## 2. CLI 工具

新增 `ask_question.py`（repo 根目錄），可直接在終端機輸入真實問題、取得
真實 Agent 回答，不需另外啟動 uvicorn：

```bash
python ask_question.py --list-kg
python ask_question.py --kg-id <uuid> "問題文字"
python ask_question.py --kg-id <uuid> --hops 1 "問題文字"   # 可調 BFS 跳數
```

同時擴充了 `/agent/chat` 的 SSE 串流，新增 `event: sources` 事件（見
`routers/agent.py::_serialize_sources()`），把本次實際檢索到的 BFS 三元組
與語意 Fact 結構化輸出，供人工核對「答案到底有沒有圖譜依據」——這也是
明日演示「顯示來源供評審審核」需求的後端基礎（前端尚未接線，屬後續工作）。

## 5. 關鍵發現（依嚴重性排序）

### 🔴 發現 1：題 5 出現確認過的數字幻覺，且不在既有「誠實拒答」設計的保護範圍內

`_build_prompt()` 目前只有在**完全沒有撈到任何事實**（`fact_lines` 為空）
時，才會附加「沒有依據就不要臆測具體數值」的指示。題 5 的 BFS 撈到了
675 筆三元組（其中確實包含正確的「生理假不併入病假」這條邊），所以走的
是「有事實」分支——但該分支的 prompt 完全沒有數字幻覺防護指示。結果
LLM 在**看起來有圖譜依據**的情況下，自行編造「每次不得超過4日，一年
最多16天（4天/次×4次）」，正確答案其實是一年3天。這比「完全沒依據、
誠實拒答」更危險，因為表面上像是有憑有據。

**建議**：明日演示避免使用題 5，或使用前先確認是否要修這個 prompt 分支
（把數字幻覺防護指示也加進「有事實」分支）——但這是程式碼變更，依專案
慣例應先討論後實作，本報告只如實記錄現況，未擅自修改。

### 🔴 發現 2：BFS 種子字面比對雜訊規模比先前記錄的更嚴重，且不穩定

10 題中有 6 題撈到 500 筆以上三元組（題 7 甚至 3169 筆），比題庫文件
（`docs/報告/12_...md` 的題 9 案例）記錄的「50 條邊」規模大上一到兩個
數量級。根本原因（已用真實查詢驗證，非臆測）：`_find_seed_entities()`
的字面比對沒有排除高頻通用詞——例如「工資」「雇主」「主管機關」這類
詞在 125 份勞動法文件中幾乎每份都出現，一旦被比對為種子，2-hop BFS
會直接炸開到數千筆不相關三元組。題 1（飛航組員）用真實查詢驗證與
`_find_seed_entities()` 直接呼叫的結果一致：只撈到 3 個種子（工資／
雇主／有——其中「有」是單字雜訊實體），且 2-hop BFS 撈到 0 筆——與題庫
記錄的「✅精準命中」相反，代表**這題目前無法重現先前驗證過的結果**，
明日演示前應重新確認是否要抽換題目。

實測 hops=1 可將題 5 的雜訊從 3036 筆壓到 486 筆（見對話記錄），但仍然
偏大，且本報告的正式 10 題結果全部採 hops=2（與正式 demo 端點行為一致），
未套用此緩解，如實呈現目前預設設定下的真實狀況。

### 🟡 發現 3：多題答案雖結論正確，但並非真正由圖譜事實支撐

題 8、9 是最明顯的案例：BFS 分別撈到 2588、1736 筆三元組，全部與問題
無關（都是「工資」「直轄市政府」等高頻詞牽出的雜訊），LLM 最終能答對
結論純粹是靠自己的訓練知識，而非圖譜依據——這與 demo 想傳達的「有依據
時清楚引用」的敘事有落差，演示這兩題時應誠實說明。

### 🟡 發現 4：LLM 輸出頻繁夾雜簡體字

`qwen2.5:7b` 在多題回答中間夾雜簡體字（如「根据」「这」「结论」「关键」），
儘管 prompt 已明確要求台灣地區用語。這是本地小模型指令遵從度的已知限制
（`docs/報告/12_...md` 已記錄類似現象），非本次新發現，但實測樣本更完整，
建議明日演示前抽選幾題確認呈現效果是否可接受。

### ⚪ 發現 5：關係連結（3.2 §c）在真實問題上的命中率偏低

10 題中只有 1 題（住院醫師排班）成功解析出 `resolved_rel_type`，其餘皆為
`QNOMATCH`（優雅降級，未篩選）。這與程式碼本身文件記錄的已知限制一致
（把整個問題字串而非抽取出的動詞片語餵給比對函式），非新問題，僅供佐證
「這個限制在真實資料上確實有感」。
