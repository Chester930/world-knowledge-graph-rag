### 4.1 Q5「當月一日」診斷 — 是**檢索問題**，非報告 26/32 標的「生成端 G4」

目標事實 `災害發生之當月一日起 → 前條所定災後六個月期間`（natural_text「災害發生之當月一日起 計算 前條所定災後六個月期間」）**在圖裡**（N0050030 chunk 3，doc_id `56556675…`）。

真因 = **檢索排序被淹沒 ＋ 文件範圍自舉失敗**：
- KG 內有 ~28 條「X 自 Y 起算」事實，來自**另外 7 部法**（N0050031 職災保護法 ×10、N0050039 施行細則 ×9、N0050021、N0050001、N0050025、N0060079、N0050002），全是「保險**效力**之開始自…零時起算」——與「災後保險費**期間**從災害當月一日起算」是不同概念。
- 問句「這個期間從哪一天開始起算」的 embedding 與這 28 條都近 → 唯一正解被擠出 top-N。
- `agent.py` 的檢索文件範圍是**從 top-N 語意 Fact 反推**（`_relevant_doc_ids_from_facts`）→ top-N 全是雜訊 → 推出的範圍 = {N0050031, N0050039, …}（錯的）→ 正確事實因不在範圍被 `_filter_*_by_source_doc_ids` **排除** → grounding 0/17。惡性循環。
- 加分不利：正確事實措辭尷尬（`災害發生之當月一日起` 當主詞、動詞「計算」、`前條所定災後六個月期間` 當受詞）。

**建議修法**（DRAIN-DONE 後、需 `chat()` 驗證）：
- 主要：檢索文件範圍改用 **BFS seed / concept 路由的文件**，而非「雜訊 top-N 語意 Fact 反推」。
- 次要：重抽 N0050030 chunk 3，把方向改成 `災後六個月期間 → 自災害發生當月一日起算`。
- 另一角度：報告 28 子問題分解已把 Q5 拆兩段，若第二段能繼承第一段的文件範圍即可濾掉雜訊。

## 6. 後續修正（驗證後衍生）

### ② `OLLAMA_EMBEDDING_NUM_GPU`（bge-m3 → CPU）— commit `dfad671`

8 GiB VRAM 塞不下兩模型同時常駐 GPU → 查詢路徑在 embed↔generate 之間快速切換時，Ollama 排程器反覆逐出重載 runner，導致每次 `chat()` 卡 10–20 分鐘（本輪 T1 一度反覆卡死；根因確認為此，非程式）。

- 新增 `settings.ollama_embedding_num_gpu`（env `OLLAMA_EMBEDDING_NUM_GPU`）：`None`（預設）＝請求不帶 `options`、行為零改變；`0` ＝ bge-m3 逼到 CPU（journal 確認 `--n-gpu-layers 0`），qwen 獨佔 GPU、不再互相逐出。
- T1 實測：套上此設定＋「啟動後完全不碰」（不對 Ollama 下診斷 `generate`、不中途 kill），72 次呼叫 1.9h 乾淨跑完。
- **T2（報告 27 §6.2）跑同一條路徑，在此機器上需開此選項。**

### Bug1：`num_predict` 1024 → 4096 — commit `94b9b9a`

SVO 抽取走 `generate_json`（Ollama `format=json`，輸出受語法約束成合法 JSON），但 generation 一旦在 `num_predict` 處停止，JSON 沒收尾就回傳 → `json.loads` 撞「Unterminated string」／「Expecting ',' delimiter」。列舉條文 chunk 的抽取 JSON 常 > 1024 token。

全新 KG 的 failed chunk 中 **8 個是此類**：N0060015 c3/c12、N0060031 c5、N0090064 c5、N0050039 c11、N0090031 c13、N0090002 c18、N0060009 c24（N0060016 c2 已於步驟 2 補）。

- 新增 `settings.ollama_llm_num_predict`（env `OLLAMA_LLM_NUM_PREDICT`），預設 4096；`OllamaLLMProvider.__init__` 收 `num_predict` 參數；`generate`／`generate_json` 用之；`stream`（RAG 答案生成）不設，行為不變。

### Bug2：`generate`／`generate_json` timeout 300 → 600 — commit `94b9b9a`

超大法規單一 chunk（N0030001 c11 勞動基準法、N0080044 c27）的抽取 JSON 生成 > 300 s → `httpx.ReadTimeout`。`_TIMEOUT` 類別常數 300 → 600。

### batch-reset

10 筆 failed → pending（`updated_at=datetime('now')`，欄位 NOT NULL）。修正 cherry-pick 進 `reextract-v2`（`cbb018b`＋`fa01475`）＋ 2 worker 帶 `OLLAMA_EMBEDDING_NUM_GPU=0` 重啟後，drain 自行以新設定重抽。佇列 completed=1359 / pending=1942 / processing=2 / **failed=0**。

另：平行 session 寫 `C:\Users\666\.wslconfig`（`[wsl2] memory=12GB swap=8GB`）＋ `wsl --shutdown` 套用 → 可用 RAM 回到 ~4.5 GiB、2 worker 穩定。
