## 1. 設計總覽（白話）

每個 **Fact 節點**（每筆來源引用各一個）多帶兩樣東西：
1. **目前狀態**（候選／有效／已被取代／已終止／爭議／已駁回之一）；
2. **事件清單**（只增不改，記錄「什麼事讓它換狀態」）。

「這條關係現在有效嗎」＝看它的 Fact 的狀態。邊（聚合關係）本身**不存狀態**，需要時由它底下的 Fact 推導。**沒有狀態資料的舊 Fact＝「尚未處理」**（不是候選、也不是有效）。

## 2. 欄位提案（Fact 節點）

| 欄位 | 型別 | 說明 |
| --- | --- | --- |
| `lifecycle_state` | 字串，缺席＝「尚未處理」 | 六個狀態之一（以 `relation_lifecycle` 的常數為準） |
| `lifecycle_events_json` | JSON 字串陣列，**只追加** | 仿現有 `citations_json` 慣例；每筆含 `event_type`／`effective_date`（可空，`YYYY-MM-DD`）／`reason`／`evidence_ref`／`trigger_kind`／`seq`（Fact 內單調遞增序號，供重播排序，不用時鐘） |

**區分兩種「空」**（對應你的三種標示）：
- **欄位缺席（NULL）**＝**尚未處理**：舊資料，從未經過狀態機；
- **`候選`**＝**已經過狀態機的起點**：之後新抽取的 Fact 一律從「抽取完成」事件進入候選。

狀態一律可由事件清單**重播**得到（`relation_lifecycle.replay`）；`lifecycle_state` 只是方便查詢的快取。若兩者不一致，以重播為準（可寫一個稽核腳本檢查，屬後續工作）。

## 4. 讀取端規則（對應報告233 R1–R5）

**共同鐵則：狀態過濾必須發生在「依（主詞,關係型別,受詞）去重」之前，也在 top-k 截斷之前**——否則新舊兩個 Fact 同鍵時，去重會留下分數高者，不管它是否已被取代（報告233 R2／R3 的風險）。

| # | 位置 | 規則（提案） |
| --- | --- | --- |
| R2 | `vector_search_facts` | 在 KNN 候選池取回後、`_dedupe_facts_by_key` 之前，依「可檢索狀態集合」過濾；索引與檢索流程不變 |
| R3 | `split_fact_lines`／`_expand_facts_by_article`／`_arrange_fact_lines` | 同一過濾邏輯；條文擴充也要排除已被取代者 |
| R1 | BFS（走訪邊） | **第一階段不過濾**，只在 trace 標示（邊狀態推導的成本與漂移風險高，見 §5）；之後再評估查詢時推導或維護推導欄位 |
| R4 | 接地核對 | 核對範圍＝送進 prompt 的事實行；過濾後自然跟著變，不需另改 |
| R5 | trace 影子標示 | **最先做**：Fact 檢索結果多帶 `lifecycle_state`，在既有 `semantic_marks` 旗標下顯示（舊資料＝「尚未處理」）；**不改任何行為** |

**「可檢索狀態集合」的預設不能只留「有效」**：在還沒有自動「驗證通過」流程之前，所有新抽取的 Fact 都停在「候選」，若只檢索「有效」，檢索會整個消失。**初始提案：可檢索＝{尚未處理（缺席）、候選、有效、爭議}；排除＝{已被取代、已終止、已駁回}**（爭議是否顯示標示待決定）。這個集合應是**參數**，不寫死。

## 5. 一個原型沒有涵蓋、必須先說清楚的落差：「互斥」的單位

`relation_lifecycle.check_exclusivity` 規定「**同一鍵同一時刻最多一個有效**」——這在**玩具資料**成立（一個鍵＝一個關係實例）。但在真實圖裡：
- 同一條規定被**不同 chunk／重疊切塊**重複抽取，會產生**多個同鍵的 Fact，且都是有效，這是正常的**（現有設計明說：Fact 以每筆引用為粒度）；
- 不同法規（例如母法與施行細則）也可能各自陳述同一個三元組。

所以真實的互斥**不能以「鍵」為單位**，而要以「**同一鍵、同一份條文的不同版本**」為單位——這需要一個「**版本譜系**」概念（哪一條新條文取代哪一條舊條文）。**目前資料沒有這個關係**。〔推論，未驗證〕較合理的做法是把「修法／新版取代」記成**條文層（`LawArticle`／文件層）的事件**，再**連動**到由該條文支持的 Fact（`SUPPORTED_BY`）：條文被取代 → 其 Fact 追加「新版取代」事件。這樣互斥與取代都在條文層定義，Fact 層只做連動。這也代表**取代的觸發主要來自條文／文件層，而不是逐條 Fact 判斷**。

→ **這是落地前最大的未決設計問題，也需要真實的多版本法規資料才能驗證。**

## 6. 邊狀態的推導（若需要）

在選項①下邊不存狀態。需要邊層（例如 BFS 標示）時：**邊的狀態＝其 Fact 狀態的聚合**，提案規則（待驗證）：任一 Fact「有效」→ 邊有效；全部「已被取代」→ 邊已被取代；有「爭議」→ 邊爭議；其餘依序類推。**第一階段只在查詢時推導並顯示，不寫回、不過濾。**

## 8. 風險與限制

1. **去重在過濾前**（§4）會讓已被取代的事實混進結果——任何實作都必須有「先過濾後去重」的測試。
2. **撤銷＝實體刪除**與「事件不可變」衝突（W3）；本文提案只在「從未被採信」時才允許刪除。
3. **「候選」永遠無人驗證**的風險（§4 的可檢索集合說明）。
4. **Fact 數量大**（現 16,826），多一個 JSON 屬性的儲存與回填成本需評估。
5. 本文是**設計與讀碼推論，沒有實測**；〔未驗證〕處（W4／W5 的 Fact 扁平屬性同步、§6 的聚合規則）實作前必須先查。
6. **民國日期**：`relation_lifecycle` 目前只收 `YYYY-MM-DD`；真實法規資料需先決定日期正規化規則。
7. 未涵蓋：更正（CORRECTION）事件、矛盾自動偵測、修法生效自動判定、前端顯示。
