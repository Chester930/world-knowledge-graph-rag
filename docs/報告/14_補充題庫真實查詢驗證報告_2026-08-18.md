## 4. 新發現：檢索到正確事實，但 LLM 忽略或給出相反結論

這是本輪測試最重要的新發現，不同於此前報告記錄的「沒撈到相關事實
所以幻覺」——這 3 個案例（題20、21、24）**BFS 確實撈到了直接回答問題
的正確三元組**，但 LLM 最終給出的結論與該三元組相反或無視它：

- **題24 最極端**：`vector_search_facts` 檢索結果雖為 0，但 BFS 撈到的
  2587 筆三元組中，**第一筆**就是「伙食代金-[RELATED_TO]計算平均工資時
  應併入→工資」——完全對應問題答案。系統最終卻回答「並沒有提到...無法
  得出結論」，等於直接無視了排在最前面的正確依據。
- **題21**：三元組第一筆就是「工作規則-[RELATED_TO]核備與公開揭示之
  法律效力→法律」，系統卻在結尾推論「工作規則即使未公佈也可能具有一定
  的法律約束力」——與原文「未揭示者對勞工不生效力」直接相反。
- **題20**：雜訊中段出現「春節假期調移或補班之排班與加班費計給」（即
  正確來源文件的標題本身，已被抽取為三元組），系統仍在結尾給出「仍需
  給付加班費」的錯誤結論。

**推測成因**（未驗證，僅供後續調查方向）：`_merge_fact_lines()` 把三元組
轉成純文字條列塞進 prompt，沒有任何相關性排序或加權提示——當同一個
prompt 裡混雜數百至數千筆雜訊時，即使正確答案排在第一行，LLM 也可能因
上下文過長、缺乏「這條特別相關」的顯著性標記而在生成階段被稀釋掉。這與
先前報告記錄的「BFS 雜訊規模過大」是同一根因的下游後果，但呈現方式更
危險——因為連「有正確依據」都救不回答案的正確性。

數字，而是整段話從頭到尾都在編。
