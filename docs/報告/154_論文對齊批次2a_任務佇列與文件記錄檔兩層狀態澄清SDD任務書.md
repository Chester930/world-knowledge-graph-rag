## 1. 背景（Claude 已核實的事實）

論文把「狀態」寫成單層，但程式有**兩層**，且分工不同：

| | 任務佇列（Chunk 層） | 文件記錄檔（文件層） |
|---|---|---|
| 儲存 | `task_queue.db`（SQLite），每個 `(kg_id, source, chunk_index)` 一列 | `_record.json`，每份文件一份 |
| 狀態 | `state/task_sm.py::TaskStatus`：pending／processing／pending_upload／completed／failed | `state/document_sm.py::ExtractionStatus`（enum 含同名五個值） |
| `pending_upload` | `services/extraction_worker.py::_process_one` 在 `merge_triples_to_graph` 成功**之後**才 `update_status(..., PENDING_UPLOAD)` | **沒有任何 `DocumentEvent` 轉入此值**（`DOCUMENT_TRANSITIONS`），`document_record_service.py` 也不寫入 |
| 完成 | Chunk 寫入 Neo4j 後：`pending_upload` →（記錄檔登記）→ `completed` | `record_chunk_completed()`：`completed_chunk_indices` 涵蓋 `svo_total_chunks`（或 `total_chunks`）才 `CHUNK_COMPLETED_FULL`→`completed`，否則 `PARTIAL`→`processing` |
| 失敗 | `_process_one` 的 `except`：`update_status(..., FAILED)` | 同一 `except`：`mark_extraction_failed()`（僅 `doc_folder is not None` 時）→ `MARK_FAILED`→`failed` |
| 失敗後 | **Worker 只領 `pending`**（`next_pending()`／`claim_next_pending()` 的 SQL 為 `status = 'pending'`），不會輪詢 `failed`。回到 `pending` 只有：`enqueue()`（`ON CONFLICT DO UPDATE ... WHERE status IN ('completed','failed')`，例：強制重建）或 `rebuild_from_records()`（先 `unlink()` 整個 db 再對帳）。`reconcile_missing_enqueues()`（重啟對帳，`INSERT OR IGNORE`）**刻意不重試既有 `failed`**（見 `_reconcile_doc` docstring） | **黏性**（報告133 X1-A）：`(FAILED, CHUNK_COMPLETED_PARTIAL) → FAILED`；只有 `CHUNK_COMPLETED_FULL` 才 `→ completed`；`RESET`／`REASSIGN` 回 `pending` |
| 狀態機程式接線 | `task_next_status()` **沒有任何 production 呼叫端**（僅 `TaskStatus` enum 被 `task_queue_service`／`extraction_worker` 引用；`state/task_sm.py` 檔頭標「characterization only」）；轉移實際由 SQL 實作 | `document_next_status()` 已由 `document_record_service._transition_extraction()` 實際呼叫 |

對論文的影響（報告152 §2.3／§4 的 N 類）：03:224、03:240、03:528、03:534 各自在「任務佇列」範圍內正確，但讀者會讀成「記錄檔與佇列同步寫入同一組狀態」；另 03:224／03:534 的「failed（可重試）」易被讀成「失敗即自動重試」。03:224 的 `pending_upload` 設計意圖（「重試只重送結果、不重跑 LLM 抽取」）與現行實作（單機同步寫入、寫入失敗歸 `failed`、重新處理時重跑抽取）也有落差，本批以「設計意圖 vs 現行實作」誠實標明，不改寫原設計說明。

```markdown
>
> ✅ **兩層狀態：任務佇列（Chunk 層）與文件記錄檔（文件層）（2026-09-30，報告154，對齊現況）**：上方五態指的是 `task_queue.db` 裡**每一個 Chunk 任務**的狀態（`state/task_sm.py::TaskStatus`）；文件記錄檔（`_record.json`）另有**文件層級**的 `extraction_status`（`state/document_sm.py::ExtractionStatus`）。兩者是各自維護的兩組狀態，並非「同步寫入同一個值」；本章未特別標明處，狀態一詞皆指任務佇列的 Chunk 層狀態。分工如下：
>
> - **`pending_upload` 只屬於任務佇列**：文件記錄檔沒有任何事件會轉入此值。
> - **文件記錄檔只登記進度與文件層結果**：Chunk 完成時由 `record_chunk_completed()` 把該 `chunk_index` 記入 `completed_chunk_indices`，全部 Chunk 都完成才轉為 `completed`，途中為 `processing`；抽取失敗時由 `mark_extraction_failed()` 標 `failed`。文件層 `failed` 具**黏性**：其後即使個別 Chunk 又成功完成，只要尚未全部完成，狀態仍維持 `failed`，只有涵蓋全部 Chunk 的完成事件才會轉為 `completed`（報告133 X1-A）；重設與重新歸屬（`reset_extraction_progress()`／`append_assignment()`）則回到 `pending`。
> - **實際轉換順序**：Worker 領到 Chunk，佇列標 `processing` → 抽取、繁體化、`merge_triples_to_graph()` 寫入 Neo4j → 佇列標 `pending_upload` → 記錄檔 `record_chunk_completed()` → 佇列標 `completed`（`services/extraction_worker.py::_process_one`）。上方「三態轉換的實際時機」一句是設計時的劃分，實際轉換以此順序為準。
> - **`pending_upload` 的設計意圖與現行實作**：設計意圖是區分「本地抽取完成」與「送達知識圖譜」，使寫入失敗時只需重送結果、不必重跑 LLM 抽取；現行實作為單機同步寫入，`pending_upload` 實際上只是「已寫入圖譜、尚未登記完成」的極短過渡態，抽取或寫入圖譜拋出例外一律歸入 `failed`，該 Chunk 重新處理時會重跑抽取，尚未做到上述分離。
> - **`failed` 的重試語意**：Worker 只領取 `pending` 的 Chunk，`failed` 不會被自動輪詢；Chunk 層 `failed` 只在 `enqueue()` 重新登記（如強制重建）或索引損毀時由 `rebuild_from_records()` 重建索引後才回到 `pending`。程式重啟時的對帳（`reconcile_missing_enqueues()`）刻意不重試既有 `failed`，避免對真正壞掉的 Chunk 反覆重跑。
```
