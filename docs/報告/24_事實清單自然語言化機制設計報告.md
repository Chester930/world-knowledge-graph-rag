# 24．事實清單自然語言化機制設計報告

**日期**：2026-09-01
**狀態**：🟡 設計已定案，**尚未實作**——依本專案「先整理資料、定案設計，待使用者確認後才動工」的既有工作慣例，本報告完成分階段任務書後待使用者逐階段確認。

## 1. 背景

[報告23](23_生成端事實清單排序機制優化設計報告.md) §6.4 用乾淨對照實驗確認：報告22題3失效案例的根因不是位置，而是 `routers/agent.py::_merge_fact_lines()` 把三元組拼接成 `f"- {subject}（{subject_type}）{verb}{object}（{object_type}）"` 這種樣板文字太生硬——只把目標事實改寫成自然語句，位置不變，LLM 就立刻引用了。位置工程（排序、截斷、zigzag重排）已到極限，需要一條新的技術線：把結構化三元組轉換成自然語言文字，即NLP領域既有的「triple verbalization／KG-to-Text」任務。

## 2. 與既有設計決策的關係釐清——不與 KAPING 的既有結論衝突

**重要**：本專案 `services/svo_service.py::_verbalize_fact()`（3.1.4 §a，事實層級向量化）的 docstring 已引用 KAPING（Baek, Aji & Saffari, 2023）的 Appendix B.5 消融實驗，主張「簡單串接優於訓練過的 graph-to-text 轉換模型」，並據此選擇「subject＋原始verb＋object」直接串接、不引入額外轉換模型。這與本報告現在要提出的「自然語言化」表面上矛盾，必須先釐清：

**KAPING 的實驗範圍是「embedding 檢索表現」，不是「LLM 生成階段的引用利用率」**——查證 `docs/參考文獻/12_三元組事實層級向量化與檢索/README.md`（已全文精讀）確認：KAPING 比較的是「簡單串接」vs.「訓練過的轉換模型」何者做成 embedding 後**檢索**更準，發現複雜轉換模型有時「生成語意偏離原三元組的文字」，反而拖累檢索精確度。這是**上游檢索階段**的問題；本報告 §6.4 對照實驗驗證的是**下游生成階段**——已經檢索到、位置也對的事實，LLM 是否會在生成答案時**引用/利用**它——這是完全不同的問題面向，兩者的最佳表徵方式不需要相同。

**兩個結論可以同時成立、不矛盾**：
- `_verbalize_fact()` 產生的 `fact_text` 用於 **embedding 相似度檢索**（`Fact.fact_embedding`）——維持簡單串接，KAPING 的結論在此仍然適用，本報告不建議變動這一用途。
- `_merge_fact_lines()` 組裝的 prompt 文字用於 **LLM 生成階段的閱讀與引用**——這是本報告要解決的新問題，KAPING 未測試過這個面向。

**風險提示（從 KAPING 借鏡）**：KAPING 觀察到訓練式轉換模型「有時生成語意偏離原三元組的文字」——這對本報告的 LLM 改寫方案是直接的風險警示：改寫必須忠實於原三元組語意，不能在追求「通順」的過程中引入幻覺或偏離。設計時需要納入忠實性防護（見 §5 階段4），呼應本專案既有 [報告20](20_抽取數值忠實性核對機制設計報告.md) 「比對生成內容與原始依據」的既定架構精神。

## 4. 設計決策：抽取階段預存自然語句，比照既有 3.1.4 §b 回填批次任務架構

**方案選擇**：報告23 §7 列出三個候選（規則式模板／查詢時LLM改寫／抽取階段預存），本報告選擇**抽取階段預存**（對應 microsoft/graphrag 的索引階段先例），理由：

1. **零查詢時延遲增量**——現行 `/agent/chat` 已有草稿生成＋接地核對（必要時再生成）的多輪 LLM 呼叫，實測常破百秒（見報告22/23真實測試記錄），查詢時再加一次改寫呼叫（方案b）會讓延遲雪上加霜；抽取階段的 LLM 呼叫成本本來就存在，多一次呼叫不影響使用者體感延遲。
2. **複用本專案已驗證的架構模式**——`services/svo_service.py::backfill_fact_nodes()`（3.1.4 §b）已經是「即時路徑＋一次性回填批次任務」這個雙軌模式的落地先例，本報告完全比照此架構，不是全新的設計典範。
3. **不需要重新抽取任何 chunk**——現有已抽取的 `citations_json` 完整保留 `subject`／`verb`／`object`／型別等欄位，回填只需要對既有邊補算自然語句，不動抽取管線本身，正在進行中的3303-chunk乾淨重跑不受影響、不需要重跑。

**Schema 設計**：關係邊新增 `r.natural_text`（字串屬性），儲存這條邊「最新一次生成」的自然語句版本。**不是**存進 `citations_json` 每筆 citation 各自一份——因為 `_merge_fact_lines()`／`SVOTriple.verb` 現行都只取 `citations[-1]`（最新一筆citation）代表整條邊，`natural_text` 沿用同一顆粒度即可，不需要為每筆歷史 citation 各自保存自然語句版本（那些舊版本從未被查詢端使用過）。

## 5. 分階段任務書（Spec-Driven Development）

依報告19/20/21/23 已建立的「先設計、後動工，每階段獨立可測試」慣例拆解如下。**每個階段完成後才進入下一階段**，階段間有明確驗收標準，不是一次性全部寫完。

### 階段1：即時路徑——`merge_triples_to_graph()` 掛載自然語言化生成

**範圍**：新增 `_naturalize_triple(subject, subject_type, verb, object_, object_type, llm_provider) -> str`（`services/svo_service.py`），用既有 `LLMProvider.generate()` 零樣本呼叫，把結構化欄位改寫成一句通順中文。掛載到 `merge_triples_to_graph()` 現有的邊寫入邏輯裡（比照 `verb_embedding` 掛載模式，`llm_provider is not None` 時才呼叫，缺席時優雅降級——`r.natural_text` 缺席，消費端沿用舊版樣板拼接）。

**驗收標準**：
- 新增函式有單元測試（fake LLM provider，驗證prompt內容、驗證回傳值正確寫入 `r.natural_text`）。
- `llm_provider=None` 時完全不呼叫、不寫入 `natural_text`（維持既有可選依賴的優雅降級慣例）。
- 全專案既有測試無回歸。

### 階段2：回填批次任務——`backfill_natural_text()`

**範圍**：比照 `backfill_fact_nodes()` 的既有簽章與冪等性設計（`services/svo_service.py::backfill_natural_text(driver, kg_id, llm_provider, *, batch_size=100) -> int`）：掃描指定 `kg_id` 內所有缺少 `r.natural_text` 的邊，逐一呼叫階段1的 `_naturalize_triple()` 補上，回傳實際新建立筆數。定位為「人工觸發的一次性腳本」（比照 `backfill_fact_nodes()` 的判斷理由：階段1的即時路徑已覆蓋所有新寫入，缺口是純歷史性的，不會持續產生新缺口），不接進 `run_governance_worker()` 定期巡視週期。

**驗收標準**：
- 冪等性測試（已有 `natural_text` 的邊跳過、無 `citations_json` 的邊跳過）。
- 分頁邏輯測試（比照 `test_backfill_fact_nodes_paginates_across_multiple_batches`）。
- 對新KG（`c15949bf`）已抽取完成的部分邊做真實小規模回填驗證，人工檢查生成的自然語句是否忠實、通順。

### 階段3：消費端整合——`_merge_fact_lines()` 優先使用 `natural_text`，缺席時 fallback

**範圍**：`routers/agent.py::_merge_fact_lines()` 改為：`r.natural_text` 存在時直接使用該句子（不再套用「主詞（型別）動詞受詞（型別）」樣板）；缺席時 fallback 回現行樣板拼接（graceful degradation，不因為某些邊還沒回填就整體失效）。`_verbalize_fact()`（Fact 節點的 `fact_text`／`fact_embedding`）**維持現狀不變**（見 §2 的 KAPING 釐清，此用途不動）。

**驗收標準**：
- 單元測試涵蓋「有 natural_text」「無 natural_text」兩種情境的輸出正確性。
- `tests/routers/test_agent.py` 既有測試無回歸（尤其是報告23新增的 `_score_lines_by_embedding`／`_arrange_fact_lines`／`_litm_reorder` 系列測試，需確認排序邏輯對 `natural_text` 版本的文字一樣適用，不依賴文字格式本身）。

### 階段4：忠實性防護（呼應 §2 KAPING 風險提示、報告20既定架構精神）

**範圍**：評估是否需要對 `_naturalize_triple()` 的輸出做輕量忠實性核對——例如確認改寫後的句子仍包含原始 `subject`／`object` 的關鍵詞（避免LLM在「順暢化」時偷換主詞受詞），或至少人工抽查一批真實回填結果評估幻覺率。**是否需要獨立的正式核對機制（比照報告20的regex比對），或抽查已足夠**，留待階段2真實回填驗證後依實際觀察到的幻覺率決定，本報告不預先假設答案。

### 階段5：真實驗證與測試計畫

**範圍**：完成階段1-3後，重跑報告22題3案例（現在應該已經有真實的 `natural_text` 可用，不需要再手動改寫），驗證是否解決；並在更多既有測試案例（報告18-23已用過的題目）上做回歸檢查，確認自然語言化沒有引入新的失效模式（例如自然語句省略了原本樣板拼接會保留的型別資訊，導致某些需要型別區分的問題答錯）。

## 6. 誠實侷限

- `natural_text` 只在「最新一次生成」時準確反映 `citations[-1]` 的 `verb`——若某條邊之後又累積了新的、`verb` 措辭不同的 citation，階段1的即時路徑會在下次寫入時重新生成、覆蓋，但**回填批次任務跑過的時間點之前累積、之後未再更新的邊**，`natural_text` 可能與當下最新 citation 的 `verb` 有些微落差（機率低，但理論上存在）——這是與 `backfill_fact_nodes()` 相同性質的既有已接受風險（見3.1.4 §b冪等性說明的「極窄競態視窗」慣例），非本報告獨有。
- LLM 改寫本身無法 100% 保證忠實（見 §5 階段4），且引入了額外的抽取階段 LLM 呼叫成本（雖不影響查詢延遲，但會拉長抽取批次的整體時間，目前3303-chunk清單重跑本身已經是多日的工作，需評估是否要等現有重跑完成後才開始回填，或並行處理）。
- 本設計只解決「三元組格式化文字生硬」這一個具體根因，不保證解決所有生成端事實遺漏案例——報告22/23已經記錄過位置工程、抽取管線本身在其他案例上運作良好，本報告聚焦的是報告23 §6.4已經用真實對照實驗鎖定的這一類問題。
