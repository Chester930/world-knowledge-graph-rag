## 2. 修法設計

### 2.1 `services/semantic_span_matcher.py`（新模組）

```python
async def match_spans_with_fallback(pool_text, spans, judge_llm_provider, *, question=""):
    # 先逐字子字串比對（與舊版規則完全相同）
    # 仍缺漏 且 有 judge_llm_provider 時，才批次呼叫一次 LLM 做語意蘊含核對
    # LLM 回傳格式錯誤時保守視為未核對成功，不假裝已核對過
```

逐字命中的項目完全不觸發 LLM 呼叫（零額外成本）；只有缺漏項目才補判一次，且是**批次**（同一題的所有缺漏 span 一次 prompt），不是逐 span 各呼叫一次。

### 2.2 `AtomicScorer.evaluate_async()` / `LineageTracker.*_async()`

兩處都比照上述模式新增異步版本，`judge_llm_provider=None` 時退化為與舊版逐字比對完全相同的結果（測試 `test_atomic_scorer_evaluate_async_no_judge_matches_sync`／`test_record_retrieval_async_no_judge_matches_sync` 驗證）。舊版同步 `evaluate()`／`record_retrieval()` 完全未改動，正式產品的 `chat()` 路徑不受影響。

`LineageTracker.diagnose_failure_async()` 的 Stage 3 判定也同步套用語意 fallback，並用 `test_atomic_scorer_evaluate_async_keeps_real_smoothing_error()`／`test_diagnose_failure_async_stage3_keeps_real_smoothing_error()` 驗證 26-Q5「當日」平滑化這種**內容確實不同**的真錯誤，語意 fallback 不會誤救。

新增 12 個單元測試（`tests/services/test_semantic_span_matcher.py`、`test_evaluation_metrics.py`、`test_lineage_tracker.py` 各補），全套 pytest 919 綠（906 舊 + 13 新，含 agent.py 相關測試異動）。

## 3. 過程中發現並修復的兩個真實 bug

這兩個 bug 解釋了「為什麼 Stage 1/2 血統資料本身就是空的、無從重評」，不是本次修的比對邏輯造成的，但直接卡住了重評分的可行範圍：

### 3.1 `scripts/eval/run_rq1_comparison.py`：M1/M2 的 `retrieved_texts` 恆為空字串

```python
retrieved_texts = [h.get("text", "") for h in hits]   # 舊版：key 打錯
```

`baseline_rag_service.search_baseline()` 回傳的 dict key 是 `"chunk_text"`，不是 `"text"`——`.get("text", "")` 永遠拿到 `""`。實測驗證：120 筆裡 M1/M2 的 `lineage.stage1_retrieval.recall_rate` **全部是 0.0**，代表 `failure_attribution` 欄位對 chunk-RAG 基準從頭到尾都誤判成「Stage 1 Retrieval Failure」——不影響 `atomic_score`（獨立從 `answer` 算），但報告52 §2 表2「典型缺陷全鏈路血統歸因」那張表對 M1/M2 完全失真。已修正為 `h.get("chunk_text", "")`（`scripts/eval/run_rq1_comparison.py`）。

### 3.2 `routers/agent.py::_serialize_sources()`：`fact_id`／三元組 `natural_text` 從未序列化進 SSE payload

`vector_search_facts()` 其實有回傳 `fact_id`（`elementId(node)`），但 SSE `"facts"` 事件的 dict 組裝時漏掉這個欄位；BFS 三元組的 `SVOTriple.natural_text` 同樣沒被序列化進 `"triples"` 事件。`run_rq1_comparison.py::fact_ids = [f.get("fact_id","") for f in r["facts"]]` 因此永遠拿到空字串——這是 M3/M4 的 Stage 1/2 血統資料完全無法回溯重建原文的根因。已補上這兩個欄位（`routers/agent.py`），**未來的評測跑測**能正確記錄 M3/M4 的檢索原文；但無法回溯修補這批已經落盤的 120 筆舊資料。

## 4. 重評分結果

### 4.1 Pareto 矩陣：修正前後對照

| 方法 | 修正前 Acc | 修正後 Acc | Delta |
|---|---|---|---|
| M1 (B0) | 68.9% | **91.1%** | +22.2pp |
| M2 (B1) | 70.6% | **96.1%** | +25.6pp |
| M3 (F) | 30.0% | **70.0%** | +40.0pp |
| M4 (K) | 32.2% | **66.7%** | +34.4pp |

四個 arm 全數上升；M3/M4 漲幅明顯大於 M1/M2（印證報告52 的假設方向：KG 路徑的用詞改寫吃虧更重），但 M1/M2 也顯著上升——代表字面比對偏誤不是 KG 獨有（18-Q5 就是 M1 本身也被誤判的案例，報告52 已指出過同一現象），chunk-RAG 生成端一樣會有「答案內容對、但沒有逐字照抄法規句式」的情況。

120 筆裡有 **38 筆 `is_perfect` 判定從 False 翻轉為 True**，且**沒有任何一筆從 True 翻成 False**——語意 fallback 只救回假陰性，沒有引入新的假陽性（測試層面也用 26-Q5「當日」平滑化案例驗證過這個不對稱性）。

### 4.2 逐案例：17-Q1（婚假八日）完全翻案

報告52 引用的鐵證案例——M3/M4 回答內容完全正確（「勞工結婚可以請八日婚假...工資照給」），語意 fallback 後 3 個 run 全部翻成 `is_perfect=True`，且 Stage 1 血統也一併修正為「Success」（M3 因 fact_id 缺失無法重建 Stage1 原文而維持原判定；但 atomic_score 本身已正確反映答案內容無誤）。

### 4.3 仍然真實存在的缺陷案例（語意 fallback 沒有、也不該救回）

- **18-Q5**（特別休假日數分級）：M1/M2/M3/M4 全部仍有缺陷，`failure_attribution` 顯示多次真實的 Stage 1（檢索沒撈到）或 Stage 3（生成端漏掉分級細節）失敗——這是真正的檢索/生成能力落差，不是測量偏誤。
- **26-Q5**（起算日「當月一日」）：M3/M4 依然常態性缺陷（Stage 1 Retrieval Failure，與報告41/50 一致，是已知的 Fact-RAG 語意排名限制，非本次範圍）。

## 5. 對 RQ1 的重新解讀

修正前的「M1/M2 遠勝 M3/M4」大部分是測量偏誤；修正後差距收斂到 ~21～29pp，但**方向沒有反轉**——KG-based 方法在這 10 題樣本上依然落後 chunk-RAG 基準。可能原因（未驗證，留給後續）：

1. Fact-RAG 全域語意排名限制（報告41/50 已記錄的 26-Q5 案例）本身仍然存在，只是不再被字面比對放大成看起來更嚴重。
2. 18-Q5 這類「答案需要列出多個分級條件」的題目，KG 路徑把法規條文拆成 SVO 三元組後，可能真的比 chunk-RAG 整段保留原文更容易漏掉細節——這才是需要進一步查證的 KG 真實弱點，而不是測量工具的問題。
3. 樣本量仍然只有 10 題，跟報告39 §4.1 建議的「效果大且方向一致時不必湊滿樣本」相反，這次差距沒有大到能一次下定論，仍需更大樣本。
