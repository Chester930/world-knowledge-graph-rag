## 1. 最重要的發現：事實在圖裡有「兩層」

〔事實〕
- **邊層（聚合）**：`merge_triples_to_graph()` 以 `MERGE (s)-[r:{rel_type} {kg_id}]->(o)` 建邊（`services/svo_service.py:1222`），**同一組（主詞、關係型別、受詞）只會有一條邊**，每筆來源引用累積進 `r.citations_json`（`:1223,1239`），`confidence` 取所有引用的最大值（`:1240`）。
- **Fact 層（每筆來源引用一個節點）**：`_create_fact_node()`（`:1072–1150`）對**每筆 citation 各 `CREATE` 一個 `Fact` 節點**，帶 `subject／object／rel_type／verb／confidence／fact_text／fact_embedding／source_doc_id`，並以 `SUPPORTED_BY` 連到來源（`Chunk` 或 `LawArticle`，`:1135`）。該函式與 `merge_triples_to_graph` 的 docstring 都明說：Fact 以「每筆引用」為粒度、邊以「三元組」為粒度收斂（`:1182–1184`）。

〔推論〕**「新舊法」恰好是「同一組三元組、不同來源文件／條文」**——在邊層會被收斂成一條邊（無法分開生命週期），但在 Fact 層本來就是不同節點。所以**狀態機最自然的載體是 Fact 層**，不必動邊的鍵；邊層的狀態可以由其 Fact 推導（例如：任一 Fact 有效則邊有效）。這與報告229 §4 說的「關係實例」不必等於新的圖結構——**Fact 節點本來就是關係實例的候選**。

## 3. 儲存選項（〔推論〕；請你選）

| 選項 | 做法 | 優點 | 缺點／風險 |
| --- | --- | --- | --- |
| **①　Fact 層屬性＋只增不改的事件清單（建議）** | 在 Fact 節點加 `lifecycle_state` 與 `lifecycle_events_json`（仿 `citations_json` 的慣例，只追加不覆寫）；邊層狀態由 Fact **推導**（查詢時或寫回） | 不動邊的鍵、不動 BFS 語意；Fact 本來就是每筆來源一個；新舊法自然分開；沿用專案既有 JSON 屬性慣例 | 要改 W1／W3（撤銷不再實體刪除）／W4（合併規則）；R1 的 BFS 仍需邊層推導；Fact 數量大（16,826） |
| ②　邊層屬性 | 邊上加 `lifecycle_state` | 最簡單 | **無法表達多段生命週期**（即原本要解決的問題）；不建議 |
| ③　獨立「關係實例節點」 | 為每個關係建 `(:RelationInstance)`，邊改連到它 | 概念最乾淨（類似 GAP-06 Relator） | 動到 BFS 走訪深度定義（`:1174–1177` 的 docstring 已警告）、查詢與回填成本最高 |
| ④　獨立事件日誌節點 | `(:LifecycleEvent)-[:ABOUT]->(:Fact)` | 與使用者 Round 3 的事件溯源最一致 | 節點數大增；查詢要重播；與 ① 可併用但複雜度更高 |

**我的建議：①**（理由：改動面最小、與現有「Fact＝每筆來源」模型吻合、可逆性最好）。落地順序建議（**每一步都需你另外同意**）：

1. **設計文件**：把 ① 的欄位、W1–W6 的規則、R2／R3「先過濾後去重」寫成設計說明（只有文件）。
2. **在拋棄式測試圖驗證**（**不得使用 KG#4、也不要在 `kg2-neo4j` 容器內寫入**——KG#4 是唯一副本；建議另起一個臨時 Neo4j 容器，用虛構 Fact 驗證 W1／W3／W4／R2／R3 的行為）。
3. **影子顯示**：先在 trace 以 R5 顯示狀態（既有資料＝無狀態）。
4. 之後才談寫入端改動、回填策略、與檢索過濾（這些都改行為，需評測）。
