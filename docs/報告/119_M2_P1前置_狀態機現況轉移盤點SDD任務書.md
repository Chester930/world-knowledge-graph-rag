## 0. 目的

M2 的鐵則是「整理前後行為完全不變」。P1 要把散落的狀態寫入集中成 Enum＋轉移表＋單一 `transition()` 入口。**轉移表必須照「現況實際會發生的轉移」寫，不能照理想寫**，否則就是改行為。所以動手前先盤點：

- 有哪些狀態？誰寫、誰讀？
- 現況實際允許哪些轉移（含看起來不合理但目前會發生的）？
- 哪些寫入會靜默失敗或被覆寫？

本任務產出的「現況轉移矩陣」是下一份任務書（報告121：SM 化實作）的**唯一依據**。

## 2. 步驟

### S1　純閱讀
依序回答 Q1–Q9（Read／git grep，不執行程式）。**自我檢查**：Q2、Q5 的矩陣每個非空格子都必須有證據行號；X1、X2、X3 必須各有明確結論（成立／不成立＋依據）。

### S2　暫存目錄離線特性重現（不碰 Neo4j）
在系統暫存目錄建立腳本（風格參照報告109 附錄 A、報告116 附錄 A），對 SM-1 與 SM-2 各做**特性重現**：

1. **SM-1**（用 `tmp` 資料夾＋`chunk_and_stage()` 建 `_record.json`，直接呼叫 `document_record_service` 函式）：
   - 序列 A：`init/append_assignment` → `record_chunk_completed(1)`（`svo_total_chunks=3`）→ 觀察 `extraction_status`；
   - 序列 B（X1）：`mark_extraction_failed` → 之後對另一個 chunk 呼叫 `record_chunk_completed(2)` → 觀察 `extraction_status` 是否仍為 `failed`；
   - 序列 C：三個 chunk 依序完成（total=3）→ `completed`；再 `reset_extraction_progress` → `pending`；
   - 序列 D：對「不存在的資料夾」呼叫三個寫入函式，記錄回傳值與是否拋例外（X3）；
   - 序列 E：`append_assignment` 在 `completed` 狀態下再呼叫 → 是否重置為 `pending`。
2. **SM-2**（用 `tmp_path` 內的 sqlite 檔）：
   - `enqueue` → `claim_next_pending` → `update_status(pending_upload)` → `update_status(completed)`；
   - 對 `completed`／`failed`／`processing`／`pending_upload` 各狀態的列再次 `enqueue`，記錄哪些被重置為 `pending`；
   - `reset_stuck_processing` 對各狀態的效果；
   - 對**不存在**的列呼叫 `update_status`（X3）；
   - **非法轉移**：直接 `update_status` 做 `completed → processing`、`failed → completed`、`pending → completed`，記錄是否都被接受（證明目前不驗證）。
3. 以表格輸出每個序列的「輸入 → 觀察到的狀態」，作為 P1 特性測試的黃金依據。

**自我檢查**：腳本可執行且全程不連 Neo4j／Ollama／server；缺依賴時寫下錯誤與嘗試，**不得為了跑通而修改 repo**；重現未完成須說明原因；腳本全文貼附錄。

### S3　判定與建議
- 對每個狀態寫入點標 `集中候選`（P1 應改為呼叫 `transition()`）、`保留原樣`（不是狀態轉移，例如只改進度數字）、`需另案`（涉及行為變更，例如修 X1）。
- **列出「P1 若要保持行為不變，轉移表必須容許的『不合理』轉移」**（例如 X1 若成立，就要在轉移表保留 `failed → processing`，並在旁註明這是既有行為、另案再修）。
- 列出建議的 P1 切分（例如：先 SM-2、後 SM-1；或反之）與各自的風險，**只列選項，不下最終決定**。
