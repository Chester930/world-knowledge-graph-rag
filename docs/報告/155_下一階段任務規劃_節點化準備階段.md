## 4. 各任務規格

### T1：N9、N10 節點卡

**目的**：驗證節點卡格式，並把 P2 搬移後的節點邊界寫成可交接的一頁。
**位置**：`services/retrieval/NODE.md`（N9）、`services/context/NODE.md`（N10）。
**格式**：依草案 §6.1（目的與規劃狀態、節點約定表、結構圖、決策槽、擁有的 SM、ports 與設定、論文章節與報告、測試、已知缺口）。
**內容原則**：

- **只寫經程式碼核對的事實**；設計中的內容（決策槽、ports、規劃中的內部節點）一律標註「規劃」；查不到的標「未核對」，不得推測。
- **節點成員要寫出現在的實際位置**：N9 的葉節點（報告95 §11 的 N9.1–N9.8）與 N10（§12 的 N10.1–N10.7）逐一對應到函式與檔案，**包含仍在 `routers/agent.py`、`services/svo_service.py` 的**（例如 `_arrange_fact_lines`、`_find_seed_entities`、`bfs_query`）。
- 決策槽欄位引用草案 §3.2 的 `GRAPH_PRUNING`、`FACT_RETRIEVAL_MODE`、`ARTICLE_EXPANSION`、`KG_RETRIEVAL_DEPTH`（N9）、`KG_CONTEXT_MODE`（N10），皆標「規劃／登記」。

**驗收**：(1) 每個葉節點對應的函式都真實存在（逐一以 AST 或 grep 核對）；(2) 「仍在原處」的名稱沒有被誤寫成已搬移；(3) 程式碼零變更（`git diff` 只有 `*.md`）；(4) 連結可解析。
**禁止**：不改任何 `.py`；不建立 `contract.py`／`ports.py`／`flow.py`（屬後續）；不在卡中寫未定案的決定（如目錄結構重組）。

### T2：節點卡檢查腳本（警告模式）

**依據**：草案 §6.2；警告或擋合併屬 §10.2a #9，**本階段採警告模式（可逆）**。
**位置**：`scripts/analysis/check_node_cards.py`、`tests/scripts/test_check_node_cards.py`。
**行為**：

1. 掃描所有 `**/NODE.md`；抽出卡中標為「已實作」的函式名，確認在其所屬檔案以 AST 找得到（不符則警告）。
2. 節點資料夾內的模組不得 import 其他節點資料夾的內部模組（沿用 P2 已有的「反向依賴 AST 測試」做法）。
3. 預設只印警告、exit 0；`--strict` 才以非零結束。
4. 測試以**暫時建立的假節點卡**驗證：能偵測到「函式不存在」「跨節點 import」「卡內宣稱已搬移但實際仍在原處」三種情況。

**驗收**：新增測試通過、完整回歸不下降、對 T1 的兩張真卡預設模式無警告（若有，須判定是卡的錯還是腳本的錯）。**禁止**：不接進 CI／pre-commit；不改 production 程式。

### T3：Neo4j 操作只讀盤點

**目的**：為 `GraphStorePort` 的介面形態（薄或語意）提供資料，**本任務只提供資料，不做介面決定**。
**範圍**：`services/`、`routers/`、`repositories/`、`scripts/`（非一次性腳本）中所有存取 Neo4j 的位置，**含包裝函式**（例如 `svo_service.py` 的 `_execute_with_constraint_retry`；**此為已知一例，不保證是唯一包裝，須自行找全**），不得只靠單一 grep 樣式。
**產出**：報告（沿用報告138 的盤點格式）——

| 欄位 | 內容 |
| --- | --- |
| 位置 | 函式、`檔案:行號` |
| 操作種類 | 讀／寫；實體寫入、關係邊合併、Fact 節點、向量檢索、圖遍歷、索引建立、回填維護、文件／條文節點… |
| 觸及的標籤與關係 | 節點標籤、關係型別 |
| Neo4j 專屬功能 | 向量索引程序、`CALL` 子查詢、`UNWIND`、`MERGE` 等 |
| 呼叫層 | 是否在 `repositories/` 之外（層次違反） |
| 測試補丁目標 | 有哪些測試 patch 了它（re-export 陷阱依據） |

並附：各種操作的數量彙整、Neo4j 專屬功能清單、「在 `repositories/` 之外直接寫 Cypher」的位置清單。可以附「薄介面 vs 語意介面各自涵蓋多少操作」的**量化觀察**，**不得下結論**。
**驗收**：抽樣 5 處回原碼核對；有一個獨立來源（另一種搜尋方式）交叉檢查沒有漏掉存取位置；程式碼零變更。

### T4：N4 依賴與副作用只讀盤點

**目的**：為 P3 與 S6 的共同前置，辨識 N4 可整組移動的最小封閉集，以及搬移前必須處理的副作用。
**範圍**：`services/svo_service.py` 中屬 N4 的函式（報告97 §6.4：`_svo_prompt`、`extract_svo_triples*`、`_find_uncovered_sentences`、`_reconcile_rel_type`、`classify_relation_by_embedding`、數值／子句守衛、`traditionalize_triples` 及其相關輔助）。
**產出**：報告——對每個函式：(1) 檔內相依的輔助函式與模組常數；(2) import 與對 `core.config`／`KGConfig` 的讀取；(3) **副作用**，含 `svo_service.py:426-433` 的 EXPAND 候選與 ESCALATE3 事件寫入 SQLite，及任何其他寫入；(4) 外部呼叫者（含 scripts、tests）與**測試補丁目標**（re-export 陷阱：只有 `patch("...svo_service.X")` 形式的補丁在搬移後會失效）；(5) 能整組移動的**最小封閉集**與搬移時會被拖帶的東西。
**另需回答（決議 Q8 的等價風險）**：EXPAND 池**誰在什麼時候讀**（`expand_worker` 的觸發條件與批次大小）；若改成「N4 回傳事件、由呼叫端在回傳後寫入」，寫入時間點從「函式途中」延後到「該 chunk 抽完之後」，會不會改變治理 Worker 看到候選的時機，並**列出會造成差異的具體情境**；不能只靠讀程式判定者，標「需實測」。
**驗收**：抽樣 5 個函式回原碼核對相依；外部呼叫者清單以兩種搜尋方式交叉；程式碼零變更。
**禁止**：不搬移任何程式；不做 S6／P3 先後的建議。
