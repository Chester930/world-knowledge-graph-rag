- **H6：符合預測。** 額外屬性不造成既有檢索／回填／撤銷函式錯誤；回填會保留它們，但撤銷的現行實體刪除會連同節點一起移除。

### V2／W4／H1、H2：簡繁合併

同一合成 KG 先建立純改名與撞名兩支；來源暫存資料夾只供 production 函式讀取，結束時刪除。

- 第一次 production `backfill_traditionalize_entity_names` 的合計統計：`renamed=2`、`merged=1`、`edges_moved=1`、`edges_unioned=1`、`edges_dropped=0`。第二次執行全欄位皆為 0。
- 純改名：Fact 存活，`HAS_SUBJECT`／`HAS_OBJECT` 已指向 `職員A`／`職務A`；Fact 扁平 `subject`／`object` 仍是 `职員A`／`职務A`，生命週期屬性仍在。
- 撞名：簡體 Entity 被移除，兩個 Fact 都存活且都連到繁體孿生 `職員B`；兩個 Fact 的扁平主詞仍分別是 `职員B`／`職員B`。
- 撞名的兩個 Fact 經 production `vector_search_facts(top_k=2)` 都返回；其去重鍵分別為 `("职員B", "RELATED_TO", "目標B")` 與 `("職員B", "RELATED_TO", "目標B")`。
- **H1：符合預測。H2：符合預測。**

### V3／W5／H3、H4：改邊型別

- production `backfill_related_to_edges` 透過 Neo4j 關係向量索引、8 維決定性假 embedding 與固定回答「是」的假 LLM，實際升級 1 條邊為 `APPLIES_TO`。
- 新邊保留 `citations_json` 與 `confidence`；Fact 的扁平 `rel_type` 仍為 `RELATED_TO`。
- 將 BFS 側 `APPLIES_TO` 三元組與 Fact 側 `RELATED_TO` 事實行交給 production `split_fact_lines`，兩側各保留 1 行，形成跨層重複。
- **H3：符合預測。H4：符合預測。**
- 未預期發現：production 改建新型別邊時沒有複製 `verb_embedding`；這是額外的 W5 寫入規則缺口，並未改 production。

### V4／H5：腳本內同步提案

只在驗證腳本執行同步 Cypher：

- 以 `HAS_SUBJECT`／`HAS_OBJECT` 反查 Entity 名稱，第一次修正 2 個 Fact，第二次修正 0 個；純改名與撞名的扁平名稱因此與目前連結的 Entity 同步。
- `rel_type` 不能只靠 Fact 的兩條 HAS 邊推得；腳本另以「端點間只有一種帶 `kg_id` 的關係型別」作為保守條件，只對 W5 fixture 執行。第一次修正 1 個 Fact 為 `APPLIES_TO`，第二次為 0。
- **H5：符合預測（在明確、唯一關係型別的合成情境下）。** 這是驗證用提案，不是 production 接線建議。
