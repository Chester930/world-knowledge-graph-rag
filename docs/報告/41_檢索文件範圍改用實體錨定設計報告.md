## 1. 問題

### 1.1 現況（`routers/agent.py::chat()`）

```
question_vector = encode(question)
fact_results   = vector_search_facts(kg_id, question_vector, top_k)         # 語意 Fact 檢索
semantic_doc_ids = _relevant_doc_ids_from_facts(fact_results, top_n=5)      # ← 從 top-N Fact 反推文件範圍
relevant_doc_ids = _intersect_doc_scopes(semantic_doc_ids, scope_doc_ids)
seeds  = _find_seed_entities(kg_id, question, ...)                           # ← 種子實體（在 doc-scope 之後才算）
triples = bfs_query(kg_id, seeds, scope_doc_ids=(relevant_doc_ids or None)) # BFS 走訪只保留範圍內文件的鄰居
triples      = _filter_triples_by_source_doc_ids(triples, relevant_doc_ids) # 事後排除
fact_results = _filter_facts_by_source_doc_ids(fact_results, relevant_doc_ids)
```

檢索文件範圍（`relevant_doc_ids`）**完全由 `vector_search_facts()` 的 top-N 結果反推**：`_relevant_doc_ids_from_facts()` 取分數最高的前 `doc_scope_top_n_facts`(=5) 筆 Fact，收集它們的 `source_doc_id`。這個範圍接著同時用於：(a) `bfs_query(scope_doc_ids=)` 的 Cypher 走訪前置約束，(b) `_filter_triples_by_source_doc_ids()` 排除 BFS 三元組，(c) `_filter_facts_by_source_doc_ids()` 排除語意 Fact 清單本身。

### 1.2 失效模式（報告38 §4.1，Q5「當月一日」，grounding 0/17）

目標事實 `災害發生之當月一日起 → 前條所定災後六個月期間`（N0050030 chunk 3，`doc_id 56556675…`）**在圖裡**。但：

- KG 內有 ~28 條「X 自 Y 起算」事實，來自**另外 7 部法**（N0050031 職災保護法 ×10、N0050039 施行細則 ×9…），全是「保險**效力**之開始自…零時起算」——與問句要的「保險費**期間**從災害當月一日起算」概念相近但語意不同。
- 問句 embedding 與這 28 條都近 → 唯一正解被擠出 top-5。
- `_relevant_doc_ids_from_facts()` 據此推出範圍 = {N0050031, N0050039, …}（**錯的**）→ 正確事實因不在範圍被 `_filter_*_by_source_doc_ids()` 排除 → grounding 0/17。
- **「雜訊檢索 → 錯範圍 → 濾掉正解 → 更雜訊」惡性循環。**

### 1.3 這是結構性風險，非個案

用「檢索結果自舉檢索範圍」（retrieval bootstrapping its own scope）本身就不穩健——語意 Fact 排序一旦被概念相鄰的雜訊淹沒，反推的範圍必然錯，且錯得有系統性（都指向雜訊來源的文件）。§3.2 §b line 22 已把它連到 §1.1 已引用的兩篇文獻，本報告完成其精讀。

> ⚠️ **本節（§1.2/§1.3）的 Q5 案例已被 §8 訂正**：上述分析是報告38 在 41% 部分 KG 上做的診斷，當時 Q5 grounding 確實 0/17。全量 KG 完成後，報告42 逐題細看發現正解事實其實**已經**被檢索到、餵進了 prompt，是生成階段把「當月一日」誤寫成「當日」，grounding 核對（正確地）判定該句主張與來源不符——不是本節描述的「範圍推導錯誤把正解濾掉」。本設計對「檢索範圍靠雜訊反推」這個結構性風險的分析本身仍成立（§1.3 的一般性論證不受影響），但**不能再拿 Q5 當實測證據**。詳見 §8。

## 2. 文獻查證（2026-09-11）

> **查證層級誠實聲明**：本次以 `WebFetch` 讀 arXiv 摘要頁 + ChainRAG 的 HTML 方法段（`arxiv.org/html/2502.14245v1`）之抽取內容，**非逐字全文精讀本地 PDF**（比照本專案 🟡 標記慣例）。下方引述來自該抽取；若 ChainRAG/CS-RAG 要在論文正文作為機制層級的實質對照（非僅方向性佐證），需另下載 PDF 逐字精讀。兩篇皆已在第一章 §1.1 引用。

### 2.1 Zhu et al. (2025)《Mitigating Lost-in-Retrieval Problems in Retrieval Augmented Multi-Hop Question Answering》（ChainRAG）

🟢 **ACL 2025**（arXiv:2502.14245）。Rongzhi Zhu, Xiangyu Liu, Zequn Sun, Yiwei Wang, Wei Hu。

- **「Lost-in-Retrieval」定義**：「the key entities are missed in LLMs' sub-question decomposition」——多跳問題被拆成子問題時，關鍵實體沒被保留下來（含代名詞未被還原成具名實體）。後果：「significantly degrades retrieval performance, disrupts the reasoning chain, and produces incorrect answers」；量化：**第二個子問題的 Recall@2 平均下降 18.29%**。
- **核心解法＝實體錨定（entity anchoring）**：檢索前先「complete missing key entities」——以代名詞偵測判斷子問題是否需要改寫，用「the current sub-question and the previous sub-questions along with their answers」餵 LLM 把代名詞補成具名實體；「When a sub-question is rewritten with explicit entities, the updated sub-question is subsequently used for retrieval — ensuring entity specificity guides candidate selection」。檢索擴展沿 sentence graph 的 **entity co-occurrence (EC) 邊**（「sentences sharing key entities」）走。
- **可遷移原則**：檢索範圍應錨定在**可靠的具名實體訊號**上，而非錨定在「一個由 LLM/embedding 產生、可能已經漂掉的中間訊號」（拆出的子問題 / 反推的文件集）。

### 2.2 Ma et al. (2026)《Toward Robust GraphRAG: Mitigating Retrieval Drift and Hallucination from Imperfect Knowledge Graphs》（CS-RAG）

🟡 **arXiv:2603.14828** cs.IR（2026-03 投稿、2026-05 v2）。Yizhuo Ma 等 9 人。本次讀摘要（`WebFetch`）。

- **「Retrieval Drift」定義**：「Spurious noise induces retrieval drift toward plausible but unsupported triples」——檢索被雜訊帶往「結構上合理但事實上無依據」的三元組。本專案 Q5 是其在**查詢端文件範圍推導**的具體展現（雜訊 Fact → 錯範圍）。
- **核心解法**：把 query 轉成「an ordered sequence of executable atomic constraints」，做「**anchor- and relation-aware retrieval to constrain evidence acquisition around the intended hop semantics**」，並在推進到下一步前做「a sufficiency check to decide whether the retrieved evidence can safely induce variable bindings」，結構支援不足時「activates textual recovery」。強調「mitigate during retrieval rather than relying on KG repair」。
- **可遷移原則**：檢索邊界由**查詢本身的錨點（實體 / 原子約束）**決定，不是由不可靠的中間排序決定；不足時優雅退回（放寬而非硬篩）。

### 2.3 兩篇的共同結論（本報告的設計依據）

> **檢索範圍（scope）應錨定在「從查詢直接得到的可靠具名實體訊號」，而非「由 embedding/LLM 產生、可能已漂移的中間衍生訊號」；當錨定訊號不足時，優雅放寬、不硬篩。**

本專案現況剛好相反：範圍來自 `vector_search_facts()` 的 top-N（衍生、可漂移），而**更可靠的種子實體訊號（`_find_seed_entities` 的字面比對命中）在流程中反而算得比較晚、沒被用來定範圍**。

## 3. 設計：檢索文件範圍改用實體錨定

### 3.1 調換順序 + 新增種子文件推導

```
question_vector = encode(question)
seeds = _find_seed_entities(kg_id, question, ...)          # ← 提前到最前面
seed_doc_ids = _relevant_doc_ids_from_seeds(kg_id, seeds)  # ← 新增：種子實體出現在哪些文件

fact_results     = vector_search_facts(kg_id, question_vector, top_k)   # 不變
semantic_doc_ids = _relevant_doc_ids_from_facts(fact_results, top_n)   # 不變（改當 fallback）

relevant_doc_ids = _resolve_doc_scope(seed_doc_ids, semantic_doc_ids, payload.scope_doc_ids)

triples = bfs_query(kg_id, seeds, scope_doc_ids=(relevant_doc_ids or None), ...)   # 不變
triples      = _filter_triples_by_source_doc_ids(triples, relevant_doc_ids)        # 不變
fact_results = _filter_facts_by_source_doc_ids(fact_results, relevant_doc_ids)     # 不變
```

### 3.2 `_relevant_doc_ids_from_seeds()`（新增）

種子實體已經過 `_drop_hub_seeds()` 剔除 degree > `seed_max_degree`(=100) 的樞紐 → 剩下的是**有辨識度的具名實體**。查它們出現在哪些文件：

```cypher
MATCH (c:Chunk {kg_id: $kg_id})-[:HAS_ENTITY]->(e:Entity {kg_id: $kg_id})
WHERE e.name IN $seed_names
RETURN DISTINCT c.source_doc_id AS doc_id
```

（`HAS_ENTITY` 結構邊在 §3.1.4 §c 修復後的 KG（含 KG#4）已完整；舊 KG 無此邊 → 回空集合 → 自動走 fallback，見 §3.4。）

### 3.3 `_resolve_doc_scope()` —— 錨定優先、語意 fallback、明確範圍取交集

| `seed_doc_ids` | `semantic_doc_ids` | `scope_doc_ids`（明確） | `relevant_doc_ids` |
|---|---|---|---|
| 非空 | 任意 | 無 | **`seed_doc_ids`**（錨定優先，語意範圍不參與——這是修 Q5 的關鍵） |
| 空 | 非空 | 無 | `semantic_doc_ids`（**現行行為，零回歸**：無 `HAS_ENTITY` 邊的舊 KG、或種子全被 hub-drop 清掉時） |
| 空 | 空 | 無 | 空（不下推，同現行） |
| 任一非空 | | 有 | 上面結果再與 `scope_doc_ids` 取交集（沿用 `_intersect_doc_scopes()` 語意：交集為空則回明確範圍本身） |

**為何錨定優先、不做 seed ∪ semantic 聯集**：Q5 的 semantic_doc_ids = 28 條雜訊來源的 7 部法，聯集會把雜訊原封不動帶回來。ChainRAG/CS-RAG 的原則就是「用可靠錨點**取代**不可靠訊號」，不是相加。

**為何不擔心種子文件範圍本身錯**：① hub-drop 已擋掉「雇主/被保險人」這種每篇都出現的通用實體；② 種子多來自字面比對（問句裡有的詞），文件範圍因此貼題；③ 種子來自 `_find_seed_entities` 的語意 fallback（`vector_search_entities`）時信心較低，但仍是**實體名稱**相似度、非 **Fact 文字**相似度，且同樣受 hub-drop 保護——比 top-N Fact 反推穩健；④ 真的種子文件範圍漏掉正解時，`_scope_by_source_doc_ids()` 既有的**歸零守衛**兜底（若過濾把非空清單清成空 → 放棄過濾、原樣回傳）。

### 3.4 相容性 / 零回歸邊界

- 舊 KG（無 `HAS_ENTITY` 邊）→ `seed_doc_ids` 空 → 走 `semantic_doc_ids` = 現行行為。
- `_find_seed_entities` 回空（字面 + 語意 fallback 都沒命中）→ `seed_doc_ids` 空 → 現行行為。
- `retrieval_mode='fact_only'`（報告39，不跑 BFS、無種子）→ `seed_doc_ids` 空 → `semantic_doc_ids`，與現行一致。
- `retrieval_mode='bfs_only'`（不跑 `vector_search_facts`）→ `semantic_doc_ids` 空 → 現在改為 `seed_doc_ids`（新：`bfs_only` 也能有範圍下推，理論上更精準；驗證時要確認不使 `bfs_only` arm 退步）。
- `payload.scope_doc_ids`（報告39 前導比較的 6 份子集）→ 交集邏輯不變。

### 8.1 發生了什麼

本報告 §1–§2 的設計動機建立在報告38（2026-09-09，KG#4 僅 41% 部分重抽）的診斷上：Q5（N0050030 災區受災勞工保險費補助辦法，問「保險費期間從哪天起算」）grounding 0/17，診斷為「`_relevant_doc_ids_from_facts()` 被 ~28 條概念相近的雜訊事實帶偏，反推出錯的文件範圍，把正解事實濾掉」。

2026-09-13，KG#4 全量重抽完成（3303 chunk，236903cf @ 100%）後，報告39 補跑正式規模七路比較（6 題 × 7 arm × 3 run = 126 筆），另一個 session 寫的報告42（`docs/報告/42_...md` §5「26-Q5」、§7.3「結論4」）對這 126 筆逐題逐 arm 逐 run 做 0/1/2 grounded 評分，發現：

- **K／K-2b arm 的事實清單確實包含正解事實**（`facts=1`，內容為「自災害發生之當月一日起計算六個月」）——即正解**已經**通過檢索、被餵進生成 prompt。
- **三次生成、三次都把「當月一日」簡化成「當日／當天」**（K 與 K-2b 皆然，關掉限制性重生 2b 沒有改善）——一字之差、語意不同（「當月一日」＝當月的第一天；「當日」在此語境會被誤讀為災害發生當天）。
- 接地核對機制判定「答案句與來源事實不符」是**正確**的判斷（答案句確實跟來源用詞不同），不是核對機制失靈，也不是檢索沒把正解餵進去。

這精確吻合 Maynez et al.（2020，ACL，*On Faithfulness and Factuality in Abstractive Summarization*）的 **intrinsic hallucination** 定義——模型讀到了正確資訊，生成時扭曲了其中的精確度。報告42 已把此文獻查證存入 `docs/參考文獻/30_`。

### 8.2 意涵：Q5 不能再當本設計的動機證據

本報告 §1.2/§1.3/§3～§6 的設計論證本身（「檢索範圍不應由不可靠的中間訊號自舉，應錨定在可靠的具名實體訊號」，引用 ChainRAG／CS-RAG）**沒有被推翻**——它仍是一個合理、有文獻依據的一般性風險分析。但 **Q5 這個具體案例不再能證明「本系統的檢索範圍推導在真實資料上確實犯了這個錯」**：真正發生的失效是下游生成步驟，本報告要修的上游檢索範圍推導在這一題上其實沒有犯錯（正解事實本來就在餵進去的清單裡）。

本報告 §5/§6 描述的 harness（`compare_doc_scope_retrieval.py`）獨立於 Q5 動機案例跑過一次真實驗證（2026-09-13，另一 session）：8 題（26-Q1~Q8）7 題精準命中 gold 文件，**1 題（26-Q7）出現 regression**（原本命中 gold 的範圍，改用錨定後沒命中）——**未達到 §6.2 原訂的「regressed=0」驗收標準**。

## 9. 第二輪事後訂正（2026-09-14）—— 推翻 §8，查明真因：Fact-RAG 全域語意排名，不是 L9 V1 修得動的環節

### 9.1 起因

使用者要求核對 §8（報告42的訂正）是否成立。逐一讀 `report39_comparison/formal_20260913/run{1,2,3}.json` 的原始 `retrieved_passages`（不是只看 §6 摘要），並直連 KG#4 Neo4j 核對，發現 §8 整段的前提是錯的。

### 9.2 查證結果

1. **§8 的「facts=1 代表正解已被檢索到」是誤讀**：K／K-2b 對 26-Q5 的 6 次執行（3 run × 2 arm），`retrieved_passages.facts` **全部只有 1 條**——內容是「災區受災勞工…其災後六個月期間內被保險人應負擔之保險費，由中央政府支應」（§2），**從未出現**「自災害發生之當月一日起計算六個月」（§3）。同一題 BFS 撈到的唯一三元組也是不相關雜訊「被保險人 溢繳之 保險費」。逐一核對 6 次執行的實際回答文字（報告42 §5 自己列的逐字記錄），三次全都是「根據事實清單…此條事實明確指出『災後六個月期間』…因此這個期間從災害發生的當天/那天開始起算」——模型從頭到尾只看到 §2、自己憑空補了「當天」，不是把「當月一日」改寫成「當日」。報告42 §6/§7.3 引用的「當月一日」原文，查證後**其實是 B0/B1（chunk-RAG）arm 的回答**（B0/B1 讀整份原文段落、天然含 §2+§3），跟 K/K-2b 的段落弄混了。
2. **不是抽取端漏掉**：直連 Neo4j 確認 `自災害發生之當月一日起 → 計算 → 前條所定災後六個月期間` 這個 Fact 節點確實存在，`source_doc_id` 正確指向 N0050030。抽取沒有問題，事實在圖裡。
3. **⚠️ L9 V1（本報告 §3 的設計）救不了它，即使接線進 `chat()` 也一樣**：用本報告 §3 的種子錨定邏輯重跑 26-Q5，重現 `compare_doc_scope_retrieval_result.json` 的 18/38 條範圍（依 §6 harness 或直接重跑 §3.1/§3.2 邏輯），逐條核對**沒有一條**含「一日／當月／起算」；範圍內唯一來自 N0050030 的仍是同一條「被保險人 溢繳之 保險費」雜訊——目標事實不在種子實體一跳可達的圖鄰域裡，本報告的範圍修法完全碰不到它。
4. **先前流傳的「26-Q5 正解事實排名躍升第 0 名」說法（見某交接備忘）無法用同一套邏輯、同一個 KG 重現**——不確定是量測方式不同還是 KG 狀態已變，**未能證實，不應再被引用為「L9 V1 已解決 Q5」的證據**。

### 9.3 真因：問題比本報告設計的環節更上游

直接量測 `vector_search_facts()` 的全域語意排名（把 `top_k` 從 20 開到 100 重跑）：目標事實排名**第 41 名**（cosine score=0.8161），前面 34 條全是其他 7 部法規「起算」類的近義雜訊（例如「其保險效力之開始…自本法施行之日起算」）。**production 用的 `top_k=20`，這條事實從一開始就沒有進入候選池**——本報告 §3 設計的「文件範圍下推」是在 `vector_search_facts()` **已經回傳結果之後**才動作的下游步驟（見 §1.1 現況圖：`fact_results = vector_search_facts(...)` 先執行，`_relevant_doc_ids_from_facts`／本報告的 `_relevant_doc_ids_from_seeds` 都是在這之後才對已撈到的結果做範圍推導或後篩選）。**上游都沒撈到，下游任何範圍邏輯都無米下鍋。**

這也解釋了為何 §8.4 觀察到「F arm 也漏了同一條事實」：F arm 直接消費 `vector_search_facts()` 的原始輸出，跟 K/K-2b 一樣卡在同一個上游瓶頸，不是本報告範圍內的另一個獨立缺口。

### 9.4 結論

- **報告42「生成端」的訂正不成立**（§8 全文作廢，保留供追溯）；報告38／本報告原本「檢索端」的大方向是對的方向，但診斷的具體機制需要再往上游修正一層。

- **Q5 需要一個尚未設計的新修法**：讓 Fact-RAG 排名在「短小、易被跨文件近義詞淹沒」的條文事實上更健壯——候選方向包括比照 B1 的 hybrid 檢索（BM25 詞面比對 + embedding 語意，RRF 融合）、大幅提高 `top_k` 後交給下游截斷/重排處理、或針對此類「起算日」句式做結構化欄位查詢（§3.5 Y4 結構化條件過濾查詢，若時序欄位涵蓋此語意）。這是一個獨立的設計任務，不屬於本報告範圍，也不因接線本報告而附帶解決。
