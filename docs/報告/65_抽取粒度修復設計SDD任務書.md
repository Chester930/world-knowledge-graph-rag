## 0. 一頁摘要

**問題**：`services/svo_service.py::_svo_prompt()` 規則7要求「一句話的每一項附加規定都各自拆成獨立三元組」（報告18/19/20時期為修復「遺漏」問題而設計），副作用是遇到「共同條件 → 一個或多個結果」的複合法規句時，條件與結果被拆進互不相干的三元組，任一筆單獨看都不完整。今天（2026-09-22）人工複核 `57-AGGR19` 時又抓到一個新鮮案例：Fact 排名**第1名**（不是排序問題）仍判未命中，因為丟了「依前項第一款規定」這個適用範圍限定。

**根因已用真實資料定位**（非猜測），見 §1。**文獻查證已完成**（§2，`docs/參考文獻/37_三元組條件限定詞與超關係表示/`），誠實結論：找不到直接研究「LLM 抽取時如何在『避免遺漏』與『避免拆散丟條件』之間取捨」的文獻，但相鄰領域（proposition 檢索、超關係知識圖譜、法律規範顯式表示）都認真對待「限定條件不該被丟」這個大原則，可作為設計方向的旁證，不能宣稱「文獻證明這樣做有效」。

**建議**：先做方向A（修 prompt，成本低、與既有修法慣例一致），用定向重抽驗證（不動全域），確認有效後再考慮是否需要方向B/C。**本報告完成後，下一步是使用者核准，再開始寫程式**。

### 1.3 根因

`services/svo_service.py::_svo_prompt()` 規則7（第232行）：

> 「一句話常常包含不只一件事實…這些都要各自拆成獨立的三元組完整抽出，不可以只抽主要動作、把附加規定省略掉…」

這條規則是報告18/19/20時期為了修復「遺漏」問題（如漏抽「十四日」上限）刻意設計的，本身沒有錯，但沒有處理「拆出來的多筆三元組之間如何保留彼此的條件關係」——這是規則7的**設計範圍之外**，不是它做錯了什麼。

### 1.4 與已知資料結構的落差（技術可行性查證）

查證 `models/knowledge_graph.py::SVOTriple`：**已經有** `source_sentence_start`／`source_sentence_end`（句子範圍，1-based）欄位（第216-217行），抽取時就會填。但查證 `services/svo_service.py::_create_fact_node()`（第1830-1905行）發現：**這兩個欄位目前沒有被寫進 Fact 節點**（Cypher `CREATE` 只寫了 `source_doc_id`／`source_svo_chunk_index`，第1885-1890行），只是呼叫端遺漏傳遞，不是能力不存在。每個 Fact 節點對應**恰好一次**特定三元組的抽取（`merge_triples_to_graph()` 第2039行註解：「每筆 citation 各自產生一個 Fact 節點，永不相互覆蓋或平均」），觸發 `_create_fact_node()` 呼叫的 `triple: SVOTriple` 物件在呼叫現場（第2049-2063行）本來就持有這兩個欄位。這個發現是方向B（見§3.2）技術可行性的依據。

## 3. 候選設計方向

### 3.1 方向A（建議優先）：修 prompt，條件複述進每筆衍生三元組

在 `_svo_prompt()` 規則7後新增一條規則與反例：當一句話是「共同條件 → 一個或多個結果」的複合結構時，**條件要重複寫進每一筆結果三元組的 verb 裡**，不能只留在單獨一筆條件三元組上。例如 `57-AGGR7` 應變成：

```
{"subject": "最低開班人數", "verb": "（雇主依本法第二十四條第二項規定辦理訓練並申請訓練費用補助時）應達", "object": "五人"}
{"subject": "訓練時數", "verb": "（雇主依本法第二十四條第二項規定辦理訓練並申請訓練費用補助時）不得低於", "object": "八十小時"}
```

**成本/風險**：低。只改一個 prompt 字串＋加反例，跟規則6/7/8/9既有修法模式一致（report24/25/29/32一貫做法），不需要 schema 變更、不需要 backfill。

**已知取捨**：verb 文字變長、同一條件在多筆三元組裡重複出現，`fact_text`／embedding 會有一定冗餘；但每筆三元組單獨可解讀，直接對症診斷出的 gold span 缺陷。

### 3.2 方向B：Fact 節點補句子層級 provenance，檢索/組裝時撈同句兄弟 Fact

`_create_fact_node()` 新增 `source_sentence_start`／`source_sentence_end` 兩個扁平屬性（沿用 2026-08-24 幫 `article_no` 做過的同一套模式），既有 16826 筆 Fact 需要 backfill（`backfill_fact_nodes()` 已有先例可仿照）。檢索到任一 Fact 時，額外查詢「同一 `source_doc_id`＋`source_svo_chunk_index`＋句子範圍重疊」的其他 Fact 一起帶入 context——比 T3（報告62，整條文擴充）更精準，不會像整條文那樣拉進不相干的其他列舉項目、拉低 SNR。

**成本/風險**：中高。需要 schema 新增＋backfill＋檢索/組裝端新邏輯；且**救不了已經污染的 embedding**——`fact_text` 本身還是破碎的，語意檢索排序不會變好，只能改善「展示時的完整性」，不能改善「排名」。

**定位**：方向A解決「一開始別讓事實破碎」，方向B解決「已經破碎的事實在展示時補救」，兩者不互斥，但方向B成本明顯更高，本階段不做，留作方向A效果不足時的候選。

### 3.3 方向C：Fact 引入顯式 qualifier（超關係表示，非本階段候選但記錄在案）

比方向A更原則性的做法：把「依前項第一款規定」這類限定條件建模為 Fact 的顯式 qualifier（新屬性或獨立邊），而非複述進自然語言 verb 字串。有文獻佐證（Galkin et al. 2020），但需要 Fact schema 根本性改造（新增 qualifier 資料結構、抽取 prompt 改輸出格式、下游所有讀取 Fact 的程式都要適配），成本遠高於A/B，且沒有本專案技術路線（LLM prompt 抽取＋cosine 檢索）下的直接先例可循。**本階段不評估實作，僅記錄為長期候選**。

## 4. 驗證計畫（先做，不動全域）

1. **改 prompt**：在 `_svo_prompt()` 加入方向A的新規則與反例（覆蓋條件→多結果、以及列舉前言天數兩種案例，即 §1.2 的 `57-AGGR7`/`57-AGGR8`/`57-CANARY5` 型與 `18-Q5` 型）。
2. **定向重抽**：用既有 `scripts/kg/reextract_chunks.py`（不是全量重抽），對 §1.2 五個案例對應的 chunk 做定向重抽——先用 `scripts/kg/reextraction_manifest.py` 或直接查 `LawArticle` 節點定位這些條文（`D0080015`第2-4條、勞工職業災害保險及保護法第85條/第26條、就業保險促進就業實施辦法第6條/第24條、第101條等）各自對應的 chunk index。
3. **重新診斷**：對這批 chunk 重新跑一次 `retrieval_failure_diagnosis.py`（或等效的唯讀查詢），確認：
   - 目標 Fact 的 `fact_text` 是否包含之前丟失的限定條件；
   - 是否有連帶副作用（例如其他既有正確的 Fact 被改壞、embedding 距離大幅改變導致排名劣化）。
4. **不擴大範圍前的決策點**：定向重抽驗證通過（條件回來、無新增劣化）才考慮是否要對更大範圍（例如整個 KG）重抽；驗證不通過則檢討 prompt 措辭，不直接放棄方向A。
5. **全程不動**：全域 `top_k`、scope filter、Hybrid、`source_doc_cap`、BFS 預設名額、題庫、正式 KG 資料（定向重抽在既有 KG 上進行，比照報告57附錄C既有慣例）。
