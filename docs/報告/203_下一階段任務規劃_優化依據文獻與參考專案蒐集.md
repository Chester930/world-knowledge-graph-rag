專案既有原則（記憶：設計決定需要**即時查證**的文獻與專案依據，不憑記憶引用）。每一筆來源必須：

1. **當場取得一手來源**（WebFetch／WebSearch 取得原文頁面、arXiv 頁面、W3C／官方規格頁面、GitHub 原始碼；`gh api` 讀取倉庫檔案），**不得僅憑記憶或二手轉述**。取不到就標「未查證」，**不得寫入結論**。
2. **逐字引用**與本專案議題相關的 1–2 句原文（標明語言），並附 URL、取得日期（2026-10-01 起）、版本或 commit。
3. 標明**查證強度**：✅ 一手全文已讀（說明讀了哪幾節）／🟡 一手摘要或規格片段／⚪ 僅搜尋結果摘要（**不得作為結論依據**）。
4. 逐項寫「**它支持什麼**」與「**它沒有證明什麼**」（例如：是否有量化實證？論域是否與本專案相同？）。**允許且鼓勵寫「查無直接依據」**。
5. **參考專案**（開源實作）必須**讀實際原始碼或其官方文件的特定檔案**，記錄 repo、commit／release、日期、檔案路徑與行為描述，並區分「**程式實作了**」與「**文件宣稱**」。
6. 本專案既有資料夾（`docs/參考文獻/01–40`）已登記的來源**不要重複蒐集**，只引用其編號；若發現既有登記有誤，**回報規劃對話**，不要自行改。

## 4. I1：文獻與規格蒐集——五個主題群

> 下列「方向」是規劃對話憑印象列出的**線索，尚未驗證，不得直接引用**；請以實際查證結果為準，並鼓勵補充我沒想到的更好來源，也可回報「此方向查無適切來源」。

**G-A　缺值的語意：未知 vs 不適用**
- 要回答：成熟的知識表示系統如何區分「未知」「無值／不適用」？
- 線索：Wikidata 的 *unknown value*／*no value*（Wikibase 資料模型）；開放世界／封閉世界假設（OWL／RDF）；資料庫缺值語意（SQL NULL 三值邏輯、Codd 的缺失資訊討論）。
- 本專案對應：型別佔位「概念」、`source_article_no` 的 `None`、空受詞（報告201）。

**G-B　身份：穩定識別碼與標籤分離、類型的剛性（人 vs 員工）**
- 要回答：實體識別碼為何要與名稱／標籤分離？「人」與「員工身分」這種層級在本體工程如何處理？
- 線索：Wikidata 項目識別碼與標籤／別名；OntoUML／UFO 對 *kind*（剛性）與 *role／phase*（反剛性）的區分；`schema.org` 的 `Role`（本專案 `data/schema_org_entity_types.json` 已含，可直接引用該資料）。
- 本專案對應：唯一鍵 `(kg_id,name)`、標準名會被改寫（報告197）、使用者的「身分層級」。

**G-C　關係的時間與狀態：有效區間、失效、狀態機**
- 要回答：圖中的關係（邊）如何帶有效性？哪些系統用「失效」而非「覆寫」？
- 線索：Wikidata qualifier（起訖時間）；時序知識圖譜與雙時態（bitemporal）資料模型；W3C OWL-Time；**面向 agent 記憶的時序圖譜**（邊的 `valid_at`／`invalid_at`）。
- 本專案對應：使用者的「每個關係是狀態機、起訖由狀態轉換定義、不強制綁時間」（v0.2 §1.4）。**請特別留意文獻是否以「時間」為唯一觸發，或也支援「條件／事件」觸發**——這是使用者設計與常見做法的關鍵差異，**寫明差異**。

**G-D　候選→已接納、信心與來源**
- 要回答：從文字抽取的事實，系統如何區分「候選」與「已採信」？
- 線索：NELL（Never-Ending Language Learning）的候選信念與升格；Knowledge Vault 的信心校準；Wikidata 的 statement rank 與 reference；W3C PROV-O（來源／產生者／時間）；RDF-star／屬性圖的 statement 層級 metadata。
- 本專案對應：抽出即 MERGE（報告197）、引用無抽取時間／模型版本、`confidence` 無語意。

**G-E　圖上的完整性約束**
- 要回答：屬性圖／知識圖譜如何宣告並檢查不變量？
- 線索：W3C SHACL（及 ShEx）；屬性圖模式語言（PG-Schema 等）；Neo4j 約束文件。
- 本專案對應：簡報第 6 步「規則與約束」（v0.2 §1.4）、報告196 的不變量清單與唯讀檢查腳本。

**每個主題群的產出**：一張表（來源｜強度｜逐字引文｜支持什麼｜沒證明什麼｜與本專案哪個發現對應）＋該群的**一段結論**（依據是否足以支持採用某種做法？把握度？有哪些直接相反或不同的做法？）。

## 5. I2：參考專案原始碼閱讀

**目標**：看**真實系統**如何處理上述議題，避免只讀論文。請選 **3–5 個**與「知識圖譜＋agent」相近的**開源專案**（建議包含：面向 agent 記憶的時序圖譜專案、Microsoft GraphRAG、LightRAG，以及專案內 `參考文獻/13` 已登記的實體去重開源專案之一；你可依查證結果替換並說明理由），**每個專案至少回答**：

1. 實體身份：用什麼當鍵？名稱會變嗎？合併如何記錄、能否回復？
2. 關係／邊：是否帶有效期間或失效？更新是覆寫還是新增＋失效舊的？
3. 型別未知：抽取不出型別時怎麼處理？有沒有「未解決」標記？
4. 來源／證據：邊或節點上記錄哪些來源資訊（文件、位置、時間、模型版本）？
5. 空值／殘缺三元組：如何處理缺少主詞或受詞的抽取結果？

**每個專案記錄**：repo URL、commit／release、取得日期、**實際讀過的檔案路徑**、對上述五問的答案（標「**程式實作**」或「**僅文件宣稱**」）、**與本專案做法的差異**。

## 7. 停止條件（遇到下列情況停止並回報）

1. 發現既有登記（`參考文獻/01–40` 或報告61／v0.2）與一手來源**不符**——回報，規劃對話會更正。
2. 某主題群**查無任何適切一手來源**——照實寫「查無」，不要湊數；可建議替代搜尋方向。
3. 需要付費牆、登入或違反使用條款才能取得的內容——標「未取得」，不要規避。
4. 任何一筆想引用但**無法取得一手來源**——不得寫入結論（可列為「待查」）。
5. 工作區出現非自己的未提交檔案：commit 前逐檔指定路徑，不得 `git add -A`；`HANDOVER.md` 先看 `git diff -U0`；commit／push 後以 `git rev-list --left-right --count origin/<分支>...HEAD` 確認同步。
