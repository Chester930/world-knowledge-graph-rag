## 0. 一頁摘要

本輪原訂補完先前因記憶體壓力於第9題中止的42題全量`M1,M2,B2`比較。採**分批執行**策略（每批約9題，獨立進程，避免單一長進程記憶體無限累積）。**第1批（9題）已完整跑完，含3筆timeout補跑後全數乾淨（0 error）**。跑完第1批後例行檢查記憶體時，發現free記憶體從批次開始前的11.2GB降到5.5GB，主動用`wsl --shutdown`重啟WSL2釋放記憶體——**重啟後才發現Docker Desktop把先前就在跑的Dify全家桶（api/worker/web/redis/postgres/sandbox/ssrf-proxy）與n8n容器一併自動拉了起來，這些不是本次任務啟動的服務**，重啟後基準可用記憶體只剩4.2GB，比batch1開始前更緊繃。這已經逼近先前導致整批中止的資源壓力等級，且Dify/n8n是否可以停用不是本次任務能自行判斷的範圍（不是我啟動的服務，可能使用者另有用途在跑），因此**主動停止繼續跑第2-6批**，只交出第1批（9題）的完整結果，如實回報現況等待裁示。

**第1批（9題）核心發現**：
1. **`retrieval_budget`分配修正在9題規模下依然有效**——9題B2全部`rounds_per_subquestion`無任何0，budget修正（commit `cb3be26`）通過更大樣本驗證。
2. **三臂比較**：M1（B0）mean atomic_accuracy 1.0（9/9 perfect）、M2（B1）0.963（8/9 perfect）、B2 0.889（7/9 perfect）——**B2平均反而略低於M1/M2**，主因集中在`18-Q5`一題（見下）。
3. **成本代價**：B2平均6.67次LLM呼叫／題 vs M1/M2的1.1-1.2次（約6倍，比報告93 n=8時的5.88次略高但同量級）；延遲100.0s vs 68s左右（約47%），context tokens 886.6 vs 606-630（約1.4-1.5倍）。
4. **新發現（與budget修正無關的confounder）**：`18-Q5`的B2在**budget分配正確**（`rounds=[4,2,2]`，跟報告93 §4.1驗證時完全一樣）的情況下，**這次生成端只答出第三級距（3-7日），漏了前兩級距（1-3日、2-5日），atomic_accuracy=0**——跟報告93 §4.1驗證跑出的1.0完全正確形成對比。**證據蒐集端一模一樣、生成端結果不同**，這是本專案已知的LLM推論非決定性問題（`core/providers/llm/ollama.py`固定seed仍無法完全消除，報告20/62 §14同源機制），不是budget分配的新缺陷。

**誠實評估**：n=9仍然太小，且這次唯一的B2退步案例（18-Q5）已經證實是生成端非決定性而非檢索/budget問題——這意味著**B2的答案品質評估比想像中更依賴run-to-run變異**，若要正式判斷B2是否優於B0/B1，需要每題×3 run取穩定通過率（比照報告62/72系列的判定慣例），單run的±1題差異屬於雜訊範圍。目前證據**不足以支持也不足以否定**「B2值得投入正式RQ1對照組」，維持report 36「optional」定位。**成本代價（約6倍LLM呼叫、快50%延遲、約1.5倍context）在9題規模下穩定重現，這部分結論比準確率更可信**。

## 1. 執行範圍與過程

### 1.1 分批設計

46題eligible（`verification_status=="verified"`且有`atomic_gold_facts`）依`id`順序切成6批：batch1-5各9題、batch6僅1題（`57-AGGR19`）。每批獨立python進程執行`--arms M1,M2,B2 --runs 1 --allow-shared-judge`，避免像上一輪那樣單一42題進程長時間累積記憶體。

### 1.2 batch1執行細節

- 首次執行（`--query-timeout-s`預設180s）：9題×3臂=27筆，**3筆timeout**（`18-Q3`/B2、`18-Q5`/M1、`18-Q5`/B2，皆卡在180s門檻附近——`18-Q3`/B2與`18-Q5`/B2先前在報告93 §3.3單獨測是160.8s／192.2s，這次在批次＋更高背景負載下略微超時）。
- 用`--query-timeout-s 300`對這2題（`18-Q3`、`18-Q5`）補跑，3臂全部在300s內完成、0 error。合併後batch1共27筆記錄、**0 error**。
- 補跑時意外發現`18-Q5`/B2的答案品質這次不同（見上方摘要第4點）。

### 1.3 記憶體壓力與WSL重啟插曲

batch1+補跑執行完後，系統可用記憶體從開始前11.2GB降到5.5GB。依任務書授權，主動執行`wsl --shutdown`（PowerShell）reclaim記憶體，重啟後手動`docker start kg2-neo4j`（首次因Docker Desktop後端尚未就緒而失敗，等待約35秒後Docker Desktop自行重啟其WSL2後端，Neo4j容器自動恢復）並確認Ollama（WSL Ubuntu-24.04）已透過systemd自動重啟（`curl localhost:11434/api/version`回應正常）。

**關鍵發現**：Docker Desktop重啟後端時，把先前也在執行中的`dify-api`／`dify-worker`／`dify-web`／`dify-redis`／`dify-postgres`／`dify-sandbox`／`dify-ssrf-proxy`／`n8n-n8n-1`等**跟本任務完全無關的容器**一併自動啟動（Docker Desktop對「重啟前正在跑的容器」的預設行為）。這些容器加上原本就在跑的Antigravity IDE、Discord、Chrome，讓WSL重啟後的基準可用記憶體只剩**4.2GB**——比batch1開始前的11.2GB低了超過一半，且是在**還沒開始跑batch2**的情況下就已經逼近先前導致中止的壓力等級。

### 1.4 決定停止擴大規模

- 這些Dify／n8n容器不是本次任務啟動的服務，也不確定使用者當下是否需要它們運作中，**不在本任務的授權範圍內自行停用**（任務書明確要求「這些操作屬於你可以自主判斷執行的維運動作」僅限於WSL重啟本身，沒有授權停用其他無關服務）。
- 在4.2GB基準可用記憶體下貿然啟動9題B2為主力的batch2，重演上一輪OOM中止的風險很高。
- 依任務書「遇到問題時」條款的精神（雖然嚴格說還沒到「連續多批失敗」，但預兆已經很明確），判斷**如實回報現況、停止擴大規模，把決定權交還使用者**是比冒險硬跑更負責任的做法。

## 3. 誠實評估

1. **budget修正本身：確認有效，證據更充分**。報告93 §4.1的單題驗證＋本報告9題規模的驗證，兩次獨立跑測都沒有任何`rounds_per_subquestion`出現0，`18-Q5`兩次驗證的budget分配結果完全一致（`[4,2,2]`）。這部分的結論可以視為穩固。
2. **答案品質的run-to-run變異比預期更大**：`18-Q5`同一套retrieval/budget條件下，兩次生成分別是1.0與0.0，差距達到滿分到零分的極端。這代表**只跑`--runs 1`的準確率數字（本報告與報告93皆是）不足以代表B2的真實品質**，正式比較需要`--runs 3`取穩定通過率，比照報告62/72系列的既有判定慣例。
3. **成本代價的結論相對穩固**：兩輪獨立pilot（報告93 n=8、本報告n=9，樣本幾乎不重疊）都測出B2的LLM呼叫數是B0/B1的約6倍量級（5.88次 vs 6.67次），延遲多28%~47%，context長度多1.4~2倍。**這個成本代價結論比準確率結論更可信**，因為它不像準確率那樣受單次生成的隨機性主導。
4. **目前證據不足以支持或否定「B2值得投入正式RQ1對照組」**——需要更大樣本＋多run穩定性評估才能下結論，維持report 36「optional」定位不變。若要繼續，下一步應該是先解決記憶體資源競爭問題（例如確認能否在跑測期間暫停Dify/n8n、或安排在這些服務沒有被使用者需要的時段跑），而不是在目前的資源環境下勉強擴大規模。

## 4. 待使用者裁示

1. **記憶體資源競爭**：本機除了本專案的Neo4j/Ollama外，還有Dify全家桶與n8n容器會被Docker Desktop在WSL重啟後自動一併復原，這些服務目前是否還在使用中？如果不需要，可以考慮跑測前先手動停用騰出記憶體空間；如果需要保留運作，擴大B2跑測規模可能需要等待其他時段或用更小的批次（例如每批3-4題）分散在更長時間執行。
2. **是否繼續補完剩餘37題**：本報告只完成9/46題。是否要在解決記憶體資源問題後繼續補完batch2-6，或現階段先以「9題規模的budget修正驗證＋成本代價定性結論」收斂，維持report 36「optional」定位，把「答案品質需要×3 run才可信」這個新發現寫進論文限制/未來工作章節。
3. 若要繼續，建議調整：每批縮小到約4-5題、`--query-timeout-s`固定用300（本次已證實180s對B2偏緊）、每批間確認記憶體與其他容器狀態後再繼續。
