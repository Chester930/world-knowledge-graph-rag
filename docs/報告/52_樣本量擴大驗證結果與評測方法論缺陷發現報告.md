## 3. 核心發現：評測方法論的系統性測量偏誤

### 3.1 機制

`services/lineage_tracker.py::record_retrieval()`：

```python
combined_text = "".join(retrieved_texts).replace(" ", "").replace("\n", "")
for span in gold_spans:
    clean_span = span.replace(" ", "").replace("\n", "")
    if clean_span in combined_text:
        hit_spans.append(span)
    else:
        missed_spans.append(span)
```

`services/atomic_scorer.py:79`（報告51§6已指出這處，本報告發現`lineage_tracker.py`還有第二個同構問題）：

```python
if clean_span in clean_answer:
```

兩處都是**gold exact_span 是否為子字串逐字出現**在（分別是）檢索到的原文／模型最終答案裡。這個比對方式隱含一個前提：**檢索到的內容跟gold_span用詞一致**。這個前提對 M1/M2（chunk-RAG）成立——它們餵給模型的就是法規原文逐字段落，`exact_span`本來就是從同一份法規原文摘出來的，天生會是段落的子字串。但對 M3/M4（Fact-RAG／KG）**不成立**——`fact_text`／`natural_text`是SVO抽取＋報告24自然語言化管線的產物，刻意把原文改寫成更通順的句子（例如把「勞工結婚者給予婚假八日，工資照給」拆成「婚假 天數為 八日」＋「婚假 照給 工資」兩條獨立事實），語意保留但字面不同，字面比對必然判定「沒命中」。

### 3.2 具體案例佐證（直接查`run1.json`的lineage/answer欄位）

**17-Q1**（勞工結婚可以請幾天婚假？工資怎麼算？，gold exact_span：「勞工結婚者給予婚假八日，工資照給」）：

- M3實際回答：「根據提供的事實清單，勞工結婚可以請八日婚假。相關事實：婚假 天數為 八日...婚假照給工資：工人結婚者給予八日的婚假，並且在請婚假期間照給工資。」——**內容完全正確**，天數、工資都答對，但因為沒有逐字出現「勞工結婚者給予婚假八日，工資照給」這句，被系統判定為「Stage 1 Retrieval Failure：1/1 gold facts missed」。
- M4同題：「勞工結婚可以請八天婚假...工會成員結婚可獲得八日的婚假。依上述事實，婚假期間照給工資。」——同樣內容正確、同樣被判失敗。
- 三次run（run1/2/3）皆重現同一模式，非單次雜訊。

**18-Q5**（警察人員特別休假核發依據，gold exact_span 三條「有左列情形之一者，給予N至M日之特別休假」）：

- **連M1（chunk-RAG基準）都在這題判定為0%**——但查看M1實際回答：「處理重大治安事件獲大功以上獎勵者可獲得1至3日特別休假；主動破獲重大案件受頒獎以上獎勵者可獲得2至5日特別休假...特殊功績的情況下最高可給予7日的特別休假」——**內容也是對的，只是模型自己換句話說，沒有逐字複製法規的「有左列情形之一者，給予...」這個句式**。這證明**這個測量偏誤不是KG獨有，chunk-RAG一樣會踩到**——只是機率上，chunk-RAG因為上游輸入是法規逐字原文，模型較容易直接複製原文用字，中招機率比KG（上游輸入已經是二次改寫過的Fact）低，不代表chunk-RAG完全沒有這個問題。

**17-Q2**（事假一年最多幾天？有沒有工資？，gold exact_span合併了「十四日上限」+「事假不給工資」兩件事）：

- M4答對14天上限，但答錯/答不出「事假期間不給工資」這半句（誤引「產假期間不給工資」）——查證後這**不是同一種測量偏誤**，是報告50 §3.2已經記錄過的既有抽取缺口（「事假期間不給工資」這個事實從未被抽取成獨立SVO事實）。這題的低分**部分是真缺口、部分是gold_span把兩件事綁成一條字串導致的額外測量問題**（即使兩個子事實都各自被正確抽取成兩條獨立Fact，字面合併比對法一樣會判失敗，因為KG裡不會有一句話同時講完兩件事）。

### 3.3 不受此缺陷影響、可信的發現

- **延遲與成本是直接量測，不受文字比對影響**：M4（K）p50延遲169.64秒為四者最高，M2（B1）僅59.65秒最低——這與報告50/報告18已知的「KG路徑BFS+多階段生成較慢」現象一致，是真實成本，值得記入論文。
- **18-Q4 M4的失敗被正確歸因為「Stage 3 Generation Failure」而非「Stage 1」**——代表這一題正解事實確實有進到prompt context（lineage的retrieval/context assembly兩階段都判定命中），是生成端選擇性拒答/未提取的既有問題（`docs/參考文獻/22_生成端過度保守與選擇性拒答/`已有文獻佐證），不是本節講的測量偏誤，是獨立且真實的缺陷。
- **18-Q5全部4個arm都低分**，且如上所述部分是測量偏誤，但也可能疊加真實的BFS/Fact召回不足（三條相似句式的特別休假規定容易互相干擾，類似26-Q5的DRM機制）——這題值得之後針對「exact_span比對放寬後，分數是否回升」再單獨查一次，才能判斷剩餘缺口有多少是真的。

## 4. 對報告42原結論的重新解讀

報告42（2026-09-13，6題×7arm）也觀察到「B0/B1優於K/K-2b/F」，當時的解讀是「本次樣本剛好是條文結構簡單、單一段落即含完整規則的短規章，chunk-RAG不會遺失結構脈絡」（報告42 §結論2）。**這個解讀本身沒有錯，但本報告的發現補上了一個更根本的解釋層**：即使KG路徑真的檢索到了正確且完整的資訊，只要最終答案或Fact文字的用詞跟`exact_span`不完全一致，就會被這套評分機制打成失敗——所以報告42觀察到的分數差距，有一部分（無法在不重跑的情況下精確量化多少比例）本來就是評分工具的偏誤，不是純粹的檢索/生成能力差距。

## 5. 建議與待決

1. **不建議直接把本報告表1的Acc/Rec數字當成RQ1的正式結論引用**——分母有已知的系統性偏誤，會不公平地低估M3/M4。
2. **要下有效的RQ1結論，需要先修`services/atomic_scorer.py`與`services/lineage_tracker.py`的比對邏輯**——報告51 §6項目2早已指出`atomic_scorer.py`需要「exact_span完全包含快篩→未命中時調用Judge LLM執行NLI蘊含驗證」的兩階段設計；本報告確認`lineage_tracker.py::record_retrieval()`／`record_context_assembly()`需要**同樣的修法**，這是先前沒被明確指出的第二個發生點。這是一個獨立於「文件內二次檢索」（報告50 §4.3）的、更基礎且優先度更高的修復項——不修這個，後續任何A/B比較的Acc/Rec數字都不可信。
3. **這120筆原始資料建議保留**（`rq1_eval_results/sample_expansion_20260915/`）：latency/cost/lineage的retrieval_fact_ids等客觀欄位不受此偏誤影響，等NLI比對修好後，可以直接對同一批`answer`文字重新評分，不需要重新呼叫LLM（省時間與Ollama資源）。
4. **待使用者裁示**：(a) 優先修`AtomicScorer`＋`LineageTracker`的NLI比對邏輯，用現有120筆資料重新評分再下RQ1結論；或 (b) 接受目前的字面比對方法論的侷限，先在論文裡誠實記錄這個侷限，繼續用其他既有的機制證據（報告17/18/25的人工核對結果）支撐RQ1；或 (c) 兩者都做，順序由使用者定。
