> 日期：2026-09-29 ｜ 基準 commit：`8345e90` ｜ 執行者：Codex（依報告129）

## 1. 總結

X1 的實際影響是：文件層級的 `failed` 訊號不是黏性的；某一 chunk 失敗後，另一個 chunk 成功時，`record_chunk_completed()` 會依完成集合把文件狀態改成 `processing`，若完成集合已達 total 則改成 `completed`。因此部分失敗可能被洗成進行中，完整集合也可能讓文件表面上進入完成。完成集合本身仍能避免「缺少某個低索引 chunk 卻誤判全完成」的問題，但它沒有保存失敗 chunk 的獨立訊號。程式與 characterization state machine 的不一致分別見 `services/document_record_service.py:226-254`、`state/document_sm.py:28-60`。

本次 KG#4 真實唯讀快照沒有觀察到 X1 目前留下的不一致：65 份 `_record.json` 的 `extraction_status` 全為 `completed`，兩項狀態／完成集合不一致檢查均為 0，3307 筆佇列列全為 `completed`，與記錄狀態的精確及保守一致性檢查也均為 0。這只能說明本次快照沒有不一致，不能證明歷史執行從未發生過 X1。評估傾向是優先採 X1-A 的最小語意修正（`failed` 保留至全量完成），理由是它修正訊號遺失而不新增資料格式；反對理由是既有重試流程必須明確把 failed chunk 重新排回佇列，否則黏性狀態可能讓使用者誤以為只要有後續成功就會自行恢復。

X3 的實際影響是：記錄檔不存在時，五個記錄寫入函式回傳 `None`；佇列列不存在時，`UPDATE` 影響 0 列但 `update_status()` 仍無回傳訊號。離線重現證實六個目標均回傳 `None`、均未 raise、缺失記錄資料夾不會被建立，缺失列的暫存 DB 只因 SQLite 連線而存在，沒有記錄任何日誌。這正是報告110／113 的 B3 類問題容易靜默通過的原因。本次 KG#4 快照無法證明過去未發生 X3；但目前快照沒有留下可觀察的不一致。評估傾向是先採 X3-A 的 warning 建立可觀測性，再依呼叫點採 X3-B 或 X3-C；不傾向直接全面 X3-D，因為 worker 的錯誤分支、虛擬／缺 record 路徑與既有缺失列測試都會受到高風險影響。反對理由是 warning 本身不修正資料遺失，且沒有契約化回傳值就不能讓呼叫端可靠處理失敗。

本報告只做閱讀、唯讀掃描與暫存目錄離線重現，沒有修復 X1／X3，也沒有修改 production、測試、`state/` 或真實 `kg-runtime` 資料。

## 4. 離線特性重現與選項 A 推演

### 4.1 現行 X1 實際序列

以下序列完全在 `TemporaryDirectory` 中建立 record，沒有使用真實 KG-runtime：

| 序列 | 每一步的實際狀態 |
|---|---|
| failed → PARTIAL（total=3，完成 1） | 初始 mark failed：`failed, [] , progress=0`；完成 1：`processing, [1], progress=1` |
| failed → FULL（total=3，完成 1、2、3） | mark failed：`failed, [] , 0`；完成 1：`processing, [1], 1`；完成 2：`processing, [1,2], 2`；完成 3：`completed, [1,2,3], 3` |
| failed → 多 chunk 到 total（total=4，完成 1、2、3、4） | mark failed：`failed, [] , 0`；完成 1：`processing`；完成 2：`processing`；完成 3：`processing`；完成 4：`completed` |

這重現直接對應 `state/document_sm.py:47-50` 的 characterization：`FAILED + PARTIAL → PROCESSING`、`FAILED + FULL → COMPLETED`。

### 4.2 X1-A「黏性 failed」的純文字推演

以下只是文字推演，沒有修改任何程式碼：

| 序列 | 若採 X1-A，預期狀態 |
|---|---|
| failed → 完成 1／PARTIAL | `failed, [] , 0` → `failed, [1], 1` |
| failed → 完成 1、2／仍 PARTIAL | `failed, [1], 1` → `failed, [1,2], 2` |
| failed → 完成 3／FULL | `failed, [1,2], 2` → `completed, [1,2,3], 3` |
| total=4，依序完成 1、2、3、4 | `failed` 持續到 `[1,2,3]`，最後完成 4 才轉 `completed` |

此推演的關鍵是：完成集合照常累積，但 PARTIAL 事件不能清除 failed。若 failed chunk 沒有被重新 enqueue，集合永遠不會到 FULL；因此 X1-A 必須與明確 retry／requeue 操作一併驗證。

### 4.3 現行 X3 缺失目標結果

對不存在 `_record.json` 的五個函式，以及不存在 queue row 的 `task_queue_service.update_status()`，離線腳本取得：六個呼叫均回傳 `None`；六個呼叫均沒有 raise；缺失記錄資料夾沒有被建立；捕捉到的 logging message 為空。暫存 queue DB 存在只是因為 `task_queue_service` 需要建立 SQLite 連線，位置在系統暫存目錄，不是真實資料。

腳本 import 服務模組時另有一則 `RequestsDependencyWarning` 啟動警告；它發生在缺失目標函式呼叫以前，並非這六個 no-op 的 logging 輸出。這是本次執行記錄的外部依賴警告，不能當成 X3 已有可觀測性。

### 5.3 建議的修復順序與切分（最終由使用者決定）

1. 先選 X3-A 建立 warning 與測試，再用實際 log 判斷哪些缺失是合法過渡、哪些是 invariant 違反；這一步不改回傳與控制流，回滾成本最低。
2. 若確認 document-level failed 必須保留，採 X1-A；同步更新 state characterization、record service 測試與 retry／requeue 測試，先不引入 B 的資料格式。
3. 針對可證明不應缺失且已有前置確認的點，再採 X3-C；`mark_extraction_failed()` 必須先做 safe wrapper，將原始例外保留為主錯誤。若需要跨所有 caller 的可程式化處理，再另案採 X3-B。
4. X1-B 與 X3-D 應視為較大型 migration／契約變更，不應與第一個修復 commit 混合；X1-C 只適合在產品明確接受失敗訊號可被後續成功洗掉時採用。

import sqlite3
from collections import Counter, defaultdict
from pathlib import Path

def stat_signature(path: Path) -> dict[str, int]:
    stat = path.stat()
    return {"mtime_ns": stat.st_mtime_ns, "size": stat.st_size}


def scan_records() -> tuple[dict, dict[Path, dict[str, int]]]:
    before: dict[Path, dict[str, int]] = {}
    payloads: list[dict] = []
    errors: list[dict[str, str]] = []
    folders = sorted((item for item in KG_ROOT.iterdir() if item.is_dir()), key=lambda p: p.name)

    for folder in folders:
        record_path = folder / "_record.json"
        if not record_path.exists():
            errors.append({"folder": folder.name, "reason": "_record.json missing"})
            continue
        before[record_path] = stat_signature(record_path)
        try:
            with record_path.open("r", encoding="utf-8") as handle:
                data = json.load(handle)
            total = data.get("svo_total_chunks") or data.get("total_chunks") or 0
            completed = data.get("completed_chunk_indices") or []
            payloads.append(

                    "folder": folder.name,

                    "status": data.get("extraction_status"),
                    "completed_count": len(completed),

                    "total": total,
                    "svo_total_chunks": data.get("svo_total_chunks"),
                    "total_chunks": data.get("total_chunks"),
                }
            )
        except Exception as exc:  # report the actual unreadable file, never infer it
            errors.append({"folder": folder.name, "reason": f"{type(exc).__name__}: {exc}"})

    status_counts = Counter(item["status"] for item in payloads)
    inconsistencies: list[dict] = []
    for item in payloads:
        total = item["total"]
        count = item["completed_count"]
        status = item["status"]
        if total > 0 and status in {"processing", "failed"} and count >= total:
            inconsistencies.append({"kind": "nonterminal_but_complete_set", **item})
        if total > 0 and status == "completed" and count < total:
            inconsistencies.append({"kind": "completed_but_incomplete_set", **item})

        "record_loaded_count": len(payloads),

    # Required read-only URI form. No schema-changing PRAGMA or write is used.
    read_only_uri = DB_PATH.as_uri() + "?mode=ro"
    with sqlite3.connect(read_only_uri, uri=True) as connection:
        rows = connection.execute(
            "SELECT source, chunk_index, status FROM task_queue "
            "ORDER BY source, chunk_index"
        ).fetchall()

    status_counts = Counter(row[2] for row in rows)
    mapped = 0
    unmatched = 0
    ambiguous = 0
    exact_status_mismatches: list[dict] = []
    semantic_mismatches: list[dict] = []
    for source, chunk_index, queue_status in rows:
        candidates = by_source.get(source, [])
        if len(candidates) == 0:
            unmatched += 1
            continue

            continue

                    "source": source,
                    "chunk_index": chunk_index,
                    "queue_status": queue_status,
                    "record_status": record["status"],
                    "folder": record["folder"],
                }
            )

                    "chunk_index": chunk_index,
                    "queue_status": queue_status,
                    "record_status": record["status"],
                    "completed_count": record["completed_count"],
                    "total": record["total"],
                    "folder": record["folder"],
                }
            )

    db_after = stat_signature(DB_PATH)
    return {
        "db_path": str(DB_PATH),
        "db_read_only_uri": read_only_uri,
        "queue_row_count": len(rows),
