## 1. 動機與範圍

兩個驅動因素：

1. **專案要開源** —— 目前把「台灣勞動法規顧問 + 繁體中文 + CJK 法規列舉」當成產品本體硬編碼在
   `_TAIWAN_CONTEXT_INSTRUCTION`、`_svo_prompt()` few-shot、去重守衛正則群裡。別人拿去接自己的語料，
   這些是障礙而非功能。
2. **一台裝置要同時處理多個 KG** —— 現在做不到：關鍵行為（domain 指示、抽取 few-shot、θ 家族門檻）
   全是 **import-time 模組常數**，一個 process 只能有一種設定。

**時機**：趁報告32 §9 的 θ 敏感度調校（報告27 §6.2 待辦2）還沒把更多「調好的硬編碼值」烤進程式碼之前做，
最划算 —— 調校的產物直接落進 per-KG profile，而非新增常數。

**使用者原則**：通用為主；不為特定 KG 寫一堆單 KG 程式；不綁定單一檔案 / 單一格式存參數。

## 2. 現況勘查摘要

（完整清單見 memory `project-per-kg-config-architecture`。）

**既有的 per-KG 機制只有 3 種**：
- **A**：`KnowledgeGraph` Neo4j 節點欄位 —— 只有 `db_name`、`pronoun_lexicon_exclude`，經 REST update 端點設定。
- **B**：執行時從該 KG 語料推導 —— `_kg_source_charset()` 掃 `workspace/<kg>/*/original.md` 當簡→繁白名單，不儲存。
- **C**：另開 process + 獨立 `workspace_dir`/`.env` —— KG #4 runtime 搬到 `D:/Users/666/Desktop/kg-runtime`。粗粒度。

**三類需要收編的東西**：

| 類別 | 例 | 現況 |
|---|---|---|
| 未校準數值常數（~20 個） | `_SEED_MAX_DEGREE=100`、`_BFS_PER_SEED_LIMIT=30`、`_BFS_EXPAND_WHEN_BELOW=8`、`_BFS_PRIZE_TOP_K=10`、`_FACT_LINE_TRUNCATE_K=18`、`_BFS_KEEP_MAX=18`、`ENTITY_DEDUP_*_THRESHOLD`（0.70/0.88/0.75）、`COMPARE_COSINE_THRESHOLD=0.75`、`QSIM_*`、`UNCOVERED_SENTENCE_THRESHOLD=0.6` | 全域一個值，多數註解自承「暫定未校準」 |
| 領域/語言鎖死的 prompt 與 pattern | `_TAIWAN_CONTEXT_INSTRUCTION`、`_svo_prompt()` 規則6-7 + few-shot、`_NATURALIZE_PROMPT_TEMPLATE` 的繁體假設、`_MEASURE_PATTERN`/`_RANGE_COMPARATOR_PATTERN`/`_ENUM_GUARD_PATTERN`/`_SCOPE_MODIFIER_PATTERN` | 連 KG 都不分，全專案鎖死 |
| 真通用（不動） | `SVO_REL_TYPES`（ConceptNet 35 型）、`ENTITY_TYPES` + `schema_org_entity_types.json`（939 型）、`_RRF_K=60`（Cormack et al.）、DEDUP/reconcile/BFS/grounding 機制骨架 | 留在程式碼 |

## 3. 文獻與參考專案對照

（完整表 + gh api 查證見 `docs/參考文獻/26_設定分層與領域可插拔化/README.md`。）

| 面向 | 先例 | 一句話 |
|---|---|---|
| 分層 config 組合 | **Hydra** ⭐10.6k / **OmegaConf** / **Kustomize** ⭐12.2k / **spaCy** config 系統 | 「以組合建立階層式 config，overlay 只寫要覆蓋的 key」是生產級成熟模式；spaCy 的 `en.token_normalizer→token_normalizer` fallback 就是本專案 `pronoun_lexicon_exclude` 的一般化 |
| 可插拔多來源 | **Dynaconf** ⭐4.3k（檔案/env/Redis/Vault/自訂 loader）/ **pydantic-settings** ⭐1.5k（`settings_customise_sources()`，本專案**已在用**） | 「code 與 settings 間的抽象層」，來源與格式可換；`ConfigSource` 層可直接建在既有 `pydantic-settings` 上 |
| per-stage metric 優化 | **DSPy** ⭐37.8k（teleprompter 對 metric 優化每個 module 的 prompt/few-shot） | 印證「few-shot 不是純 config、是要對 metric 優化的對象」；本專案先做人工版（掃參數 + gate） |
| OFAT vs DOE | **Czitrom 1999**, *The American Statistician* 53(2):126–131 | OFAT 估不到交互作用、交互顯著時導向假最佳點 |
| config drift | Puppet / IBM / AWS Well-Architected / harness-engineering | 過度與不足設定以不同方式失敗；只客製失敗環節是 sprawl 的解方 |
| 多租戶 SaaS | Clerk / Brocoders 等 2026 guides | 「把客戶需求變成 config 而非 code 分支」；客製只該有 settings / theming / extension points |

**結論**：本設計是成熟模式在「per-KG 知識圖譜 pipeline」的套用，**不是發明新機制**，風險屬工程執行面而非架構賭注。

## 4. 設計

### 4.1 三層 config 疊合

```
shipped defaults（Python 模組，逐字 == 現在的常數值 —— 行為零變化的不變式靠它守）
  → domain pack（可插拔：generic / taiwan-labor-law / …）
  → per-KG profile（該 KG 的 overrides，只寫要覆蓋的 key）
  → per-request override（ChatRequest 上少數欄位：svo_hops / top_k）
```

載入時 deep-merge 成一個 **frozen `KGConfig`**，**穿過整條 pipeline**（`bfs_query(cfg=)` / `_build_prompt(cfg=)` /
`resolve_entity_name(cfg=)` …），取代模組常數與 KG 相關的 `settings` 讀取。

「一台裝置多 KG」的關鍵就是這句「穿過 pipeline」—— 改成 `cfg` 參數後，同一 process 能同時服務
「KG-A 用台灣勞動法包 + KG-B 用 generic 包」。

### 4.2 config 來源可插拔（不綁單一檔案/格式）

```
ConfigSource（協定，可多個實作）
    get_kg_overrides(kg_id) -> Mapping        # 部分貢獻，可合併
    get_domain_pack(name)   -> DomainPack
實作：
    FileConfigSource        # 格式由副檔名分派 registry：.json / .yaml / .toml / .py
                            #   yaml、toml 為選配依賴，不裝就只有 json + python
    Neo4jNodeConfigSource   # 讀 KG 節點屬性（延伸機制 A）
    SqliteConfigSource / EnvConfigSource
    DictConfigSource        # 測試注入，不碰檔案系統
    CompositeConfigSource   # 串多個、定優先序
ConfigLoader：defaults → pack → kg overrides → request 逐層 deep-merge → 凍結
```

pipeline 只碰解析後的 `KGConfig`，**不知道也不在乎來源**。身份類參數（`domain_pack` 名）可放 KG 節點、
調校類放檔案，各貢獻一部分，loader 合併。成本近乎為零 —— loader 本來就要逐層 merge，只是把
「每層從哪讀」變成傳入的 `ConfigSource` 而非寫死 `open(path)`。

### 4.3 domain pack

```
domain_packs/generic/           ← 隨專案發佈，預設
  pack.json  { target_language, system_context（中性版）, guard_profile: "none" }
  svo_fewshots.json  []（空，或 domain-neutral 的抽象範例 —— 見 §5 R4）
domain_packs/taiwan-labor-law/  ← 隨專案發佈，當參考實作 + 論文評測語料
  pack.json  { target_language: "zh-Hant",
               system_context: "你是台灣勞動法規顧問…",
               guard_profile: "cjk-legal-enumeration" }
  svo_fewshots.json  [ 事假/特別休假/… 那幾組正反例 ]
guard_profiles/cjk-legal-enumeration.json
  { measure_units: [歲,人,週,級,類,條,款,項,點,…],
    comparator_words: [以上,以下,以內,未滿,未達],
    ordinal_patterns: [第N級, N分之M, 附表N, 之N] }
```

守衛正則從 token 清單「組出來」；`guard_profile: "none"` 直接不掛這些守衛 —— 非 CJK / 非法規語料
本來就不需要。domain pack 覆蓋 generic、找不到就 fallback（比照 spaCy 語言 factory）。

### 4.4 per-stage 評分閘控的客製化生命週期

**stage registry**：每環節登記
`{ id, customizable_params（default + 合理範圍）, eval_metric, gate（低於此分才值得客製）, capability_flags }`。

1. **baseline** —— 新 KG 全跑 generic → per-stage eval suite → scorecard（每環節在 generic 下的分數）
2. **閘控** —— 過 gate 的**留 generic（不修沒壞的）**；不過的標「需客製」
3. **建立參數** —— 標記環節：
   - **調參型** → 跑該環節專屬 sweep，挑一個能過 gate 的 config，寫進 profile 的該環節 key
   - **能力不匹配型** → 切 capability flag / 換 domain pack 片段
   - **兩者都補不上** → **程式/研究缺口（如 §9 的 G 系列），不硬塞參數**
4. **重評 + 迴歸檢查** —— 客製環節 X 不得讓 Y/Z 退步（見 §5 R2）
5. **promote + 版本** —— profile 條目帶：值、佐證的 eval run id、時間戳、「generic 分 N → 客製 M」。可稽核
6. **漂移監看 / 更新** —— 語料長大 / 換模型 / 新增 eval 題時重跑該環節 eval：generic 就過 → 退回 generic
   （profile 保持精簡）；退步 → 重調、版本 +1。這是「更新參數的流程」

**「客製節點」三強度**（越往下越該避免，對齊多租戶 SaaS「config 而非 code 分支」）：

| 強度 | 內容 | 可逆性 |
|---|---|---|
| **param-override** | 同碼、非預設純量 | 高，常態 |
| **capability-toggle / fragment-swap** | 不同分支（守衛開關）/ 不同 prompt 片段（domain pack） | 中 |
| **code fork** | 真為某 KG 寫不同邏輯 | **設計上要罕見且顯眼，最好永不 —— 需要 per-KG 程式碼 = 該環節抽象抓錯** |

**現有 vs 缺的 eval 基礎設施**：查詢端 θ（`run_theta_sweep.py` 🟡）、生成端拒答（`run_refusal_canary.py` 🟡）、
抽取完整性（報告19/20 自檢 🟢）；實體去重門檻 / reconcile 門檻 / 事實清單 K 值 ❌ 目前靠報告手動診斷。
缺的主要是「把散落各報告的手動診斷收斂成 stage-keyed eval suite + gate 定義」。

## 5. 穩定性評估

### 5.1 為什麼這個作法本身穩定

- **模式已被生產環境長期驗證**：Hydra（⭐10.6k，Meta）、Kustomize（⭐12.2k，K8s SIG）、Dynaconf（⭐4.3k）、
  spaCy config 系統都在做「分層組合 + overlay + 可插拔來源」，且都活躍維護（皆 2026-09 內有 push）。
  本設計不引入新機制。
- **本專案已有一半**：`pydantic-settings` 已在用（`ConfigSource` 直接建在上面）；`pronoun_lexicon_exclude`
  已是「per-KG 覆蓋預設、fallback」的實例。這是把既有做法一般化，不是換軌。
- **零行為變化的不變式**：`shipped defaults` 逐字等於現在的常數值 → 遷移全程 pytest 綠、行為不變。
  這是可用 golden test 機械化驗證的硬保證（見 §5.4）。
- **frozen `KGConfig` → 多 KG 併發安全**：不可變物件多執行緒免鎖存取（immutability 文獻）。一個 process
  服務 N 個 KG、各自 `KGConfig` 凍結，天生無共享可變狀態的競態。

### 5.2 已識別的風險與緩解

| # | 風險 | 依據 | 緩解 |
|---|---|---|---|
| **R1** | **config sprawl** —— per-KG profile 越積越多，沒人看得懂，實際狀態偏離 baseline | Puppet / IBM / harness-engineering | 使用者的 **gate-and-retreat 生命週期**：只客製過不了 gate 的環節；generic 重新過 gate 就**刪掉該 override**。profile 條目強制帶 provenance（eval run id + 「generic N → 客製 M」），查得出每個值的來由 |
| **R2** | **OFAT 盲於交互作用** —— `run_theta_sweep.py` 預設「一次動一軸」，交互顯著時挑到假最佳點 | **Czitrom 1999**；本專案已實測耦合（θ sweep 調 X 使 Y/Z 退步、canary FRR/MRR 消長） | OFAT sweep 只當**篩選**（找出哪些軸有影響）。動過的軸要再跑**小型 full/fractional factorial**（`run_theta_sweep.py --full` 已支援 3×3×3）+ §4.4 step 4 的「客製 X 不得讓 Y/Z 退步」硬性迴歸檢查。gate 判定用 factorial 結果、不用 OFAT 結果 |
| **R3** | **淺層 freeze 不夠** —— `KGConfig` 外層凍結、內層巢狀 dict 仍可變 → 併發下仍有競態 | immutability 文獻明確警告 | loader 產出時 **deep-freeze**（巢狀 dict → `MappingProxyType` / frozen dataclass / tuple）。加一條測試：對 `KGConfig` 任一層 setattr / setitem 都要拋錯 |
| **R4** | **generic domain pack 抽取品質下降** —— `_svo_prompt` 空 few-shot 讓 qwen 抽更差 | 文獻16「少樣本提示範例干擾」；報告32 §9.6「qwen 對 prompt 敏感」；DSPy 整個框架的存在前提 | **不宣稱** generic pack 抽取品質等同 taiwan-labor-law pack。taiwan-labor-law 是**已驗證路徑**，論文評測繼續用它。generic pack 給一組 **domain-neutral 抽象範例**（非空），其品質列入 per-stage eval，任何「generic 也夠好」的宣稱都要過 gate。這是研究問題、不是接線問題 |
| **R5** | **函式簽章 churn 面很廣** —— `cfg` 要穿過大量函式 | — | **逐環遷移**（一次一個 stage）+ 每次改動靠「defaults == 現值」不變式 + 全程綠燈。單筆改動風險低、可獨立 review/revert。先接查詢端 θ（本來就要為 §6.2 改） |
| **R6** | **domain pack / profile 版本與程式碼不同步** —— 開源使用者的 pack 對不上新版 schema | config-as-code / everything-as-code 反模式文件 | `KGConfig` schema 帶版本號；loader 對過舊 pack 明確報錯（不靜默用預設）；`generic` pack 隨程式碼一起發佈、一起改，當相容性基準 |

### 5.3 尚無法在設計階段確認、需實作後驗證的點

1. **多 KG 併發真的無競態** —— 需一個「1 process、2 KG、2 domain pack、並行問答」的整合 smoke，斷言兩邊
   `system_context` / θ 值互不污染。設計上 frozen + 穿參數就能保證，但要有測試背書。
2. **deep-merge 的邊角** —— list 是覆蓋還是併接？`None` 是「清除」還是「不覆蓋」？（OmegaConf / Kustomize
   strategic-merge 各有定義）需釘死一套語意並測。
3. **θ 交互作用的實際強度** —— R2 的緩解成本取決於「動過的軸之間交互多強」。DRAIN-DONE 後
   `run_theta_sweep.py --full` 一跑就知道；若交互弱，OFAT + 點狀 factorial 檢查就夠。

### 5.4 建議的「宣告穩定」前置驗證（實作時）

- [ ] **golden test**：`KGConfig`（無任何 source）逐欄位 == 現在的模組常數值。遷移每一環都不得動這條。
- [ ] **deep-immutability test**：`KGConfig` 任一層寫入拋錯。
- [ ] **多 KG 併發 smoke**：見 §5.3-1。
- [ ] **merge 語意 test**：list / `None` / 巢狀覆蓋各一例，對照釘死的規格。
- [ ] **θ 交互作用檢查**：對 OFAT 篩出有影響的軸跑 `--full`，確認 gate 判定不因交互翻盤。
