## 3. 討論形成的方向（**均未定案**，需使用者確認，見 §4）

1. **「缺漏」分三種**：表達缺漏（結構裝不下）、召回缺漏（LLM 沒抽出）、檢索缺漏（圖裡有但沒撈到）。節點分類主要解決前者，對召回缺漏幫助有限；**要先量三種各占多少**。
2. **先捕捉、後結構化**：事實節點＝掛在實體上、尚未結構化的陳述（類似暫存屬性，對應本體計畫的 candidate 狀態）；之後由中間層升級為屬性、關係、事件或規則。這與本專案現有 Fact 節點不同：現有 Fact 在三元組**之後**產生（缺漏會一路傳遞），使用者設想的事實節點在抽取**最前面**。
3. **依內容選框架**：發生過的事用**事件框架**（人事時地物）；法規條文是規範，用**規則框架**（主體、模態應／得／不得／視為、行為、對象、條件、例外、期限、數量）；其餘陳述留作事實節點。本體計畫自己也把「事件（Round3）」與「法規規則（Round4）」分開。
4. **案件端事件的「時」「地」是選版本的索引鍵**：必須結構化（正規化日期、管轄代碼），缺少就標示並交人工，不由模型猜。
5. **查不到事件當時的版本就阻擋／拒答，不以現行版本頂替**（本體計畫 WP6 的 `NO_EXACT_VERSION → BLOCKED`；與本專案「寧願說不知道」一致）。
6. **時間過濾要確定性**：文獻（時間誤接地、LexKairos）顯示 LLM 與向量檢索在版本選擇上不可靠；日期與管轄的比對應以結構化條件處理。
7. **裁判＝裁判支援**：產出裁決紀錄（事件、適用的規則版本與理由、各條件成立與否、確定性規則的計算結果、待人工裁決的爭點），需詮釋者交人工——與本體計畫「系統不得自動作成最終決定」一致。
